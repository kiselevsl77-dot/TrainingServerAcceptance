## 2. Новые операции: AutoML (8)

Тег `ML models: AutoML`, пути `/api/ml_models/**/find_params/**`. Смысл блока: поиск
гиперпараметров и архитектуры (NAS) — из базовой модели генерируется «популяция» мутированных
конфигураций, затем итерациями отбора (`selection`) каждая конфигурация обучается и
ранжируется, после чего выгружается сетка «конфигурация × метрика».

| № | Метод и путь | Ответ | Назначение и важные детали |
|---|---|---|---|
| 27 | `POST /api/ml_models/models/{model_id}/find_params/population` | 201, `FindParamsPopulationCreateResponse` | Создать популяцию мутантов из существующей базовой модели. Базовая модель — **только источник конфига**: каждый мутант создаётся как новая модель со случайной инициализацией, веса не наследуются. Если хотя бы один мутант не материализовался — откат целиком (частичной популяции не остаётся). Тело: `name`, `description?`, `population_config` (обяз.). |
| 28 | `POST /api/ml_models/find_params/population/{population_id}/selection` | **202**, `FindParamsSelectionRunResponse` (`task_id`, `runtime_id`, `population_id`, `message`) | Одна train-check итерация: создаётся задача `find-params` (Celery, асинхронно), обучаются все активные мутанты на `train_dataset_id`, тестируются на `test_dataset_id` (по умолчанию = train), сохраняется строка `find_params_selection` + `check_results` по каждому мутанту, проставляются метки отбора. Тело: `train_dataset_id` (обяз.), `test_dataset_id?`, `train_config?`, `test_config?`, `selection_config?`, `name?`. |

Необратимо. |
| 30 | `GET /api/ml_models/find_params/population/{population_id}` | 200, `FindParamsPopulation` | Одна популяция: `base_config`, `base_model_id?`, `name`, `description?`, `created_at`, `updated_at`. |

| 32 | `GET /api/ml_models/find_params/population/{population_id}/mutated_models` | 200, `[FindParamsMutatedModel]` | Мутанты с фильтром по метке и сортировкой по рангу. ## 3. Новые схемы (15)

| Схема | Тип | Обязательные поля | Что описывает |
|---|---|---|---|
| `PopulationConfig` | object | `rules` | Конфиг сетки: `include_base_in_population` (добавлять ли базовую модель в популяцию), `rng_seed?` (детерминизм `random_choice`), `rules[]` — список правил. Размер популяции = произведение `models_amount` по всем правилам. |
| `MutationRangeRule` | object | `path`, `mode`, `models_amount`, `range` | Ось-диапазон: `path` — dot-путь с навигаторами `[N]`/`[*]` (несколько путей через `;`, пробелы игнорируются; несуществующие сегменты молча пропускаются, новые ключи не создаются), `mode` (`scale`/`set`/`add`), `models_amount ≥ 1`, `range [low, high]`, `bounds?` (clamp), `uniform` (default `true`; `false` в grid-режиме не поддерживается), `round?`, `type` = `"range"` (дискриминатор). |
| `MutationValuesRule` | object | `path`, `mode`, `models_amount`, `values` | Ось-перечисление: `values[]` (числа или строки — так перебираются категориальные параметры при `mode='set'`, например `activation`), `random_choice`, остальное как у range; `type` = `"values"`. `bounds`/`round` не применяются. |
| `MutationMode` | string enum | — | `scale` (new = old × value), `set` (new = value), `add` (new = old + value; значение может быть отрицательным). `scale`/`add` молча пропускают нечисловые совпадения. |
| `RoundMode` | string enum | — | `int`, `nearest_pow2`, `none` (default) — округление после clamp. |
| `SelectionConfig` | object | — | Шаг разметки: `best_count` (default 1), `discarded_count` (default 1), `sort_keys[]` — уровни ранжирования. |
| `SortKey` | object | `metric`, `direction` | Уровень ранжирования: `metric` (`accuracy` \| `loss` \| путь конфига), `direction` (`asc`/`desc`), `tolerance?` (значения в пределах допуска считаются равными — решает следующий уровень), `aggregate` (`sum`/`mean`/`max`/`min`, default `sum`) для метрик-путей. Уровни применяются лексикографически. |
| `FindParamsPopulationCreateRequest` | object | `name`, `population_config` | Тело №27: `name` (≤200), `description?`, `population_config`. |
| `FindParamsPopulationCreateResponse` | object | `population_id`, `base_model_id`, `name`, `include_base_in_population`, `num_mutants`, `mutated_model_ids` | Ответ №27: `num_mutants` — производная величина (произведение `models_amount`), `mutated_model_ids[]` — идентификаторы созданных записей мутантов. |
| `FindParamsPopulation` | object | `id`, `name`, `base_config`, `created_at`, `updated_at` | Чтение популяции: `base_config` — конфиг базовой модели, `base_model_id?`, `description?`. |
| `FindParamsSelection` | object | `id`, `population_id`, `name`, `train_config`, `created_at`, `updated_at` | Итерация отбора: `dataset_id?`, `check_dataset_id?`, `train_config`, `test_config?`. |
| `FindParamsSelectionRunRequest` | object | `train_dataset_id` | Тело №28: `test_dataset_id?` (по умолчанию = train), `train_config?`, `test_config?`, `selection_config?`, `name?` (≤200). |
| `FindParamsSelectionRunResponse` | object | `task_id`, `runtime_id`, `population_id`, `message` | Ответ №28: `task_id` — задача `find-params` для монитора задач пульта (`GET /api/tasks/{task_id}`). |
| `FindParamsMutatedModel` | object | `id`, `population_id`, `config_mutations`, `created_at`, `updated_at` | Мутант: `model_id?`, `config_mutations` (свободный объект), `check_results[]` (свободные объекты, аккумулируются по итерациям), `label?`, `label_description?`. |
| `FindParamsLabel` | string enum | — | `normal`, `best`, `discarded`, `failed` — метка мутанта после последней итерации. |

Обратная сторона для пульта: `base_config`, `config_mutations`, `check_results`, `train_config`,
`test_config` — свободные `object` без свойств и примеров (§7.4), поэтому заготовку тела
итерации и разбор результатов нельзя построить «по схеме».

**нет** (существует только `GET` того же пути, №31). Либо ссылка устарела, либо операция не
описана. Приоритет **P1**: вводит в заблуждение при планировании, но обходится — популяция
создаётся от существующей модели (№27). Предложение: либо добавить операцию в контракт, либо
исправить описание.

**7.2. `text/csv` не поддержан пультом.** Ответ №34 (`grid.csv`) описан как `text/csv`, а
генератор реестра (`tools/gen_endpoints.py::_response_kind`) различает только
`application/json` (→ `json`), `application/octet-stream` (→ `binary`) и пустой контент
(→ `empty`). Проверено: сейчас реестр покажет для `grid.csv` вид ответа `json` — это вводит в
заблуждение и в консоли, и в отчёте. Нужен новый вид ответа (`csv`) либо запись в
`RESPONSE_OVERRIDES`. Отдельно фиксируется как единственный не-JSON media-тип в новом
контракте (в старом таких не было вовсе).

**7.3. Схема ответа списка нагрузок по-прежнему пуста.** `GET /api/loads/list` описывает ответ
как `application/json` со схемой `{}`, фактически приходит `{loads, result_size, limit, offset}`.
Приоритет **P1**, без изменений: в новой версии убрали `ph_n`, но ответ так и не описали.

**7.4. Свободные `object` в AutoML.** `base_config`, `config_mutations`, `check_results`,
`train_config`, `test_config` не имеют ни свойств, ни примеров: тело итерации отбора и разбор
результатов придётся собирать и читать эвристически (как с `config` модели — существующее
замечание P2). Для приёмочных проверок это означает: валидацию «по схеме» для этих полей
провести нельзя, проверяем факт и структуру ответа.

**7.5. `servers`/`security` не описаны** (как и раньше): базовый URL и авторизация держатся вне
контракта (переменная `TRAINING_SERVER_BASE_URL`), `securitySchemes` пусты. Приоритет **P2**.

**7.6. Каскадное удаление без предпросмотра.** №29 удаляет lineage целиком (модели, сигналы,
файлы, S3-блобы, ZIP-ы) без «сухого прогона» и без счётчиков «что будет удалено». На общем
стенде это требует максимально строгого подтверждения в пульте (полный `id`, только
`__TEST__`-популяции, созданные пультом). Приоритет **P2** (эксплуатационное требование).

**7.7. Что осталось без изменений в лучшую сторону.** Теги `Система`, `File Import`,
`Datasets`, `Loads`, `Task service` — состав операций тот же; описания `summary`/`description`
существующих операций не переписывались (кроме новых), поэтому замечания к API из
`SOM1. Комментарии.md` по файлам, датасетам, задачам и моделям остаются в силе.

### 10.2. Требования к независимости AutoML (обязательные)

AutoML — отдельный функционал: его недоступность, ошибки или невыполненные проверки **не
должны** влиять на приёмку остальных модулей. Обязательные требования:

1. **Отдельный модуль и группа.** Сценарии — в `acceptance/checks/automl.py`, группа —
   отдельный `GroupPlan` (`TC-AUTO`, 8 проверок) в `acceptance/checks/catalog.py`; идентификаторы
   `TC-AUTO-01…08` заводятся в `docs/02. Чек-лист испытаний.md` (§14, §15) при наполнении группы.
2. **Отказ ≠ недоступность.** Если операций AutoML нет в сборке сервера (404/405 или отсутствие
   маршрута вообще), группа получает статус «пропущена / недоступна в сборке» с отдельным
   замечанием-подсказкой; это **не** `FAILED` и не влияет на статусы чужих групп.
3. **Не входит в групповой прогон.** AutoML-проверки не попадают в `run_checks(..., only_tech=True)`
   остальных групп и не выполняются «по умолчанию» вместе с безопасным набором: запуск — только
   явным выбором группы (по той же логике, что классы `live`/`heavy`).
4. **Независимость по данным.** Для проверок нужны `model_id` (существующая модель) и
   заполненный датасет; если их нет — `PreconditionError` → «пропущена (нет данных)», остальные
   группы, снимок стенда и отчёт не затрагиваются.
5. **Независимость в отчёте.** Раздел AutoML включается только если его проверки выполнялись;
   агрегаты и проценты по остальным группам считаются без него (его наличие/отсутствие не
   меняет итоговые показатели приёмки по T1–T9).
6. **Независимость регрессии.** Тесты группы — отдельный файл `tests/unit/test_checks_automl.py`;
   фейковый стенд без AutoML-маршрутов не ломает `test_checks_loads/files/records/system/tasks`;
   `python -m pytest tests -q` остаётся зелёным при любом состоянии блока AutoML.
7. **Реестр консоли — исключение.** 8 операций AutoML присутствуют в реестре всегда (реестр
   выводится из контракта, а не из сборки сервера), поэтому они видны в консоли и в выгрузках
   реестра даже если сервер их не поддерживает — с классами безопасности и подтверждениями.
