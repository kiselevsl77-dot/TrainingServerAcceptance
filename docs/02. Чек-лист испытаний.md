> **Назначение.** Программа испытаний текущей версии сервера обучения: перечень
> проверок `TC-<модуль>-<NN>` с трассировкой на требования постановки
> (`UC-01…UC-28`, `FR-1…FR-8`, `NFR-1…NFR-7`, `BR-F1…BR-F7`, `BR-R1…BR-R10`, `FSM-1`).
> Выполняется пультом испытаний (ТЗ — `01. ТЗ на пульт испытаний (временный UI).md`).

> **Дата:** 15.09.2026. **Стенд:** `https://energomera.ai-center.online`, сборка `dev@58ac72f`
> (фактическую сборку фиксировать снимком стенда на начало сессии).

## 1. Классы проверок

| Класс | Что означает | Условие запуска |
|---|---|---|
| `tech` | безопасная проверка: чтение и валидация контракта, без изменения данных | выполняется всегда |
| `live` | боевая проверка на реальных данных стенда | подтверждение оператора, указание цели и используемых данных |
| `heavy` | ресурсоёмкая: `fill` больших объёмов, `train`, `check`, async `inference` | карточка запуска (FR-T10): цель, данные, параметры, ответственный, оценка длительности, подтверждение расхода ресурсов, решение о судьбе артефакта |
| `manual` | проверка, выполняемая только человеком (визуальная, организационная) | отметка «выполнена вручную» + заключение оператора |

## 2. Статусы проверок

| Статус | Когда ставится |
|---|---|
| `успех` | факт совпал с ожидаемым результатом |
| `отказ` | сервер/API повёл себя иначе, чем требует ожидаемый результат |
| `блокировано API` | проверка не может быть выполнена из-за известного дефекта/пробела API; автоматически формируется замечание к API (FR-T7) |
| `прервана` | обрыв связи/таймаут/перезапуск сервера или пульта (BR-R5, BR-R6) |
| `пропущена` | проверка неприменима к текущей конфигурации стенда (например, нет подходящих данных) |
| `выполнена вручную` | подтверждено заключением оператора с доказательством |

## 3. Общие правила выполнения

1. Перед сессией — снимок стенда «Начало»; после — «Окончание» (изменение реестров
   попадает в отчёт).
2. Изменяющие проверки работают только с сущностями `__TEST__…` и всегда заканчиваются
   самоочисткой; перечень созданного и удалённого — обязательный раздел отчёта.
3. Сущности без префикса `__TEST__` не изменяются и не удаляются.
4. Крупные файлы RAW (до 2.1 ГБ) не скачиваются без явного решения оператора
   (нет `Range`/`Content-Length` — замечание к API).
5. Каждая проверка выполняется с меткой `TC-…`: все её запросы находятся в журнале
   фильтром по метке, а в отчёте указывается диапазон номеров записей журнала.
6. Ресурсоёмкие проверки (`heavy`) допустимы в сессии испытаний, но не в автотестах пульта.

## 15. Порядок выполнения и отчётность

1. Порядок групп по этапам пульта: **T3** — TC-SYS, TC-FILE, TC-REC, TC-LOAD;
   **T4** — TC-TASK (и монитор задач как инфраструктура); **T5** — TC-DS;
   **T6** — TC-MOD; **T7** — TC-TR; **T8** — TC-INF; **T9** — TC-CLEAN и финализация.
2. Каждая проверка выполняется с меткой `TC-…`; в отчёте указываются номер записи
   журнала (диапазон) и доказательства (идентификаторы сущностей, размеры, ответы).
3. Итог сессии — один из вариантов: «годен», «годен с замечаниями», «не годен»,
   «не определён» (при незавершённых проверках); решение фиксируется в сессии.
4. Ресурсоёмкие проверки (TC-DS-05, TC-TR-02…05, TC-INF-01) выполняются в сессиях
   испытаний по решению заказчика, с указанием ответственного и подтверждением расхода
   ресурсов; в автотестах пульта они не запускаются.
5. Все проверки — без изменений испытуемого API: любое требование к API фиксируется
   замечанием (п. 3.2 ТЗ) либо перспективным требованием (п. 3.3 ТЗ, включая субдатасеты).
