## 2. Правила объединения (прозрачность, NFR-T2)

1. файлы классифицируются по имени: `<имя>.raw.csv` → RAW, `<имя>.markup.csv` → markup,
   остальное (`.h5`, `.onnx`, `.zip`) → «прочие файлы»;
2. внутри базы имени RAW сопоставляется с markup **по времени импорта**: берётся ближайшая
   разметка не раньше RAW; Δ ≤ 1 ч → уверенность «подтверждено», иначе «не подтверждено»
   (карточка помечается ⚠️);
3. ручное решение оператора приоритетнее эвристики и помечается «вручную» (иконка 🖐️);
4. разметка всегда принадлежит ровно одной записи: при привязке к другой записи прежняя
   её теряет, «последнее решение выигрывает»;
5. записи без разметки и разметка без RAW не скрываются — отдельные разделы;
6. актуальной версией считается последняя по `import_date`; оператор может отметить иную
   (событие журнала `record_override`, действие `current`);
7. манифест содержит **все** файлы реестра: каждый файл — ровно один раз (`raw_id`,
   `markup_id` либо отдельная строка); полнота проверяется автоматически
   (`RecordsOverview.manifest_is_complete`).

| Записей без разметки | 0 |
| Разметка без RAW | 0 |
| Записей-дублей | 128 в 61 базе имени (у одной базы 3 версии) |
| Объём | RAW ≈ 39 ГБ, markup ≈ 160 МБ |
| Полнота манифеста | контроль пройден (`True`) |
| Примеры дублей | `Antminer_S19`: 2 107 657 231 Б (13:53) и 110 929 639 Б (14:42); `3Dпринтер`: 24 566 291 Б и 1 282 054 Б; `Avalon_1240`: 2 177 904 636 Б и 114 626 610 Б |
| Разбор разметки | `Antminer_S19.markup.csv`: записей 2250, чанков 2250 (клиентская оценка) |
| Дефект API | скачивание `3Dпринтер.raw.csv` → `404`, `'latin-1' codec can't encode characters…`; не-ASCII имена у **108 из 129** записей |

Наблюдения, важные для приёмки:

1. **Дубли — это норма реестра, а не редкость**: почти каждая база имени загружена дважды,
   причём версии различаются размером в разы. Без объединения в записи и без `checksum`
   оператор не может отличить актуальную версию от повторной загрузки — требование ТЗ (п. 3.1)
   подтверждено фактом.
2. **Разметка разбирается только для ASCII-имён** (21 из 129 записей) — следствие дефекта
   `latin-1`; для остальных записей экран показывает статус «заблокировано API» и
   автоматически создаёт замечание.
3. `chunks == records` в проверенном markup-файле: каждый `chunkID` встречается один раз
   (несколько записей на чанк в этом файле нет). Это наблюдение для проверки TC-REC-05 на
   других файлах, а не дефект пульта.

## 5. Дефекты и ограничения API, выявленные на этапе

| # | Наблюдение | Приоритет | Обходной путь пульта |
|---|---|---|---|
| 1 | скачивание файлов с не-ASCII именами: `404`/`latin-1` (108 из 129 записей) | P0 | статус «заблокировано API», авто-замечание, разбор разметки только для ASCII-имён |
| 2 | нет `checksum`/`updated_at` у файлов | P1 | версии различаются по `id`/`size`/`import_date`/`s3_path`, актуальная — по дате или решению оператора |
| 3 | нет сущности «запись» (пары RAW+markup) | P1 | объединение выполняет пульт по явному правилу, манифест — приложение к отчёту |
| 4 | нет агрегатов (число записей/чанков) и состава датасета | P1 | разбор markup-файла клиентом, пометка «клиентская оценка» |
| 5 | скачивание отдаёт файл целиком (нет `Content-Length`/`Range`/`ETag`) | P1 | прогресс по факту получения, крупные RAW — только с подтверждением оператора |
| 6 | `GET /api/data/files` игнорирует `limit`/`offset` | P2 | клиентская пагинация и кэш реестра 60 с |

## 6. Что осталось за рамками T1 (не блокирует)

* полноценный **отчёт об испытаниях** (FR-T8/FR-T9, этап T9): манифест уже сохраняется в
  `acceptance_data/artifacts/` и регистрируется в сессии — раздел отчёта подключится на T9;
* **чек-лист** TC-REC (этап T3): проверки описаны, автозапуск появится вместе с движком проверок;
* групповые действия по записям (массовая привязка/исключение) — ТЗ их не требует;
* сравнение структурных характеристик версий выполняется по факту наличия разметки; для
  записей с не-ASCII именами оно станет возможным после исправления дефекта №1.
