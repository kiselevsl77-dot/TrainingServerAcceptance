# Комментарий к `SOM1.json` — описание API, нестыковки и предложения по изменениям

> **О документе.** Разбор OpenAPI-спецификации сервера обучения Energomera: что в ней есть,
> где она расходится с фактическим поведением сервера в уже проработанной части (FR-1…FR-3:
> «Система», «Файлы / Субдатасеты», «Нагрузки») и что хотелось бы изменить — включая сущности,
> которых в API изначально не предусмотрено (в первую очередь **субдатасет**).
>
> **Адресат:** команда сервера обучения (владелец `SOM1.json`), заказчик UI.
> **Дата разбора:** 15.09.2026.
>
> **На чём основано:**
> 1. Спецификация `context/01. Постановка/SOM1.json` — OpenAPI 3.1.0, `info = {Energomera, 0.1.0}`,
>    **27 путей / 32 операции / 34 схемы**, 6 тегов.
> 2. Живой сервис `https://energomera.ai-center.online` (`GET /version` → branch `dev`,
>    revision `58ac72f`, build 14.09.2026) — проверки выполнялись реальными запросами.
> 3. Реализованные и проверенные этапы UI: **этап 0** (FR-1), **этап 1** (FR-2),
>    **этап 2** (FR-3). Поведение зафиксировано интеграционными тестами (`tests/integration/`,
>    см. Приложение В).

## 1. Описание API

### 1.1 Общие сведения

| Параметр | Значение |
|---|---|
| Формат | OpenAPI 3.1.0, `info.title = Energomera`, `info.version = 0.1.0` |
| Состав | 27 путей, 32 операции, 34 схемы; теги: `Система`, `File Import`, `Datasets`, `Loads`, `ML models`, `Task service` |
| Базовый URL | **в спецификации отсутствует** (`servers` не задан) — адрес держится вне контракта (в UI — переменная `TRAINING_SERVER_BASE_URL`) |
| Авторизация | **не описана**: `securitySchemes` и `security` пусты |
| Форматы | JSON; загрузка — `multipart/form-data`; скачивание объявлено как `application/json`, фактически — бинарный поток |
| Асинхронность | Celery-задачи: `datasets/fill`, `models/{id}/train`, `ml_models/{id}/check`, `inference`, `tasks/test`; `inference/single` — синхронный |
| Идентификаторы | UUID у файлов/датасетов/моделей/задач; **строка** у нагрузок (`load_id` — бизнес-ключ, а не UUID) |

### 1.2 Состав по модулям

| Тег | Операции | Назначение | Проработка в UI |
|---|---|---|---|
| `Система` | `GET /health`, `GET /version` | доступность и сборка | этап 0 (FR-1) ✅ |
| `File Import` | `POST /api/data/file`, `GET /api/data/files`, `GET /api/data/file/{file_id}/download`, `DELETE /api/{file_id}` | реестр файлов, загрузка / скачивание / удаление | этап 1 (FR-2) ✅ |
| `Loads` | `GET /api/loads/list`, `POST /api/loads`, `PUT /api/loads/{load_id}` | реестр нагрузок (устройств) | этап 2 (FR-3) ✅ — чтение; запись UC-07/UC-08 — задел |
| `Datasets` | `GET/POST /api/datasets/`, `GET/PUT/DELETE /api/datasets/{dataset_id}`, `POST /api/datasets/fill/{dataset_id}` | датасеты и их заполнение | план этапа 3 (FR-4) |
| `ML models` | `GET/POST /api/ml_models/models`, `POST /api/ml_models/models/upload`, `GET /api/ml_models/architectures`, `GET/DELETE /api/ml_models/models/{model_id}`, `POST /api/ml_models/models/{model_id}/train`, `POST /api/ml_models/{model_id}/check`, `POST /api/ml_models/models/{model_id}/inference`, `POST .../inference/single`, `GET .../download_onnx` | каталог архитектур, модели, обучение / проверка / инференс | частично: `GET /api/ml_models/models` (этап 2), остальное — этапы 4–7 |
| `Task service` | `POST /api/tasks/test`, `POST /api/tasks/{task_id}/pause\|interrupt\|resume`, `GET /api/tasks/`, `GET /api/tasks/{task_id}` | мониторинг и управление задачами | план этапов 3–8 (FR-8) |

### 1.3 Сущности и связи

| Сущность | Ключ | Поля (фактически) | Связи в API |
|---|---|---|---|
| Файл | `id` (UUID) | `file_name`, `size`, `s3_path`, `import_date`, `file_type` | **нет** (ни с датасетом, ни внутри пары RAW↔markup) |
| Нагрузка | `load_id` (строка) | `category`, `description` (+ `phase_connection` только на запись) | **нет** (с моделями — только через `device_id`, которого в нагрузке нет) |
| Датасет | `id` (UUID) | `name`, `description`, `type` (`const = "direct_fill"`), `creation_date` | `fill` принимает `raw_file_ids`/`markup_file_ids`, но состав в ответе **не отдаётся** |
| Модель | `id` (UUID) | `architecture`, `version`, `name`, `phase_type`, `output_size`, `config`, `metrics`, `pruning_mask`, `created_at`/`updated_at`, `signals`, `signal_aliases` | `signals` = «номер сигнала → `device_id[]`» (в живых данных пусто) |
| Задача | `id` (UUID) | `type`, `name`, `description`, `created_at`, `runtimes[]` (`status`, `celery_task_id`, `parameters`, `start_time`/`end_time`, `result`, `intermediate_result`) | явных ссылок на сущности нет — только `name` вида `fill_dataset_<uuid>_<hash>` |

Связи, которые API подразумевает, но не публикует: **File ↔ Dataset**, **File ↔ File**
(RAW↔markup, т.е. субдатасет), **Load ↔ Subdataset/Dataset/Model**, **Task ↔ Dataset/Model**.

### 1.4 Конвенции (сейчас неоднородные)

| Тема | Вариант 1 | Вариант 2 | Вариант 3 |
|---|---|---|---|
| Пагинация | **отсутствует**: `/api/data/files` (`{files, count}`), `/api/ml_models/models` (`{models, count}`), `/api/datasets/` (`{datasets, count}`) | `limit`/`offset` + `count`: `/api/tasks/` (limit 1…1000, default 100; offset ≥ 0) | `limit`/`offset` + **эхо в теле**: `/api/loads/list` (`{loads, result_size, limit, offset}`) |
| Ошибки | `HTTPValidationError.detail[] = [{loc, msg, type}]` (422, FastAPI) | `{"detail": "<строка>"}` — фактически при 400/404 (в спеке не документировано) | 404 `{"detail": "…codec…"}` — дефект кодировки |
| Запуск async | `ModelTrainingResponse.task_id`, `ModelCheckResponse.task_id`, `InferenceStartResponse.task_id` | `POST /api/datasets/fill/{id}` → `202 {}` (**без `task_id`**) | — |

## 2. Недочёты и нестыковки в проработанной части (FR-1, FR-2, FR-3)

### 2.1 Спецификация не соответствует фактическому серверу

| № | Эндпоинт | Заявлено в `SOM1.json` | Фактически (живой сервис) | Последствие для UI |
|---|---|---|---|---|
| 1 | `GET /health` | `200`, схема `{}` | `{"status":"OK","environment":"dev"}` | нет контракта — ответ разбирается «на глаз» |
| 2 | `GET /version` | `200`, схема `{}` | `{branch, revision, commit, message, author, email, build_date}` | нельзя надёжно определить смену сборки (BR-R8) |
| 3 | `GET /api/data/files` | 4 параметра без `description`; только `200`/`422` | `file_name` — **подстрока** (`Antminer` → 8 записей); `file_type` — **точное и регистрозависимое** (`raw` → 0, `RAW` → 129); `import_date` — только дата (238 из 265 за `2026-09-09`) | оператор не знает правил фильтрации; фильтр по времени невозможен (поле `date-time`, параметр `date`) |
| 4 | `FileMetadataResponse` | `id, file_name, size, s3_path, import_date, file_type` | в ответе **нет `description`**, хотя загрузка его принимает (`Body_upload_data_file…description`) | загруженное описание теряется — недоступно ни в списке, ни в карточке |
| 5 | `GET /api/data/file/{file_id}/download` | `200` c `content: application/json`, схема `{}`; документированы только `200`/`422` | бинарный поток: `content-type: application/octet-stream`, `content-disposition: attachment; filename=…`, **нет `Content-Length`**, **нет `Accept-Ranges`**; при не-ASCII имени — `404 {"detail":"'latin-1' codec can't encode characters…"}` | нет прогресса загрузки и докачки (файлы до 2.1 ГБ, всего 41.7 ГБ); **54 из 62 субдатасетов** не скачиваются вовсе |
| 6 | `DELETE /api/{file_id}` | `200`, схема `{}`; 404 не описан | `{"message":"File deleted successfully", …}`; путь — **в корне `/api/`** | риск коллизии с любым будущим маршрутом `/api/<x>`; ответ разбирается эвристикой; batch-удаления пары нет |
| 7 | `GET /api/loads/list` | параметры `category, ph_n, load_id, description_search, limit, offset` **без описаний**; ответ `{}` | `{loads, result_size, limit, offset}`; элемент `{load_id, category, description}` — **без `phase_connection`**; `ph_n` **не фильтрует**; `limit=0` → пустой список при `result_size = 62` | схема `LoadDevice` неприменима (фаза обязательна) → отдельная модель `LoadItem`; фильтр по фазе недоступен |
| 8 | `POST /api/loads`, `PUT /api/loads/{load_id}` | `200`, схема `{}`; 404/409 нет | — | нельзя показать, что именно создано/изменено; нет семантики конфликтов (BR-R3) |

| 9 | `DELETE` нагрузки | **отсутствует** | — | ошибочную нагрузку нельзя удалить (файлы/датасеты/модели удаляются) |
| 10 | `POST /api/datasets/fill/{dataset_id}` | `202`, схема `{}` | в описании задачи видно «Fill dataset … with 52 raw and 52 markup files» — данные есть внутри, наружу не отдаются | UI не может перейти к мониторингу (нет `task_id`), хотя `train`/`check`/`inference` его возвращают |
| 11 | `ModelMetadata.signals` | `array` **без `items`** | в запросе `ModelCreateRequest.signals` — `object {signal_num → [device_id]}`; живые модели: `null`/пусто | противоречие типов «запрос ↔ ответ»; отобразить привязки нельзя |
| 12 | `phase_connection`, `ph_n` | свободная `string`, без справочника и описания | в разметке: `Ph_A`, `Ph_B`, **`Ph_С`** (кириллическая `С`); фазы живут только в markup-файлах | нет валидации и подсказок; фазы показываются только как часть «набора нагрузок» |
| 13 | `device_id` vs `load_id` | у моделей фильтр `device_id`, в `InferenceClass` — `device_ids`, в разметке — `LoadID` | реестр нагрузок устройства не отдаёт | неясно, как сопоставлять модель и нагрузки («набор нагрузок модели» строится эвристикой) |
| 14 | `DatasetType` | `const: "direct_fill"` (одно значение) | все 6 живых датасетов — `direct_fill` | любое расширение (например, датасет из субдатасетов) — ломающее изменение контракта |
| 15 | `file_type` | `string`; в описании параметра — «RAW, LOADS, ONNX» | фактически `RAW` 129, `LOADS` 129, `H5` 5, `REPORT_ZIP` 2 | значения вне контракта; в UI появился раздел «Прочие файлы» и своя таблица MIME-типов |

### 2.2 Внутренние несогласованности API

1. **Три конвенции пагинации** в одном API (см. 1.4) — клиенту нужны три разных обработчика;
   `count` и `result_size` — синонимы с разными именами.
2. **Маршруты одной сущности в трёх префиксах:** `POST /api/data/file` (ед. ч.),
   `GET /api/data/files` (мн. ч.), `DELETE /api/{file_id}` (корень `/api/`).
3. **`POST /api/ml_models/{model_id}/check`** вместо `/api/ml_models/models/{model_id}/check` —
   выбивается из остальных маршрутов моделей (то же, что и `DELETE /api/{file_id}`).
4. **Асимметрия CRUD:** удаление есть у файлов, датасетов, моделей, но не у нагрузок;
   обновления нет у файлов; у датасетов нет «очистить/перезаполнить».
5. **Нет `updated_at`** у файлов и нагрузок (BR-R2 требует для изменяемых сущностей) —
   при повторной загрузке/правке невозможно понять, что актуально.
6. **Не описан контракт разметки:** формат markup-файла (`markupId;chunkID;LoadID;Ph_n;Category`,
   разделитель `;`, UTF-8), допустимые значения `Ph_n`, правило «`LoadID` = реестр нагрузок» —
   всё это UI узнал реверс-инжинирингом.
7. **Не описаны `servers` и `security`** — базовый URL и задел авторизации (NFR-7) вне контракта.

## 3. Предлагаемые изменения API

### 3.1 Субдатасет — сущность первого класса (главный запрос)

**Зачем.** Обучение и проверка идут не по отдельному файлу, а по **паре** RAW (осциллограмма) +
markup (разметка): живые данные — 129 RAW + 129 LOADS = 62 пары. В API пары не существуют:
UI обязан склеивать их по имени и времени импорта (эвристика), а сервер при `fill` расставляет
соответствие сам и не показывает его (в тексте задачи видно «52 raw and 52 markup files»).
При 41.7 ГБ файлов ошибка в паре дорога и при этом не диагностируется.

**Вариант A (полноценная сущность, рекомендуемый).** Ресурс `/api/subdatasets/`:

```json
{
  "id": "0f5f0e0e-0000-4000-8000-000000000001",
  "name": "Antminer_S19",
  "status": "complete",
  "version": 2,
  "raw":    {"file_id": "…", "file_name": "Antminer_S19.raw.csv",    "size": 12345678,
             "import_date": "…", "checksum": "sha256:…", "records": 42750},
  "markup": {"file_id": "…", "file_name": "Antminer_S19.markup.csv", "size": 700000,
             "import_date": "…", "checksum": "sha256:…", "records": 42750, "chunks": 42750},
  "loads":  [{"load_id": "Antminer S19", "phases": ["Ph_С"],
              "categories": ["Номинальная нагрузка"]}],
  "dataset_ids": ["06b5d3f3-…"],
  "created_at": "…", "updated_at": "…"
}
```

`status` ∈ `complete | missing_markup | missing_raw | duplicate | unpaired`.

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/subdatasets/` | список: фильтры `name`, `status`, `import_date`, `dataset_id`, `has_markup`, `limit`/`offset`, `sort`; конверт `{items, total, limit, offset}` |
| `GET` | `/api/subdatasets/{id}` | карточка (состав выше) |
| `POST` | `/api/subdatasets/` | собрать пару (`raw_file_id`, `markup_file_id`) — идемпотентно; а также автоматически при загрузке файлов |
| `PUT` | `/api/subdatasets/{id}` | заменить markup / переименовать (новая версия пары) |
| `DELETE` | `/api/subdatasets/{id}` | удалить пару (опционально `?with_files=true`) |
| `GET` | `/api/subdatasets/{id}/loads` | нагрузки разметки (вместо клиентского парсинга) |
| `GET` | `/api/subdatasets/{id}/stats` | `records`, `chunks`, `loads`, `phases[]`, `categories[]` |
| `GET` | `/api/subdatasets/{id}/download` | zip пары (собирается на сервере; с поддержкой `Range`) |

**Вариант B (минимальный, без новой сущности).** Добавить в `FileMetadataResponse`:
`base_name`, `pair_role` (`raw` | `markup`), `subdataset_id`, `paired_file_id`, `records`,
`chunks`, `checksum`, `dataset_ids`, `updated_at`; в `GET /api/data/files` — `limit`/`offset`/`sort`
и `group_by=subdataset`. Этого достаточно, чтобы UI перестал склеивать пары эвристикой.

**Вариант C (компромисс).** `/api/subdatasets/` только на чтение (сервер формирует пары
при загрузке), без CRUD.

**Правила формирования (для любого варианта):** пара создаётся автоматически при загрузке
(сначала по имени файла, затем по времени импорта); повторная загрузка создаёт **новую версию**
пары, а не «третий файл» (сейчас 265 файлов на 147 имён); неполные пары видны как
`missing_markup`/`missing_raw`; дубликаты (совпадающий `checksum`) помечаются.

### 3.2 Связь «датасет ↔ файлы/субдатасеты» и статистика

Сейчас `DatasetFillRequest` принимает `raw_file_ids`/`markup_file_ids`, а `DatasetResponse` =
`{id, creation_date, name, description, type}` — то есть **записать состав можно, прочитать
нельзя** (и пары снова угадывает клиент).

1. `DatasetResponse`: добавить `subdataset_ids` (или `statistics: {subdatasets, raw, markup,
   records, chunks, loads}`), `updated_at`, `status` (`new` | `filling` | `ready` | `failed`,
   производный от задачи `fill`), `task_id`.
2. Новые чтения: `GET /api/datasets/{id}/subdatasets`, `GET /api/datasets/{id}/files`,
   `GET /api/datasets/{id}/loads`, `GET /api/datasets/{id}/records` (постранично);
   обратные — `GET /api/data/files?dataset_id=…`, `GET /api/subdatasets/?dataset_id=…`.
3. `POST /api/datasets/fill/{dataset_id}` — принимать `subdataset_ids` (сейчас только файлы:
   клиент обязан сам собрать пары) и возвращать `{task_id, status, dataset_id, message}`
   (как `ModelCheckResponse`).
4. `GET /api/datasets/{id}/tasks` — связь датасета с задачами (BR-F3).
5. `GET /api/data/files/summary` (или `POST`) — агрегаты по типам, парам, «требуют внимания»,
   чтобы UI не выгружал весь реестр ради KPI.

### 3.3 Модуль `Loads`: фазы, справочники, симметрия CRUD

1. Вернуть `phase_connection` в элемент `GET /api/loads/list` (или сделать фазы отдельной
   сущностью с `GET /api/loads/{load_id}/phases`).
2. **Починить `ph_n`** либо убрать его из спецификации: сейчас параметр не влияет на результат
   (в реестре фазы не заполняются).
3. Справочники: `GET /api/loads/phases`, `GET /api/loads/categories` + нормализация регистра
   категорий, запрет дублей вида «малая нагрузка» / «Малая нагрузка».
4. `GET /api/loads/{load_id}` — детализация; `DELETE /api/loads/{load_id}` — удаление либо
   `409 Conflict`, если нагрузка используется в разметке/датасетах/моделях.
5. `updated_at` у нагрузок (BR-R2: изменяемая сущность).
6. Устранить расхождение терминологии **`device_id` ↔ `load_id`**: либо добавить `device_id`(ы)
   в нагрузку, либо перейти на `load_id` в `ModelCreateRequest.signals` / `InferenceClass.device_ids`.
   Сейчас модель ссылается на устройства, которых в реестре нет.
7. `GET /api/loads/{load_id}/subdatasets` и `/datasets` — обратная навигация «где нагрузка
   встречается».
8. Для разметки: нагрузки/фазы/категории отдавать эндпоинтом `GET /api/subdatasets/{id}/loads`
   (см. 3.1) — тогда UI не парсит markup и не «угадывает» набор.

### 3.4 Файлы: скачивание, загрузка, контракт разметки

1. **Скачивание:** объявить `application/octet-stream` (+ реальный MIME), добавить
   `Content-Length`, `Accept-Ranges: bytes` и поддержку `Range` (докачка/частичная выдача),
   `HEAD`, `ETag`; имя в заголовке — по RFC 5987 (`filename*=UTF-8''…`), то есть **исправить
   дефект с не-ASCII именами** (сейчас `404 latin-1 codec`). Для очень больших файлов —
   presigned S3 URL.
2. **Пакетные операции:** `POST /api/data/files/delete` (`{file_ids}` или `{subdataset_id}`),
   `POST /api/subdatasets/{id}/download` (zip на сервере): сейчас UI удаляет пару по одному
   файлу и собирает zip в памяти.
3. **Загрузка:** валидировать по расширению/содержимому, а не по MIME части запроса (сейчас
   обязателен `text/csv`, а `application/octet-stream` отвергается с `400 Only CSV files are
   allowed`); ошибки отдавать структурированно
   (`{"detail": {"code": "missing_columns", "message": "…", "columns": [...]}}`), а не строкой;
   поддержать `Idempotency-Key` и дедупликацию по `checksum`.
4. **Метаданные файла:** вернуть `description` (загрузка его принимает, ответ — нет), добавить
   `checksum`, `uploaded_at`/`updated_at`, `uploaded_by`, `records`, `chunks`, `subdataset_id`,
   `dataset_ids`.
5. **`file_type`:** сделать `enum` и добавить справочник `GET /api/data/file_types` со всеми
   фактическими значениями (`RAW`, `LOADS`, `ONNX`, `H5`, `REPORT_ZIP`) и описаниями.
6. **Контракт разметки:** описать формат файла (колонки `markupId;chunkID;LoadID;Ph_n;Category`,
   разделитель `;`, UTF-8, допустимые `Ph_n`) и добавить эндпоинт валидации/разбора
   (`POST /api/data/file/markup/validate` или `GET /api/subdatasets/{id}/loads`), который
   сообщает в том числе «`LoadID` отсутствует в реестре нагрузок» — это сейчас UI делает сам
   и показывает оператору как предупреждение.

### 3.5 Единые конвенции (пагинация, агрегаты, ошибки, версия)

1. **Пагинация — одна на весь API:** параметры `limit` (с ограничениями, как в `/api/tasks/`:
   1…1000, default 100) и `offset` (≥ 0) во **всех** списках (файлы, датасеты, модели, нагрузки,
   субдатасеты) + `sort`/`order`; конверт `{items, total, limit, offset}`
   (`total` вместо `count` и `result_size`).
2. **Агрегаты:** эндпоинты `…/summary` (файлы, нагрузки, субдатасеты) — KPI без выгрузки реестра.
3. **Ошибки — один формат** (например, RFC 9457 Problem Details: `type`, `title`, `status`,
   `detail`, `instance`) либо, как минимум, `{"detail": {"code", "message", "context"}}`;
   документировать `400`, `404`, `409`, `413`, `422`, `500`. Для `422` сохранить
   `HTTPValidationError` (FastAPI/Pydantic).
4. **`servers` в спецификации** — хотя бы один URL (сейчас контракт «висит в воздухе»);
   при нескольких контурах — `x-environments`.
5. **`securitySchemes`** — задекларировать (хотя бы placeholder), чтобы UI подготовил авторизацию
   (NFR-7).
6. **Описания и примеры:** у `GET /api/loads/list` ни один параметр не имеет `description`;
   добавить описания, `examples`, `default`, `minimum`/`maximum` (ограничения `limit`/`offset`).
7. **Версионирование:** схема ответа `GET /version`, заголовок `X-Api-Version`, политика обратной
   совместимости и changelog; `info.version` в спеке (сейчас `0.1.0`).

### 3.6 Асинхронные операции и задачи

1. **Единый ответ запуска** для `fill`/`train`/`check`/`inference`:
   `{task_id, status, entity_id, message}` — сейчас `fill` отдаёт `202 {}`, а остальные —
   полноценные схемы с `task_id`.
2. **Ссылки на сущности в задаче:** `dataset_id`, `model_id`, `subdataset_ids`/`file_ids`
   в `CeleryTask.parameters` (сейчас только человекопонятное имя `fill_dataset_<uuid>_<hash>`).
3. **Прогресс:** документировать `runtimes[].intermediate_result` (доля выполнения, текущий шаг,
   ETA) — UI нужен индикатор для длительных операций.
4. **Команды:** уточнить семантику `pause`/`resume`/`interrupt` для состояний `new`/`pausing`/
   терминальных (BR-R3: идемпотентность + `409`).
5. `GET /api/datasets/{id}/tasks`, `GET /api/ml_models/models/{id}/tasks` — история прогонов
   по сущности.

## 5. Классификация требований к API по итогам уточнений заказчика (15.09.2026)

Уточнено: в текущей версии сервера **понятия «субдатасет» нет**, и в разрабатываемом UI
оно не вводится. Различаются:
* **запись** — пара файлов RAW + markup, поставляемых вместе (единица работы оператора);
* **дубль** — файл с тем же именем, что уже есть в хранилище (различается `id`, `size`,
  `import_date`, `s3_path`);
* **субдатасет** — группа записей, объединённых признаком (дата измерений, назначение);
  это понятие относится к перспективе.

В связи с этим требования к API разделены на три независимых блока.

### 5.1. Актуально сейчас (требование к UI, не к API)

**Прозрачность объединения RAW и markup в записи** при наличии дублей с одинаковыми
наименованиями: явное правило сопоставления и «уверенность» рядом со значением, показ
**всех** кандидатов пары (`id`/`size`/`import_date`/`s3_path`), ручная перепривязка
оператором, отдельные разделы для несопоставленных файлов, выгрузка **манифеста
объединения** (CSV/JSON) и включение его в отчёт об испытаниях.
Реализуется в пульте испытаний (этап T1), проверки — `TC-REC-01…TC-REC-06`.

**Реализовано (T1, 15.09.2026)** — экран «🧩 Записи (RAW + markup)»:
объединение по правилу «имя + время импорта» (окно подтверждения 1 ч), карточки записей
с кандидатами разметки, вкладки «Дубли» / «Несопоставленные» / «Прочие файлы» /
«Манифест», ручные решения оператора (`records_overrides.json`: привязка, снятие,
исключение, актуальная версия) с аудитом, разбор разметки (записи/чанки — клиентская
оценка), манифест с автоматическим контролем полноты (каждый файл реестра попадает в
манифест ровно один раз), сохранение выгрузок в артефакты сессии.

Фактические показатели реестра на 15.09.2026 (живой сервис, `tools/probe_records.py`):

| Показатель | Значение |
|---|---|
| Файлов в реестре | 265 (129 RAW + 129 markup + 7 прочих) |
| Записей (RAW + markup) | 129, из них с разметкой 129 (100 %) |
| Записей-дублей | 128 в 61 базе имени (у одной базы 3 версии); версии различаются размером (например, `Antminer_S19`: 2 107 657 231 Б и 110 929 639 Б) |
| Не-ASCII имена | 108 из 129 записей → до исправления дефекта `latin-1` не скачиваются (разбор разметки — «блокировано API») |
| Объём | RAW ≈ 39 ГБ, markup ≈ 160 МБ |

Практический вывод: объединение в записи требуется не «на будущее», а **сейчас** —
без него оператор не может отличить актуальную версию от повторной загрузки, а
отсутствие `checksum`/`updated_at` делает различение версий полностью клиентской задачей.
