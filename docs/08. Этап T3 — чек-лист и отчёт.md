# Этап T3 — чек-лист проверок и отчёт об испытаниях

**Этап выполнен.** Ниже — что сделано, что проверено на живом стенде и какие
решения приняты. Состав этапа — по плану `llm_tasks/08. Итоговый состав этапа T3`
(после уточнения: боевые проверки `TC-FILE-11/12/13` автоматизируются с самоочисткой).

## 1. Что реализовано

**1. Каталог проверок — 41 проверка** (`acceptance/checks/catalog.py`)

| Группа | Проверок | Классы |
|---|---|---|
| `TC-SYS` — модуль «Система» | 6 | tech 5 + manual 1 (`TC-SYS-06`) |
| `TC-FILE` — «File Import» | 14 | tech 11 + live 3 (`TC-FILE-11/12/13`) |
| `TC-REC` — записи (RAW + markup) | 6 | tech 5 + manual 1 (`TC-REC-03`) |
| `TC-LOAD` — модуль «Loads» | 7 | tech 7 |
| `TC-TASK` — «Task service» (T4) | 8 | tech/live/manual |

Каталог по-прежнему **сверяется с таблицами `docs/02` тестом** (id, название,
требования, класс, эндпоинты: `tests/unit/test_checks_catalog.py`). В `CheckSpec`
добавлено поле `probe_paths` — маршруты негативных проб, которых **нет** в реестре
операций именно потому, что проверка подтверждает их отсутствие
(`GET /api/__test_unknown__`, `DELETE /api/loads/{load_id}`).

Расхождение с §14 `docs/02` (там для `TC-FILE` указано «tech 10 / live 4»): в таблице
§5 проверка `TC-FILE-14` (удаление несуществующего файла) описана как `tech`, поэтому
каталог следует таблице — `TC-FILE`: tech 11 / live 3.

**2. Движок проверок** (`acceptance/checks/engine.py`)

* `attach_artifact` — выгрузка файла как доказательства проверки (артефакт сессии +
  имя файла в `evidence["artifacts"]`);
* `ensure_defect_note` — **автоматическое** замечание к API по статусу
  «блокировано API» (дедупликация по заголовку, приоритет из реестра дефектов);
* `checklist_rows` / `group_stats` / `overall_stats` — единая логика выборки
  чек-листа для экрана, выгрузок и отчёта (фильтры: группа, статус, класс, поиск,
  «только невыполненные»);
* `run_checks(..., only_tech=True)` — групповой прогон безопасных проверок из экрана.

**3. Сценарии автоматических проверок** — `runner.py` и четыре домена

| Модуль | Сценарии |
|---|---|
| `checks/runner.py` | `AutomationContext` (сессия, API, монитор, журнал, параметры, `RawProbe`), `CheckOutcome`, `PreconditionError`, `evaluate`/`automate`, `scenario`, ленивый реестр `automations()` |
| `checks/system.py` | `TC-SYS-01…05`: доступность, версия и её состав, неизвестный путь, неизвестная задача, единый формат ошибок |
| `checks/files.py` | `TC-FILE-01…14`: реестр и фильтры (`file_name`, `file_type`, `import_date`), пагинация, объём, дубли, скачивание (ASCII, заголовки, не-ASCII), а также `live`: негативные загрузки, **круговой рейс** `upload → download → sha256 → delete`, удаление несуществующего файла |
| `checks/records.py` | `TC-REC-01/02/04/05/06`: объединение RAW+markup, дубли и полнота манифеста, несопоставленные файлы, разбор разметки (записи/чанки), сравнение версий одной записи |
| `checks/loads.py` | `TC-LOAD-01…07`: реестр и срез `limit`/`offset`, состав полей, фильтры `ph_n` и точные `load_id`/`category`, поиск по описанию, качество справочника категорий, отсутствие удаления нагрузки |

`checks/tasks.py` (T4) после рефакторинга **реэкспортирует** `automate`/`evaluate`/
`scenario`/`AutomationContext`, поэтому `ui/common/check_run.py` и прежние тесты
работают без изменений.

**4. Экран «✅ Чек-лист проверок»** (`acceptance/ui/pages/checks.py`, переписан)

* KPI: «Проверок в каталоге» (`41 / 69`), «В выборке», «Выполнено», «Успех»,
  «Отказ», «Блокировано API», «Не выполнено» + прогресс готовности выборки;
  счётчики считаются **по видимым строкам**, то есть по всем активным фильтрам
  (раньше они зависели только от группы, и при фильтре по классу или поиску KPI
  расходился с таблицей);
* фильтры: группа (все наполненные группы + «Все группы»), статус, класс, поиск по
  id/названию/требованиям, «только невыполненные»;
* таблица (id, группа, проверка, требования, класс, статус, вердикт, диапазон
  журнала, время) и карточка проверки: шаги, ожидаемый результат, эндпоинты,
  `probe_paths`, статус, доказательства, запуск сценария с пикерами цели
  (`task_id`/`file_id`/`load_id`), ручные отметки, замечание к API;
* действия: групповой прогон `tech`, выгрузка CSV, сохранение чек-листа в артефакты
  сессии (CSV + Markdown);
* при статусе «блокировано API» движок сам создаёт замечание к API
  (`ensure_defect_note`).

**5. Отчёт об испытаниях** (`acceptance/report.py`, новый; экран `ui/pages/report.py`)

Комплект: `report_<сессия>.md` (11 разделов), `report_<сессия>.json`
(машиночитаемая копия) и приложения `checks.csv`, `notes.csv`, `test_entities.csv`,
`journal.jsonl`, файлы манифеста записей (`records_manifest_*`), выгруженные экраном
«Записи». Разделы: сессия, программа и объём, снимки стенда и их сравнение, сводка,
детализация по группам (вердикт, журнал, доказательства), наблюдение за задачами
(история FSM-1), артефакты и `__TEST__`-сущности, замечания к API по приоритетам,
перспективные требования, итог и подписи, приложения.

Отчёт строится **только по данным сессии и структурного журнала**: ни одного запроса
к испытуемому серверу при формировании (проверяется тестом с подменённым
`httpx.Client.send`). Готовность («чего не хватает»: не заполнено ядро, нет снимков,
есть невыполненные/отказные проверки, «блокировано API» без замечания, не удалены
`__TEST__`-сущности, нет итогового решения) видна и на экране, и в отчёте.

**6. Учёт `__TEST__`-сущностей** (`acceptance/session.py`, схема **v4 без миграции**)

`counters["test_entities"]` + `add_test_entity` / `test_entities` /
`mark_test_entity_deleted` / `pending_test_entities`; каждая запись — это `id`, тип,
действие (`создан`/`удалён`), время, `check_id`, примечание. События
`test_entity_created` / `test_entity_deleted` пишутся в историю сессии (вход для
`TC-CLEAN-01/02` в T9). Боевые проверки обязаны использовать имена `__TEST__…`
(проверяется до запроса) и удалять созданное в самом сценарии.

**7. Журнал и состояние**

* экран «Журнал»: пикер метки проверки (метки берутся из журнала) + фильтр по задаче
  (`task_id` из пути запроса) и прежние фильтры (ошибки, подстрока, лимит строк);
* `state.load_loads()` / `refresh_loads()` — кэш реестра нагрузок с TTL (для пикера
  `load_id`);
* метки проверок `TC-…` остаются в каждой записи журнала, поэтому карточка проверки
  показывает диапазон `journal_from…journal_to`.

**8. Реестр известных дефектов** (`acceptance/notes.py`)

`DEFECT_BY_CHECK` + `defect_for(check_id)` + `note_from_check(check_id, evidence=…)`:
замечание к API собирается по идентификатору проверки, поэтому движок создаёт его
автоматически, а оператор видит готовый текст с фактом и ожиданием.

## 3. Живой прогон чек-листа (стенд dev@58ac72f, 17.09.2026)

Технические проверки T3 на живом стенде дают вердикты (запуск — через
`checks_engine.run_checks`, тот же путь, что и кнопка «Выполнить безопасные проверки»):

* **успех** — `TC-SYS-01/02/04/05`, `TC-FILE-01…09/14`, `TC-REC-01/02/04/05/06`,
  `TC-LOAD-01/04/05/06`;
* **блокировано API** — `TC-FILE-10` (скачивание не-ASCII имени: `404 latin-1`),
  `TC-LOAD-02` (в элементе реестра нет `phase_connection`), `TC-LOAD-03`
  (`ph_n` не влияет на выдачу). К этим статусам движок создаёт замечания
  автоматически (`ensure_defect_note`);
* **отказ** — `TC-SYS-03`: неизвестный путь `/api/__test_unknown__` отвечает
  **405** вместо **404** (ожидание `docs/02` — 404 с разобранным `detail`). Причина
  видна по журналу: маршрут `DELETE /api/{file_id}` в корне `/api/` перехватывает
  произвольный путь, поэтому сервер сообщает «метод не разрешён» — это живое
  подтверждение замечания «DELETE /api/{file_id} расположен в корне /api/ (риск
  коллизий)». Отказ — результат испытаний, а не дефект пульта; замечание к API
  оператор оформляет из карточки проверки.

`TC-REC-05` (разбор разметки: записи и чанки) занимает ≈10 с — скачивание и разбор
нескольких markup-файлов; характеристики сохраняются в сессии как **клиентская**
оценка (серверных агрегатов в API нет).

## 5. Известные ограничения

* `TC-SYS-03` на текущей сборке — «отказ» из-за 405 вместо 404; пока сервер не
  поправит обработку неизвестного пути, проверка остаётся красной (так и задумано —
  программа испытаний зафиксировала расхождение).
* `TC-LOAD-07` (негативная проба `DELETE /api/loads/{load_id}`) не включается в
  автоматический прогон из `tests/integration/test_live_write.py`: проба выбирает
  нагрузку и подтверждает **отсутствие** маршрута — на стенде с реализованным
  удалением она бы удалила нагрузку. Оператор запускает её осознанно (в карточке
  видно, что маршрут негативный).
* Ручные проверки (`TC-SYS-06`, `TC-REC-03`, `TC-TASK-08`) автоматического сценария не
  имеют: их отмечает оператор заключением в карточке проверки.
* Ресурсоёмкие группы (`TC-DS`, `TC-MOD`, `TC-TR`, `TC-INF`, `TC-CLEAN`) — этапы
  T5–T10; каталог для них уже описан (69 проверок в программе, 41 реализована).
* Отчёт — каркас комплекта T3: сравнение сессий, финализация с подписями и
  приложения артефактов — этап T9 (в отчёте есть раздел «Итог и подписи» с полем
  решения сессии и предупреждениями о полноте).
