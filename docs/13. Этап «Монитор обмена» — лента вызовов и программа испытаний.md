## 2. Что сделано по частям

### 2.1. Прозрачность вызовов (п. 1)

* `acceptance/http_log.py`: запись журнала `HttpExchange` хранит **заголовки запроса и ответа**
  (`request_headers`/`response_headers`, до 40 пар), они попадают и в JSONL, и в `as_dict()`;
  заголовки запроса дублируются в событие `http_request`.
* `acceptance/exchange.py`: единая сборка команды `curl` (`curl_command`, `exchange_curl`) —
  запрос без тела, JSON-тело и multipart (placeholder файла).
* `acceptance/ui/common/exchange_monitor.py`: компонент лента — уровни `кратко`/`сводка`/
  `заголовки`/`тело`/`полностью`, фильтры (ошибки, метка, лимит), порядок, бейдж результата,
  действия: `curl`, повтор с правками, замечание к API, переход в консоль.
* `acceptance/ui/pages/monitor.py`, регистрация экрана в `acceptance/app.py`.

### 2.2. Контроль исполнения и программа испытаний (пп. 2–3)

* `acceptance/plan.py`: модель `PlanItem`/`PlanState`, построение плана из каталога
  (`build_plan`), правила галочек (`set_enabled`), поиск следующего пункта (`next_item`),
  ожидания и вердикты (`expected_statuses`, `judge_call`), хранение в сессии
  (`load_plan`/`save_plan`), оценки для ленты (`verdicts_for_feed`).
* `acceptance/plan_runner.py`: исполнение пункта (`execute_item`) в двух режимах —
  «проверка целиком» (движок чек-листа, вызовы закрываются по фактическим обменам журнала) и
  «по вызовам» (ровно один запрос по шаблону пункта); правила подтверждения
  (`item_needs_confirmation`).
* `acceptance/ui/common/plan_panel.py`: панель «Программа испытаний» — KPI, режим, пауза,
  кнопки контроля, авто-прогон фрагментом Streamlit с тиком 1 с и паузой оператора, фильтры,
  массовые галочки, дерево пунктов, параметры вызова + `curl`, одиночный запуск пункта.
* `acceptance/session.py`: **схема v6** — поле `plan` (пункты, режим, пауза, указатель,
  статусы, вердикты, диапазоны журнала).
* `acceptance/report.py`: **REPORT_VERSION = 2**, раздел «12. Программа испытаний (план
  вызовов)», приложение `plan.csv`, предупреждения готовности (невыполненные включённые
  пункты, снятые галочками проверки, пункты с отказом).

### 2.3. Терминология (п. 4)

* `acceptance/glossary.py` — единый источник терминов: сущности стенда с префиксом `$`
  (`$Задача`, `$Файл`, `$Датасет`, `$Модель`, `$Нагрузка`), внутренние сущности пульта без
  префикса, разведение «карточки», «программы» и «монитора», подписи экранов.
* руководство `docs/12` §1.4 — соглашение и таблица терминов; подписи экранов
  («⏱️ `$Задачи`», «🗂️ `$Датасеты`») и навигация берутся из глоссария.

### 2.4. Предпросмотр `__TEST__`-данных (п. 5)

* `acceptance/test_payloads.py` — правила из каталога (`post /api/data/file`,
  `post /api/datasets/`, `post /api/datasets/fill/{id}`) и константы тел из
  `acceptance/checks/files.py`: имя файла, содержимое CSV, тип датасета, тело наполнения,
  признак «убирает за собой».
* блок «📤 Что будет отправлено» в карточке проверки (`checks.py`) и в параметрах пункта
  плана (`plan_panel.py`).

### 2.5. Журналы по запускам и руководство

* `acceptance/paths.py` + `logging_setup.py`: текстовый журнал — **свой файл на каждый запуск**
  (`logs/applog/applog_<ГГГГММДД-ЧЧММСС>.log`), `list_app_logs`; экран «Журнал» показывает
  хвост текущего запуска и выбор прошлых.
* руководство `docs/12`: §27 (монитор и программа испытаний), §1.4 (терминология), §26.x
  (карта кода, схема v6, `plan.csv`), исправлены §15.5 и §25.2 (дефект Loads закрыт
  контрактом 17.09.2026).
* стоп-тесты документации: `tests/unit/test_user_guide_doc.py`, `tests/unit/test_glossary.py`.

## 4. Найденные и исправленные дефекты (внутри этапа)

| Дефект | Как проявлялся | Решение |
|---|---|---|
| «Пинг-понг» галочек плана | Сравнение значения виджета с моделью в теле рендера давало бесконечную перерисовку: снятие галочки проверки и виджет её вызова «перетягивали» друг друга | Галочки переведены на колбэки (`on_change`) + синхронизация значений виджетов (`sync_checkbox`); поймано смоук-тестом AppTest |
| Ошибка API считалась «вызов не выполнен» | `execute_request` заполняет `error` и для ответов 4xx/5xx, из-за чего вердикт был неверным | `judge_call` судит по статусу ответа; `error` используется только когда ответа нет |
| Пропуск пункта без пояснения | Ранние выходы исполнителя заполняли только вердикт, а панель показывала пустой текст | Единый помощник `_stop` (вердикт = пояснение = причина) |

## 5. Ограничения и следующий шаг

* Авто-прогон не отправляет проверки классов `live`/`heavy`: они требуют карточки запуска на
  экране «Чек-лист» (FR-T10, NFR-T4) — панель останавливается и подсказывает, что заполнить.
* Multipart-вызовы повторяются только в консоли (содержимое файла в журнал не пишется —
  фиксируется имя, размер и поля формы).
* Негативные пробы (`probe_paths`) выполняются сценарием проверки; в режиме «по вызовам» они
  помечаются «пропущено», чтобы не дублировать пробу.
* Дальше: группы T6–T11 каталога (модели, обучение, инференс, AutoML) и передача комплекта
  испытаний (T10) — план и лента для них уже готовы.
