### Что меняется в порядке и почему

| Было                             | Стало                                                        | Следствие                                                    |

## Этап T4 — детальный план (делаем первым)

**1. Данные и схема сессии v4** (`acceptance/session.py`)
* новое поле `tasks[]`: `task_id`, `type`, `name`, `origin` (пульт/внешняя), привязка к проверке (`check_id`), `status`, `first_seen`/`last_seen`, `history[]` переходов FSM-1, настройки поллинга (интервал, активен, последний опрос), ссылка на номер записи журнала;
* `add_task` / `update_task` / `task_history` + событие `task_observed`; чтение сессий v1–v3 без правок (как сейчас).

**2. Каталог проверок — первый срез** (`acceptance/checks/catalog.py`)
* 8 `CheckSpec` группы `TC-TASK` из `docs/02` (id, название, модуль «Task service», трассировка UC-26…UC-28/FR-8/FSM-1/BR-R3/BR-R7/BR-R5, класс `tech`/`live`/`manual`, шаги, ожидаемый результат, эндпоинты);
* структура каталога сразу рассчитана на 10 групп (добавление в T3 и далее — без переделки);
* тест сверки каталога с таблицей чек-листа (id, группа, класс) — по образцу `tests/unit/test_endpoints.py`.

**3. Движок проверок — минимальная версия** (`acceptance/checks/engine.py`)
* старт проверки под меткой `TC-TASK-NN` (`label_context`), фиксация `journal_from`/`journal_to`, параметров, времени и длительности;
* вердикт и статус (`успех` / `отказ` / `блокировано API` / `пропущена` / `выполнена вручную` / `прервана`), заключение оператора, доказательства; подтверждение для `live`/`heavy`; запись в `session.checks` (поле уже есть в схеме v3).

**4. Монитор задач — движок** (`acceptance/tasks_monitor.py`)
* `TaskMonitor`: регистрация задачи (из ответа `train`/`check`/`inference`/`fill`-поиска, из `console_calls`, из списка задач, вручную для внешней), поллинг `GET /api/tasks/{task_id}` через `lib.polling.poll_until` + `client.tasks.TasksApi`, интервал настраивается, пауза/возобновление/снятие с наблюдения;
* определение переходов FSM-1 (`lib/task_status.get_status_presentation`, `is_terminal`, `available_actions`), события журнала по каждому изменению статуса, остановка на терминальном статусе, обработка обрыва связи и перезапуска пульта (BR-R5, BR-R6) — возобновление по сохранённому `task_id` из сессии.

**5. Экран «⏱️ Задачи»** (`acceptance/ui/pages/tasks.py` + пункт меню в `app.py`, группа «Испытания»)
* **KPI:** наблюдаемых, активных, завершённых, прерванных/с ошибкой, внешних;
* **«Список задач» (сервер):** фильтры `task_type` и `status` (перечисления из спецификации), `start_date`/`end_date`, лимит/смещение (по умолчанию `limit=100`), таблица, кнопки «наблюдать» / «открыть карточку»;
* **«Наблюдение»:** таблица отслеживаемых задач (пульт/внешняя, статус, прошедшее время, `intermediate_result`), кнопки «обновить», «пауза поллинга», «снять с наблюдения»;
* **Карточка задачи:** `TaskWithRuntimes` + `runtimes[]` (`status`, `start_time`/`end_time`, `result`, `intermediate_result`, `celery_task_id`), история переходов из сессии, действия **строго по `available_actions`** (`pause` из `running`; `resume` из `paused`; `interrupt` из `running`/`pausing`/`paused`) с предупреждением о no-op/409 (TC-TASK-06);
* **Диагностика:** «запустить `celery-test`» (`POST /api/tasks/test?duration=N`, класс `write` → подтверждение), авто-наблюдение созданной задачи;
* **Внешняя задача:** ручной ввод `task_id` (TC-TASK-08) с пометкой «внешняя»;
* **Действия:** «прикрепить к проверке» (`TC-…`), «создать замечание к API», «сохранить карточку в артефакты», переход «открыть в консоли»/«показать обмены в журнале».

**6. Экран «✅ Чек-лист проверок» — минимальная версия** (`checks.py`)
* список группы `TC-TASK` с KPI и статусами, карточка проверки (шаги, ожидание/факт, вердикт, заключение, доказательства, диапазон журнала), запуск/подтверждение/пропуск/«блокировано API»; расширение до 10 групп — в T3.

**7. Консоль (помощники задач)** (`console.py`)
* выбор `task_id` из живого списка задач прямо в path-параметре (снимает «ручной копипаст»), кнопка «открыть в мониторе», автоматическая регистрация `task_id` из ответа (`_task_id_from_response` уже есть) — монитор подхватывает задачу, даже если она запущена из консоли (требование FR-T3 из ТЗ).

**8. Кэш и состояние** (`acceptance/ui/state.py`)
* кэш списка задач с TTL (по аналогии с `FILES_CACHE_TTL`), автоподхват задач из текущей сессии при входе на экран.

**9. Тесты**
* unit: монитор (переходы FSM, терминальность, поллинг на `httpx.MockTransport`, запись в сессию, миграция v3→v4), каталог `TC-TASK` (сверка с `docs/02`), страница «Задачи» (AppTest), помощник консоли;
* smoke: экран «Задачи» целиком (`AppTest`), запуск celery-test на моке;
* integration (живой стенд, чтение + `POST /api/tasks/test` малой длительности): список, карточка с `runtimes[]`, цепочка `pause → resume`, `interrupt`, `not_found`.

**10. Документы**
* `docs/06. Этап T4 — задачи и монитор.md` (состав работ, живые результаты, схема v4, тесты, дефекты API);
* `README.md`: этапы (T4 выполнен, T3 следующий, пометка зависимостей), схема сессии v4, число тестов;
* `docs/README.md`: строка нового документа;
* `docs/05. Сложность формирования запросов…`: после появления пикера `task_id` уровни операций `pause`/`resume`/`interrupt`/`GET /api/tasks/{id}` пересматриваются (S2 → S1) + тест документа обновляется вместе с таблицей.

**DoD этапа T4:** `TC-TASK-01…08` выполняются из пульта; монитор доводит реальную `celery-test`-задачу до терминального статуса, показывает историю FSM-1 и допускает `pause → resume`/`interrupt`; внешняя задача наблюдается по `task_id`; вызовы консоли с `task_id` подхватываются; `pytest`/`ruff`/`mypy`/`gen_endpoints --check` — зелёные.

* **T8** — экран «🔮 Инференс»: async по датасету и генератор base64-сэмпла из RAW (снимает второй S4).

* **T10** — приёмка, свод замечаний, завершение §14 чек-листа (`TC-TR`/`TC-INF`/`TC-CLEAN` + итог 69), инструкция оператора, комплект передачи.
