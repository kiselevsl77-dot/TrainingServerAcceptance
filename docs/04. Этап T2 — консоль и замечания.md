## 2. Реестр эндпоинтов: спецификация — единственный источник

Ручной список эндпоинтов неизбежно расходится со спецификацией, поэтому реестр
**генерируется** из `docs/SOM1.json`:

```powershell
python -m tools.gen_endpoints           # пересобрать блок ENDPOINTS + ruff format
python -m tools.gen_endpoints --check   # проверка актуальности (exit 1, если устарел)
python -m tools.gen_endpoints --report  # разбор: модуль, метод, путь, класс, параметры
```

1. генератор читает пути, параметры (с `required`, `enum`, `default`), тела запросов
   и ответы, разыменовывая `$ref`;
2. для каждого эндпоинта строится готовая **заготовка JSON-тела** (обязательные поля
   и поля со значениями по умолчанию) — кнопка «Вставить заготовку» в консоли;
3. расхождения спецификации с фактическим сервером фиксируются в одном месте
   (`RESPONSE_OVERRIDES`: скачивания отдаются файлом, а не JSON) и в примечаниях операций;
4. тест `tests/unit/test_endpoints.py::test_registry_matches_specification` сверяет
   реестр со спецификацией **по значениям** (устойчиво к форматированию), поэтому
   забыть пересобрать реестр нельзя.

Классы безопасности назначены правилами, а не «на глаз»: `DELETE` → `destructive`;
`POST/PUT/PATCH` → `write`; ресурсоёмкие (`fill`, `train`, `check`, async-инференс) →
`heavy`; исключения объявлены явно (`POST /api/tasks/test` → `write`;
`inference/single` → `read` — синхронное вычисление без изменения данных стенда).

## 3. Движок вызова: результат вместо исключения (NFR-T3)

`client.http.ApiHttpClient` возвращает только тело ответа, а консоли нужны статус,
заголовки, длительность, размер и сырое тело — поэтому консоль работает «сырым»
`httpx.Client`, но обёрнутым в **тот же** `LoggingTransport`:

1. **Никогда не бросает исключений.** Сеть/таймаут → `error_kind=network`, 404 →
   `not_found`, 422 → `validation`, прочие 4xx/5xx → `api`, некорректный URL →
   `request`. Оператор видит причину на экране, а отчёт получает результат испытаний.
2. **Подбор кодировки.** Тело читается как `utf-8`, затем `cp1251`, затем `latin-1`
   (дефект `latin-1` виден как текст, а не как ошибка декодирования); фактическая
   кодировка показывается в результате.
3. **Управление объёмом.** Текстовые тела обрезаются по `PULT_BODY_LIMIT` с пометкой
   в интерфейсе; бинарные ответы не удерживаются в памяти (размер и имя файла из
   `Content-Disposition`), содержимое скачивается повторно только по явной команде
   «Ответ в артефакты».
4. **Воспроизводимость.** Каждый вызов пишется в JSONL сессии (через транспорт) и в
   историю сессии (`console_calls`): метка проверки, операция, статус, длительность,
   тело запроса, номер записи журнала. Рядом с результатом выводится готовая
   команда `curl`.
5. **Метка проверки.** Все записи обмена помечаются `label_context(...)`, по умолчанию
   `TC-CONSOLE`; метка позволяет связать обмен с проверкой чек-листа и найти его
   на экране «Журнал».

## 4. Подтверждения: одинаковые правила на всех экранах (NFR-T4)

| Класс | Операции | Что требует пульт |
|---|---|---|
| 🟢 `read` | 22 операции (`/health`, `/version`, все GET, `inference/single`) | ничего; для скачивания файла содержимое не удерживается в памяти (размер и имя из реестра), а файл крупнее **50 МБ** скачивается только после подтверждения (то же правило, что на экране «Записи») |
| 🟠 `write` | создание файла/датасета/нагрузки/модели, `PUT`, управление задачами, `POST /api/tasks/test` | чекбокс подтверждения **+** префикс `__TEST__` у имён создаваемых сущностей: имена извлекаются из JSON-тела (`name`, `title`, `category` и др.) и multipart-файла, без префикса запуск заблокирован |
| 🔴 `destructive` | `DELETE /api/{file_id}`, `/api/datasets/{id}`, `/api/ml_models/models/{id}` | чекбокс **+** слово `DELETE`; если удаляемая сущность не помечена `__TEST__` (или её имя не удалось определить по реестру) — дополнительно повторный ввод полного `id` |
| 🟣 `heavy` | `fill`, `train`, `check`, async-инференс | карточка запуска: цель проверки, используемые данные, параметры, ответственный, ожидаемая длительность/ресурсы, судьба артефактов, комментарий **+** подтверждение расхода ресурсов; `task_id` из ответа сразу регистрируется в сессии как задача для монитора T4 |

Повтор вызова кнопкой «🔁 Повторить» разрешён только для читающих операций: изменяющие
и ресурсоёмкие требуют повторного прохождения подтверждений — обход правил невозможен.

Карточка запуска вынесена в `acceptance/ui/common/run_card.py` и будет использована
этапами T4 (монитор задач), T5 (датасеты) и T7 (обучение/проверка/ONNX) без изменений.

## 5. Экран «Консоль запросов»

1. **Выбор операции** — по модулям спецификации: `Система` (2), `File Import` (4),
   `Datasets` (6), `Loads` (4), `ML models` (9), `Task service` (7);
2. **карточка операции** — метод, путь, `operationId`, класс безопасности, вид тела и
   ответа, поля тела, известная особенность и требования перед запуском;
3. **параметры** — поля path-параметров по типам из спецификации, query-параметры
   (checkbox/select-по-перечислению/поле с значением по умолчанию) и «свободные»
   параметры строками `key=value` (нужно для `limit`/`offset`, которых нет в спецификации);
4. **тело** — редактор JSON с заготовкой из спецификации или выбор файла для multipart
   (имя файла, тип, описание, автоматический MIME по расширению, размер);
5. **результат** — статус, длительность, размер, номер записи журнала; ошибка класса
   (`network`/`not_found`/`validation`/`api`/`request`) с текстом `detail`; значимые
   заголовки (по кнопке — все); JSON или текстовое тело с усечением; признак файла
   для скачиваний;
6. **действия** — «💾 Ответ в артефакты» (тело ответа сохраняется в `artifacts/` и
   регистрируется в сессии), «📌 Приложить к проверке» (событие `console_attachment`
   с меткой и номером журнала), «✍ Создать замечание к API» (форма с предзаполненными
   фактом, воспроизведением и доказательствами), «🔁 Повторить», «🧹 Очистить»;
7. **вкладка «История вызовов»** — все вызовы сессии (`console_calls`) с деталями и
   обмены журнала по текущей метке; **вкладка «Операции API»** — полный реестр
   32 операций с классами безопасности и примечаниями.

## 6. Экран «Реестр замечаний к API»

1. **KPI**: всего замечаний, P0/P1/P2, из шаблонов (авто), ручных (оператор), с привязкой
   к проверкам;
2. **реестр**: фильтры по приоритету, модулю, источнику, привязке и поиск по тексту;
   таблица (`№`, приоритет, модуль, замечание, эндпоинт, проверка, источник, дата, `id`),
   карточка выбранного замечания с фактом/ожиданием/воспроизведением/доказательствами;
3. **правка формулировки** (`api_note_updated`) и **удаление** ошибочного замечания
   (`api_note_removed`) — только с подтверждением, оба действия пишутся в историю сессии;
4. **добавление**: из 11 шаблонов известных дефектов (с привязкой к проверке и
   доказательствами) или вручную (модуль, приоритет, эндпоинт, факт, ожидание,
   воспроизведение, доказательства, метка проверки);
5. **перспективные требования** (5 пунктов, в первую очередь субдатасеты) — отдельный
   раздел бэклога с возможностью превратить требование в замечание;
6. **выгрузка**: Markdown-раздел отчёта с группировкой P0/P1/P2, JSON (машинный формат
   с `meta`, `summary`, `notes`, `prospective_requirements`) и CSV (utf-8-sig, для Excel);
   комплект сохраняется в `artifacts/` и регистрируется в сессии.

Замечание создаётся **из любого места пульта**: кнопка шаблона в карточке записи,
форма в результате вызова консоли, форма на экране реестра. Дедупликация по заголовку
не даёт завести одно и то же замечание дважды; одинаковые тексты сообщений на всех
экранах (хелпер `api_notes`) исключают расхождения подсказок.

## 7. Сессия испытаний: схема v3

| Поле | Содержание |
|---|---|
| `console_calls[]` | метка проверки, операция, класс безопасности, метод, путь, статус, длительность, номер записи журнала, `task_id` созданной задачи (если вернулся), тело запроса, ошибка, примечание (карточка запуска и подтверждения) |

Дополнительно история сессии получает события `console_call` (вызов), `console_task_started`
(создана задача — её подхватывает монитор задач T4) и `console_attachment` (обмен приложен
к проверке). Сохранение сессии на диск штатное, поэтому ручные вызовы консоли доступны и
после перезапуска пульта; файлы схем v1/v2 читаются без правок (отсутствующие поля
заполняются значениями по умолчанию).

## 10. Замечания к API, подтверждённые на этапе T2

1. **Скачивания описаны в спецификации как JSON.** `GET /api/data/file/{id}/download`
   и `GET /api/ml_models/models/{id}/download_onnx` объявлены с `content:
   application/json` и пустой схемой, фактически отдаётся файл
   (`application/octet-stream` + `Content-Disposition`); в реестре эндпоинтов вид
   ответа переопределён явно (`RESPONSE_OVERRIDES`).
2. **`/health` возвращает неописанный состав.** Живой ответ —
   `{"status": "OK", "environment": "dev"}`; в спецификации схема ответа отсутствует
   (`{}`), поля `environment` нет, значение `status` в верхнем регистре.
3. **`limit`/`offset` отсутствуют в спецификации** у `GET /api/data/files` (заявлены
   только `id`, `file_name`, `import_date`, `file_type`), при этом сервер их молча
   игнорирует — в консоли такие параметры можно передать только «свободной» строкой.
4. **Не-ASCII-имена по-прежнему дают 404** при скачивании (дефект `latin-1`, P0) —
   подтверждено интеграционным тестом «404 — результат, а не исключение».
