## 2. Схема сессии v4: наблюдение за задачами

Асинхронная задача не может жить «в памяти экрана»: Streamlit перерисовывает страницу, а
пульт может перезапуститься между опросами. Поэтому наблюдение хранится **в сессии**
(`session.tasks`), а монитор каждый раз собирается заново из неё.

```json
{
  "task_id": "9f0a5b7e-0000-4000-8000-000000000001",
  "type": "celery-test",
  "name": "__TEST__probe",
  "origin": "пульт",
  "check_id": "TC-TASK-04",
  "status": "paused",
  "first_seen": "2026-09-16T10:00:00",
  "last_seen": "2026-09-16T10:00:07",
  "poll": {"interval": 2.0, "active": true, "last_poll": "2026-09-16T10:00:07", "polls": 4},
  "journal_from": 41,
  "journal_seq": 57,
  "intermediate_result": {"progress": 40},
  "runtimes": [{"status": "paused", "start_time": "...", "celery_task_id": "..."}],
  "note": "задача создана из консоли: post /api/tasks/test",
  "errors": [],
  "history": [
    {"at": "...", "previous": null, "status": "", "journal_seq": null,
     "note": "задача поставлена на наблюдение", "error": ""},
    {"at": "...", "previous": "", "status": "running", "journal_seq": 41, "note": "", "error": ""},
    {"at": "...", "previous": "running", "status": "paused", "journal_seq": 52, "note": "", "error": ""}
  ]
}
```

API схемы (`acceptance/session.py`): `add_task`, `update_task`, `find_task`, `task_history`,
`set_task_check`, `register_task_from_console`, `console_task_ids`, `tasks_summary`.
События истории сессии: `task_observed`, `task_status_changed`, `task_poll_error`,
`task_attached`, `task_unobserved`, `task_command`.

Ключевые правила:

1. **Одна запись на `task_id`** — повторная регистрация идемпотентна: задача из списка,
   из ответа API, из консоли или введённая вручную указывают на одну запись.
2. **Переходы FSM-1 фиксируются последовательно**: `history[]` хранит `previous → status`,
   номер записи журнала и примечание, поэтому цепочка проверяется по отчёту (TC-TASK-04/05).
3. **Ошибка опроса не теряет задачу** (BR-R5): наблюдение остаётся активным, ошибка
   дописывается в `errors[]`, а опрос повторяется на следующем шаге.
4. **Файлы v1–v3 читаются без правок**: отсутствующие поля заполняются значениями
   по умолчанию (`tasks=[]`), а `session_meta` получает `tasks_total`.

## 4. Движок проверок: воспроизводимость вместо «нажали и поверили»

`acceptance/checks/engine.py` решает три задачи:

1. **Метка проверки на всех запросах.** `check_label("TC-TASK-04")` открывает
   `label_context` (метка в журнале обмена) и `check_context` (поле `check_id` в JSONL
   сессии). Монитор уважает уже активную метку: сценарий проверки «окрашивает» свои опросы
   и команды в свой `TC-…`, а действия оператора — в проверку задачи или `TC-TASK`.
2. **Диапазон журнала.** `CheckRun` фиксирует `journal_from` (номер следующего обмена на
   момент старта) и `journal_to` (последний обмен проверки); результат проверки ссылается
   на этот диапазон, поэтому доказательства проверки отделяются от «фонового» журнала.
3. **Вердикт и требования к запуску.** `mark()` ставит статус без прогона (ручные отметки),
   `check_confirmation()` требует для классов `live`/`heavy` цель проверки, данные и
   ответственного (NFR-T4, FR-T10), а `record_result()` хранит **одну** запись на проверку
   (`session.checks`) и пишет событие `check_recorded`.

Статусы — из `acceptance/checks/registry.py`: `не выполнена`, `успех`, `отказ`,
`блокировано API`, `пропущена`, `выполнена вручную`, `прервана`.

## 5. Монитор задач (`acceptance/tasks_monitor.py`)

Монитор — «фундамент» всех асинхронных проверок: `dataset-fill` (T5), `training` и
`model-testing` (T7), `inference` (T8) наблюдают задачи так же, как `celery-test` в T4.

| Возможность | Реализация |
|---|---|
| Регистрация | `register` (задача), `register_task` (из списка), `register_external` (вне пульта), `register_from_response` (`tasks/test`, `train`, `check`, `inference`), `adopt_from_session` (задачи из вызовов консоли) |
| Опрос | `poll_once` (один опрос и запись перехода), `poll_all` (проход по наблюдению), `due` (задачи с истёкшим интервалом), `watch` (блокирующий цикл до терминального статуса) |
| FSM-1 | `available_actions_for`, `is_terminal_status`, `status_label`, `status_icon` — на данных `lib/task_status.py` (единые подписи и индикаторы пульта) |
| Команды | `run_command` — только по `available_actions`; осознанное исключение `force=True` (TC-TASK-06); эффект определяется повторным опросом: «переход» или «no-op», `409` пишется как вариант, а не как авария |
| Управление наблюдением | `set_active`, `set_interval`, `attach_to_check`, `unregister`, `kpi` |
| Доказательства | `card`, `card_snapshot`, `runtime_row` (прогоны `runtimes[]`), `last_intermediate`, `task_card` (проекция карточки для списка: статус, тип, название, времена прогона) |
| Статус для таблиц | `status_glyph`, `status_color`, `status_text`, `status_legend` — компактные пиктограммы (`▶`/`✔`/`✖`/`?`) и цвета из `lib.task_status.py`; `task_status_view` собирает статус строки списка из трёх источников с приоритетом «карточка → снимок → последний опрос» и помечает источник (`SOURCE_CARD`/`SOURCE_SNAPSHOT`/`SOURCE_POLL`/«нет данных») |

Особенности, закреплённые тестами:

* **статус берётся из последнего прогона** (`TaskWithRuntimes.runtimes[]`): отдельного поля
  `status` у задачи в спецификации нет;
* **`not_found` — результат, а не сбой** (BR-R7): сервер отвечает неизвестной задачей, и
  монитор различает «не найдена» (наблюдение останавливается) и «сервер недоступен»;
* **терминальный статус останавливает поллинг**, но карточка, история и журнал остаются;
* **некорректный `task_id`** (не UUID) и отклонение схемы дают понятное сообщение, а не падение;
* **обрыв связи не теряет задачу** (BR-R5, BR-R6): наблюдение восстанавливается по
  сохранённому `task_id` из файла сессии после перезапуска пульта.

## 6. Экран «⏱️ Задачи»

| Вкладка | Что делает |
|---|---|
| 📋 Список сервера | `GET /api/tasks/` с фильтрами `task_type`/`status`, периодом создания (переключатель «Фильтр по периоду»; границы считаются как дата-время в `lib.period.day_bounds`) и видами **«🗂 Активные / 📦 Архив / Все»**; список читается целиком (`limit` стенда не ограничен, пульт режет его на `LOAD_TASK_CAP = 500`) и сортируется в пульте по «создана ↓» (`created_at` + `id`), страницы — клиентские (`lib.pagination.paginate`). Колонки: **«Статус»** (пиктограмма с цветом: `▶`/`✔`/`✖`/`?`), **«Источник»** (карточка/снимок/опрос/нет данных), «Наблюдение», «Проверка», «Название» и «Описание» (первые 21 символ, полные значения — в панели строки), «Создана», «Начало», «Окончание», «Архив». Кнопки «⟳ Обновить список», «⟳ Обновить статусы» (сброс кэша карточек), «⏱️ Наблюдать», «🔎 Открыть карточку», «📡 Открыть в консоли» (TC-TASK-02) |
| ⏱️ Наблюдение | таблица наблюдаемых задач (тип, происхождение, проверка, статус, прошедшее время, опросов, интервал, `intermediate_result`, последняя ошибка), кнопки «опросить все сейчас», «пауза поллинга», «снять», настройка интервала |
| 🔎 Карточка задачи | `TaskWithRuntimes` и прогоны, история переходов FSM-1, команды по `available_actions`, привязка к проверке, замечание к API, артефакт, переходы в консоль и журнал, запуск сценариев `TC-TASK-01…07` |
| 🩺 Диагностика | `POST /api/tasks/test?duration=N` с обязательным подтверждением оператора; созданная задача сразу ставится на наблюдение (TC-TASK-01) |
| 🔗 Внешняя задача | ручной ввод `task_id` задачи, запущенной вне пульта; задача помечается «внешняя» (TC-TASK-08, BR-R5) |

Автоопрос: к каждой перерисовке монитор опрашивает задачи, у которых истёк интервал
(`PULT_POLL_INTERVAL`, по умолчанию 2 с; интервал настраивается по задаче). Один опрос за
перерисовку — интерфейс не блокируется; блокирующий `watch()` оставлен для консоли и тестов.

### Статусы строк списка: снимок `task_snapshot.json`

Статуса задачи в `GET /api/tasks/` нет, поэтому экран ведёт **снимок последних известных
статусов** (`acceptance/task_snapshot.py`, файл `acceptance_data/task_snapshot.json` — общий
для пульта, как `records_overrides.json`; в файл сессии эти данные не пишутся):

* таблица рисуется сразу: статус берётся из карточки (если она запрошена), снимка или
  последнего опроса сессии, а колонка «Источник» показывает, откуда он взят; если данных нет,
  в строке честное «— нет данных», а не выдуманный статус;
* карточки видимых строк догружаются **батчами** по `STATUS_BATCH = 25` (внутри батча —
  параллельно, `STATUS_FETCH_WORKERS = 5`), с меткой `TC-TASK-02` и прогрессом; после батча
  страница перерисовывается, поэтому статусы появляются без действий оператора, а свежие
  карточки живут в `session_state` до истечения `STATUS_CACHE_TTL = 30` с;
* статус переживает перезапуск пульта: снимок обновляется при каждом наблюдении, а кнопка
  «⟳ Обновить статусы» сбрасывает кэш карточек и запрашивает заново;
* сообщения о действиях оператора не теряются при таких перерисовках: `repeat_flash`
  (`ui/common/flash.py`) возвращает показанный текст в очередь перед `st.rerun`.

### Архив задач: правило и перенос

Архива задач в API нет (проверяется пробой TC-TASK-02: в элементе списка нет ни признака
архива, ни времени завершения), поэтому правило считает пульт:

* **авто-архив** (`acceptance.task_snapshot.ARCHIVE_AFTER = 1 сутки`): задача с терминальным
  статусом (`completed`, `failed`, `interrupted`, `not_found`) уходит в архив, когда её
  `end_time` из прогона карточки старше суток; задача, **вернувшаяся в работу**, из архива
  возвращается (иначе оператор видел бы в архиве исполняющуюся задачу). Оба перехода пишутся
  событиями `tasks_archived_auto` / `tasks_unarchived_auto`;
* **кнопка оператора** «📦 Перенести завершённые в архив» — в раскрывающейся панели, с
  подтверждением и ценой действия: сначала опрашиваются задачи с неизвестным статусом
  (`GET /api/tasks/{id}`, N+1, батчами), затем завершённые переносятся (событие
  `tasks_archived`, подпись «сколько всего и сколько завершилось за последние сутки»);
* вид «📦 Архив» по умолчанию показывает задачи, **завершённые ≥ суток назад**; флажок
  «Показать перенесённые за сутки» добавляет «только что перенесённые» — так архив не
  «прыгает», когда оператор перенёс завершённые вручную. Записи, которых уже нет в выдаче
  сервера, остаются видны в архиве (по ним показывается тип, название, статус и время
  завершения из снимка).

## 8. Консоль запросов: `task_id` и монитор

1. **Живой список задач в path-параметре.** Рядом с полем `task_id` появился список задач
   сервера с кнопкой «подставить»: ручное копирование UUID убрано, но поле остаётся
   редактируемым (внешняя задача может отсутствовать в списке).
2. **Авто-наблюдение.** Если ответ операции содержит задачу, она сразу ставится на
   наблюдение (`register_task_from_console`), а монитор подхватывает такие задачи при входе
   на экран «Задачи» (`adopt_from_session`).
3. **Переход «в монитор».** Кнопка открывает экран «Задачи» с карточкой этой задачи.
4. **Точность извлечения `task_id`.** Для чтения (`GET`) и ресурсоёмких операций берётся
   любой `task_id`/`task`/`id`; для остальных изменяющих операций `id` означает созданную
   сущность (файл, датасет, модель) и задачей не считается.

## 10. Найденные особенности API и решения пульта

| № | Наблюдение | Как учтено |
|---|---|---|
| 1 | У задачи нет поля `status` — состояние живёт в `runtimes[]` | монитор берёт статус последнего прогона (`current_status`), карточка показывает все прогоны |
| 2 | Неизвестный `task_id` отдаётся статусом `not_found`, а не 404 (BR-R7) | сценарий `tasks.unknown_task` принимает оба варианта, а «сервер недоступен» отличается от «не найдена» |
| 3 | `POST /api/datasets/fill/{id}` не возвращает `task_id` (P1) | обходной путь `TaskMonitor.find_recent` (`GET /api/tasks/` по типу) — используется в T5 |
| 4 | Статус вне FSM-1 не проходит схему задачи | сценарий карточки фиксирует это как «отказ» с фактом «ответ не по схеме», а не молчит |
| 5 | Повтор команды может дать no-op или `409` (BR-R3) | `run_command` не отправляет команду вне `available_actions`, кроме осознанной проверки; вариант записывается в историю и отчёт |
| 6 | `runtimes[]` может содержать прогоны без `end_time`/`result` | карточка показывает прочерки, а TC-TASK-03 отмечает фактически заполненные поля |
| 7 | `start_date`/`end_date` принимаются **только как дата-время** (`format: date-time`): строка `2026-09-09` отвечает 422 `datetime_parsing` («invalid datetime separator, expected T, t, _ or space»); допустимы `…T00:00`, `…T00:00:00`, `.ffffff`, `Z`, `+03:00` | границы периода считает `lib.period.day_bounds`, «чистую» дату не пропускает и `client.tasks._iso`; в TC-TASK-02 добавлена проба «чистой» даты (факт, не отказ), а заглушка смоук-теста отклоняет такой формат так же, как стенд |
| 8 | `end_date` — **исключающая** граница (`created_at < end_date`), `start_date` — включающая (с артефактом ±1 с: задача, созданная за 0,5 с до границы, ещё попадает в выборку) | конец периода отдаётся началом следующих суток, поэтому выбранный день попадает в выборку целиком; семантика границ зафиксирована в замечании P2 и в доказательствах TC-TASK-02 |
| 9 | Границы периода необязательны по отдельности, а наивные значения сравниваются с наивными UTC-отметками задач (то же время, что в таблице) | фильтр периода по умолчанию выключен (видны все задачи, серверный `limit`), подпись под фильтрами показывает фактические границы и предупреждает про UTC |
| 10 | В элементе `GET /api/tasks/` **нет статуса задачи**: в спецификации у `CeleryTask` только `type`, `name`, `description`, `id`, `created_at` — статус есть лишь в карточке (`runtimes[-1].status`); там же нет ни времени завершения, ни признака архива | статус строки собирается из трёх источников (`task_status_view`): карточка → снимок `task_snapshot.json` → последний опрос сессии, а таблица сразу показывает, откуда он взят; карточки видимых строк догружаются батчами по 25 с меткой `TC-TASK-02` и прогрессом; архив («завершена ≥ суток назад») ведёт пульт; замер N+1 на стенде: 10 карточек ≈ 7,4 с последовательно и ≈ 0,7 с через пульт (5 потоков) → замечание **P1**; факты и состав полей пишет TC-TASK-02 |
| 11 | Сортировка задач не поддерживается, порядок выдачи не хронологический (`sorted(created_at) != created_at`) | «свежие сверху» делает пульт: список читается целиком и сортируется локально (`created_at` ↓, затем `id`), страницы — клиентские; факт зафиксирован замечанием **P2** и доказательством `list_unsorted` |
| 12 | Верхняя граница `limit` в спецификации не объявлена, `limit=1000` вернул весь список | пульт читает список одним запросом (`LOAD_TASK_CAP = 500`) и режет его сам — отсюда виды «Активные / Архив / Все» без серверных запросов; факт `limit_uncapped` в TC-TASK-02, живая проба в `test_live_tasks.py` |

### Дефект пульта, найденный на живом стенде (исправлен)

При открытии вкладки «Список задач» экран отправлял «чистые» даты
(`GET /api/tasks/?start_date=2026-09-09&end_date=2026-09-16&limit=25`) и получал **422**
на каждый показ — это видно в журнале пульта (`http_response` со статусом 422) и было
первым, что увидел оператор. Причина: `date.isoformat()` вместо дата-времени, которое
требует спецификация (`format: date-time`). Локальный `pydantic` такие строки принимает,
поэтому баг не воспроизводился в юнит-тестах; его пропустили и сценарий TC-TASK-02
(период не проверялся), и смоук-тест (заглушка отвечала независимо от query).

Что сделано, чтобы это не повторилось:

* границы периода считает один помощник `lib.period.day_bounds` (страница, сценарий,
  тесты), а «чистую» дату не пропускает и клиент (`client/tasks._iso`);
* заглушка `/api/tasks/` в смоук-тестах повторяет поведение стенда — отвечает 422, если у
  `start_date`/`end_date` нет разделителя `T`, поэтому регрессия падает в тестах;
* TC-TASK-02 проверяет период пробами и пишет в доказательства границы и статус,
  которым стенд отвечает на «чистую» дату;
* в консоли у параметров появилась подсказка формата (`ParamSpec.format` из
  спецификации → `start_date (string, date-time)`), чтобы ручной ввод тоже был защищён.

### Дефект UI при аудите списка (исправлен)

На вкладке «Список задач» рендерились **два** селектора размера страницы: рабочий
(«Записей на странице», уходит в `limit`) и второй из общей пагинации («На странице»),
который ни на что не влиял — оператор мог переключить его и не увидеть эффекта.
`render_pagination` получил параметр `show_size`, экран задач вызывает её с
`show_size=False`; смоук-тест проверяет, что на вкладке остался ровно один селектор
(`tasks_per_page`, ключа `tasks_page_size` больше нет).
