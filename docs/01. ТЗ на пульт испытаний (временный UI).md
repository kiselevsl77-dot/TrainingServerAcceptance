## 1. Назначение, цель и границы

**Цель.** Обеспечить проведение испытаний и приёмки текущей версии сервера обучения:
проверить все модули API на реальных данных и в «боевом» режиме, зафиксировать
результаты и замечания, оформить отчёт об испытаниях — не ожидая готовности
продуктивного UI и без изменений со стороны сервера.

**Ключевой принцип.** Всё, что не удалось проверить из-за дефектов/пробелов API,
является **результатом испытаний** (статус «блокировано API» + замечание в отчёте),
а не ошибкой пульта. Ни одна проверка не должна требовать доработки API.

**В объёме работ:**
* все 32 операции 6 модулей API (`Система`, `File Import`, `Datasets`, `Loads`, `ML models`, `Task service`);
* скриптованный чек-лист проверок с трассировкой на требования (UC/FR/BR/FSM);
* свободная консоль запросов к API (диагностика, произвольные пробы);
* прозрачное объединение RAW- и markup-файлов в **записи** (включая дубли имён);
* сессии испытаний (кто/когда/что/с каким результатом) и отчёт об испытаниях (md/json + приложения);
* богатая система журналирования (журнал приложения, структурный журнал сессии, журнал HTTP-обмена).

**Вне объёма:** доработка испытуемого API; авторизация/РБАК (NFR-7 — задел);
продуктивный UI FR-1…FR-8 (развивается отдельно по своему плану); интеграция с
Фабрикой Данных; обучение рабочих моделей вне программы испытаний.

## 2. Терминология (по уточнениям заказчика)

| Термин | Определение | Статус в API |
|---|---|---|
| **Запись (record)** | Пара файлов, поставляемых вместе: `<имя>.raw.csv` (сигналы) + `<имя>.markup.csv` (разметка). Единица работы оператора | **отсутствует** (реестр файлов плоский) → объединение выполняет UI |
| **Дубль** | Файл с тем же `file_name`, что уже есть в хранилище: другой `id`, `size`, `import_date`, `s3_path`. Одноименные файлы — разные версии записи | различаются только по `id`/`size`/`import_date`/`s3_path`; `checksum`/`updated_at` нет |
| **Субдатасет** | Группа записей, объединённых признаком (дата измерений, назначение и т. п.). Не является «версией записи» | **отсутствует** → перспективное требование (п. 3.3); в UI — только помеченное представление |

Следствия, зафиксированные в реализации:
1. понятие «субдатасет» не используется как сущность контракта: группировка выполняется
   пультом и всегда помечается как представление UI;
2. объединение RAW+markup в записи — **актуальное требование текущей версии** (п. 3.1);
3. при наличии дублей оператор обязан видеть все кандидаты пары и иметь возможность
   ручной привязки (п. 3.1).

## 3. Требования к API: три независимых блока

### 3.1. Актуально сейчас — прозрачность объединения RAW+markup в записи (требование к UI)

1. Каждое объединение выполняется по **явному правилу**; правило и «уверенность»
   показываются рядом со значением (подтверждено / не подтверждено / вручную).
2. При дублях отображаются **все** кандидаты (`id`, `size`, `import_date`, `s3_path`),
   а не «лучший» из них.
3. Ручная перепривязка markup ↔ RAW разрешена; решение оператора фиксируется в журнале
   и в истории сессии.
4. Результат объединения выгружается как **манифест** (CSV/JSON) и входит в приложения отчёта.
5. Несопоставленные файлы не скрываются: отдельные разделы с причиной
   («RAW без разметки», «разметка без RAW», «прочие файлы: H5/REPORT_ZIP»).
6. Число записей и чанков считается по markup-файлу и помечается как клиентская оценка
   (серверных агрегатов нет — замечание к API).

### 3.2. Минимальные доработки API, запрашиваемые под испытания

Без этих доработок соответствующие проверки получают статус «блокировано API»
(это фиксируется в отчёте как результат испытаний):

| # | Доработка | Зачем испытаниям | Обходной путь в пульте |
|---|---|---|---|
| 1 | `Content-Disposition: filename*=UTF-8''…` в `GET /api/data/file/{id}/download` | **54 из 62 субдатасетов** не скачиваются (`404 latin-1`) → разметка большинства записей недоступна | скачивать только ASCII-имена; остальное — «блокировано API» |
| 2 | `Content-Length`, `Range`/`ETag` при скачивании | контроль целостности и объёмов (RAW до 2.1 ГБ; всего 41.7 ГБ) | сверять `size` из реестра; не качать крупные RAW целиком |
| 3 | `updated_at`/`checksum` для файлов | однозначное различение дублей и версий | `id` + `size` + `import_date` + `s3_path` |
| 4 | `task_id` в ответе `POST /api/datasets/fill/{id}` | довести проверку наполнения датасета до мониторинга задачи | поиск задачи `dataset-fill` в `GET /api/tasks/` |
| 5 | `phase_connection` в `GET /api/loads/list` + рабочий фильтр `ph_n` | соответствие реестра нагрузок спецификации (FR-3) | набор нагрузок по markup/имени, с пометкой «предварительно» |
| 6 | единый формат ошибок (`HTTPValidationError`) | автоматическая проверка кодов и контрактов | разбор `{"detail": …}` строкой/массивом |

### 3.3. Перспективные требования (в бэклог; сейчас не блокируют)

1. **Субдатасет как сущность первого класса:** `POST/GET /api/subdatasets`,
   `GET /api/subdatasets/{id}/files`, агрегаты (число записей и чанков), признак
   группировки (дата измерений, назначение); альтернатива — поля пары в файле
   (`record_id`/`pair_id`/`role`) плюс группирующий признак.
2. Агрегаты и структурные характеристики: `GET /api/datasets/{id}/summary`
   (состав, записи, чанки, нагрузки), серверные характеристики субдатасета.
3. Связи `load ↔ субдатасет ↔ датасет` (отказ от эвристического «набора нагрузок»).
4. Справочники (`Ph_n`, категории, `file_type`, `DatasetType`), единый формат ошибок,
   описание формата markup-файла, `updated_at`/`checksum`.
5. Эксплуатационные улучшения: presigned URL, batch-операции, сортировка, `ETag`,
   `securitySchemes`/`X-Api-Version`, примеры в спецификации.

## 5. Функциональные требования к пульту (FR-T)

### FR-T1. Панель «Стенд»
* `GET /health` и `GET /version` с показом **всех фактических полей** сборки
  (`branch`, `revision`, `commit`, `message`, `author`, `email`, `build_date`);
  запрос выполняется только по действию оператора (или при первом входе) — каждый
  запрос должен быть осознанным и видимым в журнале.
* Адрес сервера, таймауты, порог скачивания, уровень журналирования, пути журналов.
* **Снимок стенда**: счётчики реестров (файлы и их объём, уникальные имена и дубли,
  типы файлов, нагрузки, модели, датасеты, задачи) и сборка сервера на **начало** и
  **окончание** сессии; сравнение снимков (изменение реестров за сессию).
* Ошибки отдельных запросов снимка не прерывают снимок, а попадают в его раздел «ошибки».

### FR-T2. «Записи и субдатасеты» — прозрачное объединение RAW+markup
* Таблица **записей**: имя базы, RAW (`id`, `size`, `import_date`, `s3_path`),
  markup (те же поля), Δ времени импорта, правило сопоставления, уверенность
  (подтверждено / не подтверждено / вручную), признак дубля, число кандидатов.
* Разделы: «полные записи», «RAW без разметки», «разметка без RAW», «прочие файлы»,
  «дубли имён».
* Действия оператора: ручная перепривязка markup ↔ RAW, снятие привязки, исключение
  из испытаний, комментарий; все решения — события журнала и записи истории сессии.
* Разбор разметки (число записей и чанков) по каждому доступному markup-файлу;
  сравнение дублей одной записи между собой.
* Экспорт **манифеста объединения**: `record_id, base_name, raw_id, raw_name,
  raw_size, raw_import_date, raw_s3_path, markup_id, markup_name, markup_size,
  markup_import_date, markup_s3_path, rule, confidence, manual, comment`
  (CSV + JSON, обязательное приложение к отчёту).
* Производная группировка записей в субдатасеты — **только помеченная** как
  представление UI («в API такого понятия нет»).

### FR-T3. Консоль запросов
* Метод, путь, query, JSON-тело, multipart-файл; шаблоны по всем эндпоинтам `SOM1.json`.
* Предупреждение и подтверждение для изменяющих и ресурсоёмких запросов (NFR-T4).
* Вывод: статус, заголовки, тело, длительность, размер; кнопки «приложить к проверке»
  (метка `TC-…`) и «создать замечание к API».
* Все запросы консоли идут через тот же логирующий транспорт, что запросы проверок.

### FR-T4. Чек-лист проверок (ядро испытаний)
* Проверка = `CheckSpec`: `id` (`TC-<модуль>-<NN>`), название, модуль, трассировка
  (`UC-xx`, `FR-x`, `BR-Fx`, `BR-Rx`, `FSM-1`), класс (`tech`/`live`/`heavy`/`manual`),
  шаги, ожидаемый результат, эндпоинты, признак «зависит от дефекта API».
* Статусы: `не выполнена`, `успех`, `отказ`, `блокировано API`, `пропущена`,
  `выполнена вручную`, `прервана`.
* Результат: факт (сырые данные), ожидание, автоматический вердикт, заключение
  оператора, доказательства, параметры, время и диапазон номеров журнала
  (проверка воспроизводима по JSONL сессии).
* Классы `live`/`heavy` запускаются только после подтверждения оператора; создаваемые
  сущности — с префиксом `__TEST__` и обязательной самоочисткой; отчёт содержит
  перечень созданных и удалённых сущностей.

### FR-T5. Сессия испытаний
* Автоматически: `session_id`, начало/окончание и длительность, адрес сервера, сборка
  (`branch`/`revision`/`commit`/`build_date`), версия пульта (git, Python, ОС), пути
  журналов, снимки стенда, число запросов и ошибок, история событий.
* Заполняется испытателем: наименование испытаний, программа/методика (реквизиты),
  объект испытаний (сборка), заказчик, испытательная организация, оператор (ФИО,
  должность), состав комиссии, цель, объём (перечень проверок), условия, ограничения,
  критерии оценки, дополнительные сведения, подписи.
* Состояния: `черновик` → `идёт` → `завершена`; переоткрытие, «снять с просмотра»,
  выгрузка/загрузка файла сессии (передача между пультами), список сессий.
* Персистентность: `acceptance_data/sessions/<session_id>.json` (сессия переживает
  перезапуск пульта и перерисовку экрана).

### FR-T6. Журналирование (богатая система)

**Назначения (sinks):**
1. консоль — краткий формат для оператора;
2. `acceptance_data/logs/app.log` — текстовый журнал приложения (ротация 10 МБ,
   хранение 10 файлов, UTF-8);
3. `acceptance_data/logs/session_<id>.jsonl` — **структурный** журнал сессии
   (машинный след испытаний и основа отчёта; данные в JSON, читаются программно).

**Контекст каждой записи:** `time`, `level`, `session_id`, `check_id`, `module`,
`event`, `message`, `payload` (структурированные данные).

**Типы событий (обязательный минимум):** запуск пульта; создание/открытие/импорт/
старт/завершение/переоткрытие/удаление сессии; сохранение полей сессии; снимки стенда;
`http_request`, `http_response`, `http_error` (каждый обмен с сервером); шаги проверок,
их вердикты и статусы; добавление замечаний к API; действия оператора (запуск проверки,
подтверждение ресурсоёмкой операции, ручная перепривязка записи, выгрузка отчёта);
очистка журнала; ошибки и исключения с трассировкой.

**Что фиксируется по каждому HTTP-обмену:** порядковый номер, время, метод, путь,
query, метка проверки, статус, длительность (мс), размеры запроса и ответа,
`Content-Type`, текст ошибки соединения, тела (для текстовых типов — до лимита
`PULT_BODY_LIMIT`, с пометкой об усечении; бинарные данные — только размером;
multipart — только размер).

**Уровни:** `DEBUG` (детали и тела), `INFO` (события и шаги), `WARNING` (аномалии:
дубли, не-ASCII, эвристики, расхождения спецификации), `ERROR` (отказы и исключения).
Уровень переключается оператором в интерфейсе; значение фиксируется в отчёте.

**Требования к надёжности журнала:** запись синхронная по умолчанию
(`PULT_LOG_ENQUEUE=false`), журнал испытаний не должен теряться при аварийном
завершении процесса; журнал не блокирует интерфейс; объём контролируется ротацией и
лимитом тела; содержимое файлов данных не логируется (только метаданные и размеры).

**Экран «Журнал»:** сводка (записей, ошибок, максимум мс, объёмы), таблица обменов с
фильтрами (только ошибки / метка проверки / подстрока по пути и ошибке), просмотр
деталей обмена, очистка журнала в памяти, выгрузка журнала (JSON), скачивание
структурного JSONL сессии, просмотр и скачивание любых сохранённых журналов сессий,
хвост `app.log`.

### FR-T7. Реестр замечаний к API

* Поля замечания: заголовок, модуль, эндпоинт, приоритет (`P0`/`P1`/`P2`), факт,
  ожидание, воспроизведение, привязка к проверке (`check_id`), доказательства,
  источник (`оператор`/`авто`), дата.
* Ручное создание — из любого места пульта (консоль, результат проверки, записи).
* Готовые шаблоны известных дефектов (11 замечаний: `latin-1` при скачивании,
  отсутствие `Range`/`Content-Length`, игнорирование `limit/offset` у файлов,
  отсутствие `phase_connection` и неработающий `ph_n`, отсутствие «записи/субдатасета»,
  отсутствие связи «датасет ↔ файлы» и агрегатов, отсутствие `task_id` в `fill`,
  типы `H5`/`REPORT_ZIP` вне перечисления, `DELETE /api/{file_id}` в корне `/api/`,
  отсутствие удаления нагрузки и свободный текст категорий, пустые `signals` у моделей).
* Дедупликация по заголовку; сортировка по приоритету; группировка P0/P1/P2 для отчёта.
* Раздел «Перспективные требования» (в первую очередь субдатасеты) ведётся отдельно и
  в отчёт попадает как бэклог, а не как замечание текущей приёмки.

### FR-T8. Отчёт об испытаниях

Одна кнопка формирует комплект:
* `reports/<session_id>_report.md` — читаемый отчёт;
* `reports/<session_id>_report.json` — машиночитаемая копия;
* приложения: `…_records.csv` (манифест объединения записей), `…_checks.csv`
  (таблица результатов), `…_api_notes.csv` (реестр замечаний), выдержки из JSONL.

**Структура отчёта:** 1) шапка сессии (кто/когда/на какой сборке, программа-методика,
условия, ограничения, критерии); 2) снимок стенда на входе и выходе с изменением
реестров; 3) сводка результатов (успех / отказ / блокировано API / пропущено +
итоговое решение); 4) детализация по каждой проверке (шаги, запросы и ответы,
ожидание/факт, вердикт, заключение оператора, ссылки на номера записей журнала);
5) реестр замечаний к API по приоритетам; 6) ресурсоёмкие операции и расход ресурсов
(что создано/удалено/сохранено как артефакт); 7) перечень созданных и удалённых
`__TEST__`-сущностей; 8) выводы и рекомендации; 9) перспективные требования (бэклог,
включая субдатасеты); 10) приложения.

Отчёт строится **только** по данным сессии и журнала (никаких запросов к серверу при
формировании) — это обеспечивает воспроизводимость: любой шаг проверки повторяется по
записи `http_request`/`http_response` из JSONL.

### FR-T9. Просмотр отчёта, сравнение и финализация

* Просмотр отчёта в интерфейсе, скачивание файлов, перегенерация после дозаполнения полей.
* Сравнение двух сессий (таблица «проверка → статус в сессии A/B») — для повторных приёмок.
* Финализация: обязательные поля проверяются (наименование, объект испытаний, оператор,
  даты, критерий оценки), фиксируется итоговое решение и подписи.

### FR-T10. Ресурсоёмкие («боевые») проверки

* Классы проверок: `tech` (безопасные, дешёвые — выполняются всегда), `live` (боевые на
  реальных данных), `heavy` (ресурсоёмкие: `datasets/fill` больших объёмов, `train`,
  `check`, async `inference`), `manual` (только вручную).
* **Карточка запуска `heavy`-проверки (обязательна перед стартом):** цель проверки;
  используемые данные (датасет/файлы/модель и их идентификаторы); параметры
  (`epochs`, `batch_size`, `learning_rate`, аугментация, `quantization`, `threshold`);
  ответственный испытатель; оценка ожидаемой длительности; явное подтверждение
  «разрешаю расход ресурсов стенда»; решение о судьбе артефакта
  (сохранить как артефакт испытаний / удалить после проверки).
* **Обязательная фиксация в сессии и отчёте:** параметры запуска, `task_id`,
  `celery_task_id`, время старта и окончания, фактическая длительность, переходы
  статусов по FSM-1, `result`/`intermediate_result`, метрики модели (для `train`),
  `version`/`updated_at` модели, имя ONNX-файла (для экспорта), решение о судьбе артефакта.
* **Наблюдение:** поллинг `GET /api/tasks/{task_id}` с настраиваемым интервалом; каждое
  изменение статуса — событие журнала; при обрыве связи или перезапуске пульта
  наблюдение возобновляется по сохранённому `task_id` (BR-R5) без потери истории.
* **Дешёвая предпроверка** каждой `heavy`-операции выполняется всегда: валидация
  контракта (422 на несуществующих идентификаторах, граничные значения, корректность
  перечислений) — без расхода ресурсов.
* **Раздел отчёта «Ресурсоёмкие операции и расход ресурсов»:** что запускалось, сколько
  длилось, что создано, что удалено, что рекомендуется оставить как артефакт испытаний.

### FR-T11. Монитор задач (инфраструктура асинхронных проверок)

* Список задач (`task_type`, `status`, `start_date`, `end_date`, `limit` (по умолчанию
  100)/`offset`), карточка задачи с `runtimes[]` (`status`, `start_time`, `end_time`,
  `result`, `intermediate_result`, `celery_task_id`), история переходов статусов.
* Доступные действия по статусу (FSM-1): `pause` для `running`, `resume` для `paused`,
  `interrupt` для `running`/`pausing`/`paused`.
* Ручной ввод `task_id` для наблюдения за задачей, **запущенной вне пульта**;
  признак «создана пультом / внешняя».
* Кнопки «прикрепить задачу к проверке» и «создать замечание к API» из карточки задачи.
* Диагностический запуск `POST /api/tasks/test?duration=N` — дешёвый способ проверить
  `pause → paused → resume`, `interrupt`, `not_found` и идемпотентность команд без
  расхода ресурсов обучения.
* Монитор обязателен до этапов обучения/инференса: все остальные асинхронные проверки
  (`dataset-fill`, `training`, `model-testing`, `inference`) опираются на него.

## 6. Нефункциональные требования (NFR-T)

* **NFR-T1. Без доработки API.** Ни одна проверка не требует изменений сервера;
  зависимость от дефекта даёт статус «блокировано API» + автоматическое замечание.
* **NFR-T2. Прозрачность.** У любого вычисленного значения указан источник
  (сервер / эвристика UI / решение оператора); правила и уверенность видны рядом.
* **NFR-T3. Устойчивость.** Обрыв связи, таймаут, перезапуск сервера или пульта не
  разрушают сессию: проверка помечается «прервана», шаги остаются в журнале
  (сценарии A/B из `03. backend_requirements.md`).
* **NFR-T4. Безопасность данных.** По умолчанию только чтение; изменяющие и ресурсоёмкие
  проверки — за подтверждением оператора; временные сущности `__TEST__` удаляются;
  крупные файлы (RAW до 2.1 ГБ) не скачиваются без явного решения оператора.
* **NFR-T5. Производительность.** Логирование не блокирует интерфейс; тела в журнале
  ограничены; списки — пагинация (для файлов клиентская, т. к. `limit`/`offset`
  сервер игнорирует).
* **NFR-T6. Совместимость со стеком проекта.** Streamlit ≥ 1.36, httpx ≥ 0.27,
  Pydantic ≥ 2.6, python-dotenv; дополнительные зависимости не вводятся (отчёт — md/json/csv).
* **NFR-T7. Воспроизводимость.** В отчёте фиксируются commit пульта, `revision`/`branch`
  и `build_date` сервера, ОС/Python, уровень журналирования, период испытаний; сессия и
  журнал выгружаются вместе.

## 7. Критерии приёмки пульта (DoD)

1. Чек-лист (≥ 40 проверок) выполняется end-to-end на текущем API; ни одной доработки
   API не потребовалось; «блокировано API» встречается только для сценариев, зависящих
   от известных дефектов (перечень — в чек-листе), и каждое такое случается с
   автоматически сформированным замечанием в отчёте.
2. Каждая проверка даёт статус, вердикт и полный HTTP-трейс в журнале
   (запрос → ответ → проверка → вердикт), привязка — по диапазону номеров записей.
3. Отчёт формируется одной кнопкой в md **и** json; содержит все поля сессии (включая
   начало и окончание, сборку сервера, решение), сводку и детализацию проверок, реестр
   замечаний по приоритетам, приложения (манифест записей, таблицы, выдержки журнала).
4. Манифест объединения RAW+markup выгружается, включает все дубли и ручные привязки;
   несопоставленные файлы отражены явно.
5. Сессия переживает перезапуск пульта; черновик можно продолжить; файл сессии
   переносится между пультами.
6. Автотесты: unit (сессия, манифест/дубли, отчёт, логирующий транспорт, реестр проверок,
   настройки), smoke через `streamlit.testing.v1.AppTest`, integration против живого
   сервиса (чтение + `POST /api/tasks/test` с малой длительностью); `pytest`, `ruff`,
   `mypy` — без замечаний.
7. Ресурсоёмкие проверки включаются в программу испытаний, фиксируются в отчёте отдельным
   разделом (расход ресурсов, созданные артефакты и решение по ним); автотесты пульта
   ресурсоёмких операций не выполняют.

## 9. Риски и допущения

* **Стенд общий.** Изменяющие проверки влияют на живые данные; поэтому только
  `__TEST__`-сущности, самоочистка и перечень созданного/удалённого в отчёте.
  Удаление сущностей без префикса — только вручную и с двойным подтверждением.
* **Ресурсоёмкие прогоны.** `train`/async-инференс допустимы в рамках сессий испытаний
  (решение согласовано), но требуют карточки запуска, ответственного и подтверждения;
  в автотестах пульта они отсутствуют.
* **Доступность данных.** 54 из 62 субдатасетов не скачиваются до исправления дефекта
  `latin-1`: часть проверок будет «блокировано API» — это и есть предмет приёмки.
* **Отсутствие изоляции на сервере.** В API нет тестового режима/песочницы: границы
  «боевых» проверок определяет оператор, пульт лишь требует подтверждения и всё
  протоколирует.
* **Формат отчётности.** md + json + csv, без новых зависимостей; `docx` — только по
  отдельному запросу заказчика.
* **Субдатасеты.** До появления сущности в API группировка записей выполняется пультом
  как представление UI; при появлении серверной сущности пульт переводится на неё через
  манифест (совместимость сохраняется).
