## 2. Контур учёта состава датасета (замечание P1)

Контракт 17.09.2026 состав датасета **не отдаёт**: `GET /api/datasets/{dataset_id}`
возвращает только метаданные (`id`, `creation_date`, `name`, `description`, `type`), а
`POST /api/datasets/fill/{id}` отвечает 202 **без `task_id`**. Поэтому состав ведёт
пульт — и всегда подписывает, откуда данные:

| Источник (`source`) | Что это | Достоверность |
|---|---|---|
| `server` | состав от сервера (ожидаемая операция `GET /api/datasets/{id}/summary`) | эталон |
| `local` | факт наполнения пультом: перечень `raw_file_ids`/`markup_file_ids` записан **до** вызова `fill` | факт (верен даже при отказе задачи) |
| `heuristic` | предположение по реестру файлов (совпадение имени датасета с именем/путём файла) | гипотеза, требует подтверждения заказчика |
| `unknown` | данных нет | «состав недоступен (P1)» |

Правила контура:

1. **Серверный состав имеет приоритет.** Как только операция состава появляется в
   реестре операций, провайдер включает её сам (`server_summary_key()` ищет ключ в
   `acceptance.endpoints`), поэтому ни экран, ни сценарии переписывать не нужно.
2. **Сверка вместо доверия.** Если серверный состав и факт пульта оба есть, `compare`
   сравнивает наборы RAW и markup: расхождение — дефект API (сценарий `TC-DS-03` в этом
   случае получает статус «отказ»).
3. **Учёт переживает сессию.** Состав пишется и в сессию (для отчёта), и в
   `acceptance_data/dataset_composition.json` — датасеты живут дольше одной сессии.
4. **Гипотеза не маскируется под факт.** `heuristic` всегда помечен ярлыком и текстом
   «требует подтверждения»; `TC-DS-03` при отсутствии серверного состава завершается
   «успех с замечанием P1», а не «отказ» — так требование постановки (`docs/02` §9) не
   подменяется поведением пульта.

| `TC-DS-04` | `datasets.update` | live | создаёт датасет, правит `name`/`description`, подтверждает `GET`, удаляет | правка сохранена; `updated_at` в схеме нет (замечание) |
| `TC-DS-05` | `datasets.fill` | **heavy** | 1 пара RAW+markup (параметр `fill_pairs`) → `fill` → 202 → поиск задачи `dataset-fill` → монитор до терминального статуса → состав в учёт → удаление | 202 без `task_id` (P1); задача найдена обходным путём и завершилась `completed`; состав зафиксирован |

| `TC-DS-07` | `datasets.delete` | live | «до/после» по реестру, создание, удаление, подтверждение отсутствия, повторное удаление | датасет удалён, отсутствие подтверждено `GET` (404) и списком; размер реестра вернулся к исходному |

Окна `TC-DS-05` (параметры карточки запуска): поиск задачи — 30 с по умолчанию,
ожидание терминального статуса — 600 с; в юнит-тестах окна нулевые, поэтому оба исхода
(«задача найдена» / «не найдена») проверяются без задержек.

## 4. Экран «🗂️ Датасеты»

| Вкладка | Возможности |
|---|---|
| 📋 Реестр | KPI (датасетов, `__TEST__`, записей состава, задач `dataset-fill`), клиентские фильтры (`name`/`description`/`type`/`creation_date`), таблица с ярлыком состава, выгрузка перечня в артефакты (CSV) |
| 🆕 Создание | создание только `__TEST__`-датасетов (проверка префикса), регистрация в учёте сессии, перечень созданного и не удалённого |
| 🔎 Состав | выбор датасета из реестра или ввод UUID, режим чтения (`auto`/`server`/`local`/`heuristic`), карточка источника и файлов, агрегаты сервера, сверка серверного состава с фактом, «Зафиксировать в учёте», «Состав в артефакты» (JSON), «Замечание к API» из шаблона P1 |
| ⬆️ Наполнение | новый или существующий `__TEST__`-датасет, пары RAW+markup из живых записей, обязательное подтверждение (NFR-T4), ответственный, окна ожидания, состав записывается до вызова API, задача `dataset-fill` ставится на наблюдение и опрашивается до терминального статуса |
| 🧹 Уборка | список `__TEST__`-датасетов реестра с поштучным удалением, массовое удаление с подтверждением, закрытие «хвостов» учёта сессии (вход `TC-CLEAN-01`) |

Боевые датасеты экран **не наполняет**: файлы из датасета удалить нельзя (API такой
операции не имеет), поэтому наполнение боевого датасета было бы необратимым изменением
стенда. На вкладке «Наполнение» это сказано оператору явно.

## 5. Отчёт и замечания к API

* Раздел **7 «Датасеты и состав»** (`report.py`) — таблица состава (датасет, источник,
  файлы, RAW/markup, размер, задача, время, уверенность) и косвенные признаки дублей:
  файлы, входящие в несколько датасетов, и повторные загрузки «имя + размер» с разными
  `id`. Формулировка вывода честная: **вероятностная** — в контракте нет `checksum` и
  `uploaded_by`, поэтому «кто загрузил дубль» доказать нечем.
* `report.json` содержит `datasets.compositions` (полные записи состава) и
  `datasets.overlap` (итоги анализа) — комплект воспроизводим без обращения к стенду.
* Шаблоны замечаний (`notes.py`) на датасеты уже были в реестре известных дефектов;
  этап T5 связал их с проверками: `TC-DS-03` и `TC-DS-05` теперь дают готовое
  замечание P1 к модулю «Datasets» (в том числе автоматически при статусе
  «блокировано API»).

## 7. Ограничения (фиксируются как замечания, а не как дефекты пульта)

1. **Состав датасета недоступен через API** (P1): пульт ведёт учёт сам; для датасетов,
   наполненных вне пульта (например, `skfu-*`/`leti-*`/`synt-*` в живом реестре),
   возможен только режим `heuristic`/`unknown`. Требование к API — перспективное
   (`GET /api/datasets/{id}/summary`, `notes.PROSPECTIVE_REQUIREMENTS`).
2. **`fill` не возвращает `task_id`** (P1): задача ищется в `GET /api/tasks/` по типу
   `dataset-fill` и времени создания (допуск 60 с на расхождение часов). Если сервер
   начнёт отдавать `task_id`, обходной путь отключается сам (монитор принимает `task_id`
   из ответа).
3. **Дубли доказуемы лишь косвенно**: в `FileMetadataResponse` нет `checksum` и
   `uploaded_by`, поэтому отчёт говорит о «признаках», а не о фактах.
4. **Наполнение боевых датасетов не выполняется** ни сценарием, ни экраном (изменение
   необратимо: удаления файлов из датасета в API нет).

## 8. Инструкция оператору (живой прогон TC-DS)

1. Экран «✅ Чек-лист проверок» → группа `TC-DS`; безопасные проверки (`TC-DS-02`,
   `TC-DS-03`, `TC-DS-06`) можно запускать групповым прогоном класса `tech`.
2. `TC-DS-03`: выбрать датасет в карточке (или ввести UUID) и режим чтения состава
   `auto` — пульт покажет источник данных и файлы состава, а для серверного состава
   выполнит сверку с фактом наполнения.
3. `TC-DS-01`, `TC-DS-04`, `TC-DS-07` (класс `live`) требуют карточки запуска и
   подтверждения: они создают и удаляют **свой** `__TEST__`-датасет.
4. `TC-DS-05` (heavy): подтвердить карточку запуска, указать число пар, дождаться
   терминального статуса задачи `dataset-fill`; результат — вердикт, `task_id`, статусы
   FSM-1 и запись состава в отчёте.
5. После прогона — вкладка «🧹 Уборка» экрана «Датасеты»: убедиться, что `__TEST__`
   -датасетов не осталось, и снять финальный снимок стенда (`TC-CLEAN-03`).
