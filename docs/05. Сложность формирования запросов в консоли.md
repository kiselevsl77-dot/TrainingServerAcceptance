## 1. Что оценивается и как этим пользоваться

Оценка отвечает на один вопрос: **сколько данных нужно собрать до нажатия кнопки «Выполнить»**
и где эти данные взять. Метод запроса (GET/POST) сам по себе ничего не говорит: `GET` с одним
`id` из реестра сложнее, чем `POST` с двумя литеральными полями.

Документ используется при:

1. планировании этапов T3–T8 — какие помощники консоли нужны раньше, а какие могут подождать;
2. подготовке сессии испытаний — заранее видно, какие данные надо выгрузить (реестр файлов,
   список задач, сэмпл RAW-строки), чтобы не собирать запрос в спешке;
3. разборе инцидентов — если проверка «не сошлась», по уровню сложности видно, запрос собран
   неверно или сервер ответил иначе.

Вне области оценки: время выполнения сервером, расход ресурсов стенда, стоимость самих
проверок (классы `tech`/`live`/`heavy`/`manual` описаны в `02. Чек-лист испытаний.md`).

## 2. Из чего складывается сложность

| Фактор | Что именно влияет |
|---|---|
| Источник значений | литерал в поле / ответ предыдущей операции / живой реестр (файлы, датасеты, модели, задачи) / файл на диске / значение взять негде (справочник не документирован) |
| Длина тела | одиночные `id` против массивов идентификаторов (десятки–сотни элементов в одном теле) |
| Структура тела | плоское тело против вложенных объектов, свободных схем (`config`), base64-полезной нагрузки |
| Ограничения инструментов | что консоль физически не умеет отправить, а API — не отдаёт (например, состав датасета) |

## 3. Шкала сложности

| Уровень | Оценка | Критерии | Операций |
|---|---|---|---|
| 🟢 S1 | тривиально, до минуты | тела нет или все поля — литералы и константы; только query-параметры, плюс `task_id`, который подставляется из живой задачи пульта | 15 |
| 🟡 S2 | нужны подготовленные данные | есть один `id` из живого реестра, имя с префиксом `__TEST__`, файл на диске или порог `threshold`; подтверждение оператора | 16 |
| 🟠 S3 | много полей, вложенность, справочников нет в API | 4+ полей, диапазоны, вложенные объекты, значения берутся угадыванием (перечни не описаны), нужны идентификаторы из двух и более предыдущих операций | 6 |
| 🔴 S4 | вручную невоспроизводимо | длинные массивы идентификаторов, base64-полезная нагрузка, поле, которое консоль не умеет отправлять | 3 |

**Как читать главную таблицу (§4).** Колонка «Класс» — класс безопасности из реестра
(`read`/`write`/`destructive`/`heavy`), он определяет требования перед запуском (NFR-T4):
изменяющие операции — подтверждение и префикс `__TEST__`, удаляющие — двойное подтверждение
и повторный ввод `id`, ресурсоёмкие — карточка запуска (FR-T10). Колонка «Тело» — что нужно
заполнить: `json`, `multipart` или `—` (тела нет). Колонка «Сложность» — уровень из шкалы выше.
«Что нужно подготовить и откуда» — практический чек-лист оператора, «Обоснование» — почему
уровень именно такой.

## 5. Разбор сложных случаев

### 5.1 `POST /api/datasets/fill/{dataset_id}` — длинный список файлов (S4)

Тело принимает два массива UUID: `raw_file_ids` (обязательный) и `markup_file_ids`
(по умолчанию пустой). Идентификаторы берутся только из `GET /api/data/files`; пары
RAW+markup API не публикует, поэтому их собирает оператор по правилу объединения в записи
(имя плюс время импорта) и выбирает актуальную версию из дублей.

```json
{
  "raw_file_ids": ["cb98aaca-…", "…ещё 128 идентификаторов"],
  "markup_file_ids": ["4f1c2b0e-…", "…ещё 128 идентификаторов"]
}
```

Цифры при срезе 15.09.2026: 265 файлов, 129 записей, 128 дублей в 61 базе имени. Полное
наполнение — 258 идентификаторов в одном теле (около 11 КБ форматированного JSON),
фактический прогон сервера по журналу задач — 52+52 (около 4,5 КБ). Ручной «копипаст»
такого тела не даёт гарантии, что пары собраны верно: сервер соответствие не показывает,
в ответе нет `task_id` (P1), а состав датасета потом не читается (`GET /api/datasets/{id}`
отдаёт только метаданные). Отсюда уровень S4 и требование помощника: тело `fill` должно
собираться из манифеста записей (экран «Записи», этап T5), а не набираться вручную.

### 5.2 `POST /api/ml_models/models/{model_id}/inference/single` — base64-нагрузка (S4)

Обязательные шесть полей — сигналы `U_A_signal`…`I_C_signal`, закодированные base64 по
строке `raw_data` CSV, плюс ADC-метаданные (`U_mult` 721, `U_dev` 1, `I_mult` 25000,
`I_dev` 66, `byte_order` `Little`, `signal_bytes` 3) и `threshold` (по умолчанию 0,5):

```json
{
  "U_A_signal": "<base64>", "U_B_signal": "<base64>", "U_C_signal": "<base64>",
  "I_A_signal": "<base64>", "I_B_signal": "<base64>", "I_C_signal": "<base64>",
  "U_mult": 721, "U_dev": 1, "I_mult": 25000, "I_dev": 66,
  "byte_order": "Little", "signal_bytes": 3, "threshold": 0.5
}
```

В браузере такую строку получить нельзя: нужен RAW-файл (а 108 из 129 записей не
скачиваются из-за не-ASCII имён), разбор строки CSV, кодирование трёхбайтовых значений в
заданном порядке байт и base64. Поэтому операцию нельзя считать «ручной» — её закрывает
помощник этапа T8 (выбор записи и строки, подготовка тела), а ручной режим остаётся только
для проверки границ `threshold` (TC-INF-03) на уже подготовленном сэмпле.

### 5.3 `POST /api/ml_models/models/upload` — поле, которое консоль не умеет отправлять (S4)

В multipart обязательны `file` (файл `.h5`) и `metadata` — **строка** с JSON-описанием
модели. Схема `ModelFileUploadRequest` в спецификации отсутствует (имя встречается только
в описании поля), а `MultipartPayload` консоли умеет отправлять лишь `file`, `file_type` и
`description`. Это означает, что сегодня операция из консоли не выполняется вообще: запрос
уйдёт без `metadata` и получит 422. До этапа T6 (модели) операцию нельзя провести вручную —
это ограничение пульта, а не API.

### 5.4 `POST /api/ml_models/models` — вложенные объекты и base64 (S3)

Обязательных полей три (`architecture`, `name`, `output_size`), но модель без связей
бесполезна, а необязательные поля — самая сложная часть тела:

```json
{
  "architecture": "<из GET /api/ml_models/architectures>",
  "name": "__TEST__model",
  "output_size": 4,
  "phase_type": "three",
  "signals": {"1": ["device-a", "device-b"], "2": ["device-c"]},
  "signal_aliases": {"1": "Фаза A"},
  "config": {"<любая структура>": true},
  "pruning_mask": "<base64>"
}
```

Спецификация не описывает ни перечень `phase_type` (`single`/`three` упомянуты только в
описании метаданных), ни структуру `config`, ни формат `signals`/`signal_aliases` сверх
подсказок. Живые модели приходят с пустым `signals` (P2), образец скопировать негде —
значения приходится конструировать, а ошибку видно только как 422 (TC-MOD-02, TC-MOD-03).

### 5.5 `POST /api/ml_models/models/{model_id}/train` — параметры с диапазонами (S3)

Девять полей, из них четыре с диапазонами, вложенное квантование и два идентификатора из
предыдущих операций:

```json
{
  "dataset_id": "<id заполненного датасета>",
  "batch_size": 32, "epochs": 10, "learning_rate": 1e-05,
  "trained_model_name": "__TEST__trained",
  "augmentation_noise_percentage": 0.01, "augmentation_num_samples": 2,
  "preprocessing_converter": "direct",
  "quantization": {"enabled": true, "num_bits": 8, "symmetric": true}
}
```

`additionalProperties: false` — лишнее или перепутанное имя поля даёт 422, а не подсказку.
Дешёвая предпроверка контракта (граничные значения `epochs`, `batch_size`, `learning_rate`)
выделена в отдельную проверку TC-TR-01, а сам запуск — в TC-TR-02 с карточкой расхода
ресурсов (FR-T10).

### 5.6 `POST /api/loads` и `PUT /api/loads/{load_id}` — справочников нет в API (S3)

```json
{"load_id": "__TEST__load", "phase_connection": "<Ph_…>", "category": "<категория>"}
```

Допустимые значения фаз и категорий API не публикует: в реестре встречаются категории с
разным регистром и служебная `__OTHER__`, а фаза обозначается строкой с кириллической «С»
(`Ph_С`). Ошибка выбора возвращается как 422 без перечня допустимых значений. Для `PUT`
ситуация хуже: `phase_connection` не отдаётся в списке (P0, TC-LOAD-02), поэтому новое
значение подставляется «вслепую», а достоверность правки подтвердить нечем.

### 5.7 AutoML: `POST .../find_params/population` и `.../selection` (S3, контракт 17.09.2026)

Блок AutoML — самый «дорогой» для ручного формирования из добавленных операций. Тело
популяции (`FindParamsPopulationCreateRequest`) содержит список правил-осей
(`MutationRangeRule`/`MutationValuesRule`) с дискриминатором `type`: dot-путь конфига модели
(`layers[*].parameters.filters`), режим мутации (`scale`/`set`/`add`), обязательный
`models_amount` и, для оси-диапазона, пару `range` плюс необязательные `bounds`, `round`,
`uniform`. Размер популяции — произведение `models_amount` по всем правилам, а ошибка в пути
выясняется только по ответу: контракт описывает правила, но не сам конфиг модели.

```json
{
  "name": "__TEST__population",
  "population_config": {
    "include_base_in_population": true,
    "rng_seed": 42,
    "rules": [
      {"type": "range", "path": "layers[0].parameters.filters", "mode": "scale",
       "models_amount": 3, "range": [0.5, 1.5], "round": "int", "uniform": true}
    ]
  }
}
```

Итерация отбора (`FindParamsSelectionRunRequest`) добавляет `train_dataset_id` заполненного
датасета и `selection_config` (`best_count`, `discarded_count`, `sort_keys` с `metric`/`direction`/
`tolerance`/`aggregate`): без настройки отбора мутанты обучаются, но метки не проставляются, и
`grid.csv` приходит без рангов. Ответ — 202 и задача `find-params`, которую дальше ведёт монитор
задач. Отсюда уровень S3 и требования помощника этапа AutoML: заготовка `PopulationConfig`,
подстановка `model_id`/`population_id`/`dataset_id` из живых реестров, просмотр мутантов и
итераций, сохранение `grid.csv` артефактом (см. `docs/09` §8, шаг 1.3).

## 9. Ограничения, выявленные при оценке

1. **Пульт:** `MultipartPayload` (`acceptance/exchange.py`) отправляет только `file`,
   `file_type`, `description`, поэтому обязательное поле `metadata` операции
   `POST /api/ml_models/models/upload` не передаётся вовсе. До этапа T6 (модели) операция
   недоступна из консоли — требуются произвольные поля multipart-формы.
2. **API:** схема `ModelFileUploadRequest` в `SOM1.json` не определена (имя упомянуто только
   в описании поля `metadata`): формат «JSON-строкой» не типизирован, клиент не может
   проверить тело до отправки.
3. **API:** у `fill` нет ни batch-альтернативы, ни обратного чтения состава, ни `task_id` в
   ответе (P1) — проверить, что сервер взял именно указанные файлы, нечем; требуется
   сопоставление по описанию задачи и состав датасета.
4. **API:** перечни, необходимые для заполнения тел, отсутствуют как схемы (`FileType`,
   `PhaseType`), а `phase_connection` не возвращается в реестре нагрузок (P0) — значения
   подбираются угадыванием, ошибка видна только как 422.
5. **Пульт (не блокирует):** для `fill` и `inference/single` нет даже «полуручного» пути:
   собрать такие тела можно только внешним скриптом, а затем вставить строку в консоль —
   это стоит зафиксировать в сессии как артефакт подготовки данных.

## 10. Правило синхронизации документа

Документ опирается на реестр операций, поэтому при обновлении спецификации порядок такой:

1. `python -m tools.gen_endpoints` — пересобрать реестр из `docs/SOM1.json`;
2. `python -m tools.gen_endpoints --check` — убедиться, что расхождений нет;
3. `python -m pytest tests/unit/test_request_complexity_doc.py -q` — проверить, что таблица
   §4 не потеряла операции и совпадает с реестром по виду тела и классу безопасности;
4. для новых операций — добавить строку в таблицу §4 (номер, класс, тело, источник данных,
   уровень из шкалы §3) и при необходимости расширить §5–§9.

Уровни сложности — экспертная оценка, а не свойство спецификации: они пересматриваются
после каждого этапа (T5–T8), когда появляется помощник и операция переходит, например,
из S4 в S2.
