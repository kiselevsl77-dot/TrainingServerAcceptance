# 59. «Реальная тренировка» (контекст К2): план Э1–Э5 и этап Э1 — карточка модели

Продолжение работ после шагов 1–6 плана M2 (`llm_tasks/52`–`53`). Здесь — **второй
контекст работы пульта**, согласованный с заказчиком 01.10.2026.

## 0. Два контекста (решение заказчика)

| | К1. Сплошная проверка API | К2. Реальная тренировка |
|---|---|---|
| Вопрос | «Работает ли API как заявлено» | «Получить пригодную модель» |
| Данные | любые валидные, минимум нагрузки | **боевой датасет**, валидированный вне пульта |
| Модель | первая подходящая из реестра | **конкретная**, выбранная по свойствам |
| Ресурсы | минимизируем | не экономим: качество важнее |
| Результат | вердикты + отчёт | модель + метрики качества + `.onnx` + комплект |

Решения по вопросам (таблица заказчика, 01.10.2026):

1. разделение К1/К2 — **принято**, работаем этапами **Э1 → Э5**, начинаем с Э1;
2. мастер К2 — **отдельная вкладка «Реальная тренировка»**;
3. боевые имена — **разрешить** создавать/загружать сущности без `__TEST__` в режиме
   «полная нагрузка» (двойное подтверждение + запись в сессию);
4. валидация датасета — **внешняя**: пульт не «валидирует», а фиксирует, какой датасет
   использован и что оператор подтвердил его пригодность (автор, время, метаданные);
5. новых проверок `TC-*` — **пока не добавляем**;
6. порядок этапов — не принципиален.

## 2. Этап Э1 — что сделано (детали)

### 2.1. Разведка по коду (что было и чего не было)

* модели видны только таблицей `view.model_rows`: имя, архитектура, версия, фаза,

### 2.2. Живые факты, на которых построена карточка (снято 01.10.2026)

Карточка `stft_mlp-skfu-train-dev (trained)` (стенд `energomera.ai-center.online`):

  (группы 0 и 1: четыре нагрузки + `__OTHER__`);

* `metrics.training_history.loss` — список по эпохам `[0.066989…]`;
* `metrics.testing_history.tests` — список `{accuracy, report_file_id, dataset_id, tested_at}`;
* `metrics.dataset_stats` — ключевые числа (`total_chunks 386869`, `valid_chunks`,
  `filtered_chunks`, `loads_count 52`, `tensors_per_chunk*`);
* `metrics.memory_usage` — `rss_mb`, `vms_mb`, `percent`;

* **фильтр `device_id` у списка моделей падает** (`TC-MOD-05`, 500) — поэтому отбор по

## 3. Отчёт по Э1

### 3.1. Что сделано

* **Карточка модели доступна из пульта.** Маршрут `GET /api/models/{model_id}` отдаёт
  готовую view-модель: свойства, группы сигналов с `device_info` (устройства и категории),
  классы (`signal_aliases`), слои (`config.layers`), сводку метрик (эпохи, батч, скорость
  обучения, препроцессинг, аугментация, потоковая загрузка, память, датасет обучения,
  модель-основа), историю `loss`, историю проверок с `accuracy` и состав датасета обучения,
  а также **размер `.h5`** из реестра `$Файлов` (модель хранит только `file_id`).
* **Отбор «конкретной» модели** — поиск по имени/описанию/идентификатору, архитектура,
  фаза, размер выхода и три признака (обученные, `__TEST__`, боевые). Отбор идёт на стороне
  пульта: фильтр `device_id` у стенда отвечает `500` (`TC-MOD-05`), поэтому запросом
  фильтровать нельзя. Сортировка выводит обученные и свои модели первыми.
* **Профиль прогона живёт в сессии** (схема **v9**, поле `ml_profile`): объект и цель,
  ответственный, режим полной нагрузки с отметкой времени, отметка «датасет валидирован вне
  пульта» (тоже со временем) и выбранная модель (`id` + подпись). Каждое изменение — событие
  `ml_profile_updated` в истории сессии, поэтому решения восстанавливаются по файлу сессии, а
  не по истории чата.
* **Вкладка «Реальная тренировка»** — один честный экран: профиль, отбор моделей, карточка и
  **шаги Э1–Э4 со статусами**. Шаги Э2–Э4 подписаны как запланированные, чтобы незаполненная
  форма не выглядела сломанной.
* **Документы.** `docs/12`: новый раздел §28 (зачем отдельная вкладка, что работает, что
  запланировано, правила общего стенда, карта кода), §18.3 дополнен ссылкой на карточку;
  `README.md`: 30 маршрутов и состав интерфейса.

### 3.2. Что нашлось в процессе (и почему так исправлено)

* **`0` в `signal_num` превращался в пустую строку** (`item.get(...) or ""`): группа сигналов
  «0» становилась «`""`». Исправлено — значение берётся как есть, `None` отдельно.
* **«Проверок выполнено: 0» засоряло сводку** необучённой модели: строка теперь появляется
  только когда проверки действительно были — карточка не выдумывает данных.
* **`docs/12` — не «документ для чтения», а охраняемая часть продукта:** тест требовал, чтобы
  число подразделов `<details>` равнялось пяти, и ловил чужие правки. Страж уточнён до зоны
  «Данные стенда» (`results-sub-*`) — теперь он проверяет то, о чём написан.
* **Номер плана пришлось сменить 56 → 59:** `llm_tasks/56` уже занят планом how-to сквозного
  прохода; ссылки в коде, `docs/12`, тестах и файлах 57/58 приведены к `llm_tasks/59`.
* **Браузерная проверка требует `--virtual-time-budget`:** с обычным `--dump-dom` DOM
  снимается по `load`, до ответов `/api/state` и `/api/train` (они ходят на живой стенд), и
  проверка ложно «проходит» по одной разметке. С бюджетом 25 с в DOM видны живые значения —
  именно это ловит дефекты уровня «скрипт не выполнился».
