## 1. Что именно стало доступно (факты из ответа разработчика)

| Данные                 | Откуда                                                       | Что это даёт пульту                                          |
| ---------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| Идентификатор датасета | `GET /api/datasets/` → `id` (в ответе разработчика он показан как `<uuid>_33b718e3`) | ключ сопоставления задачи и датасета                         |
| Задача наполнения      | `GET /api/tasks/?task_type=dataset-fill` → `name = "fill_dataset_<dataset_id>_<hash>"`, `description = "Fill dataset <id> with 52 raw and 52 markup files"` | находим связанную задачу; в `description` — дешёвый превью-счётчик файлов без карточки |
| **Запрошенный состав** | `GET /api/tasks/{task_id}` → `runtimes[].parameters.dataset_id`, `raw_file_ids[]`, `markup_file_ids[]` | **точный перечень файлов датасета** — то, чего, как считалось, API не отдаёт |
| **Принятый состав**    | `runtimes[].result.raw_processing.loaded_files[]`, `done_raw_file_ids[]`, `failed_files[]`; `markup_processing.loaded_files[]`, `done_markup_file_ids[]` | что реально залито, что упало (частичное наполнение)         |
| Агрегаты               | `result.raw_processing.total_records`, `skipped_records`, `row_positions{file_id → N}`, `execution_time`; `markup_processing.total_records`, `saved_records`, `skipped_invalid_phase`, `missing_external_ids` | записей по датасету **и по каждому файлу**, время, отходы    |
| Состояние              | `runtimes[].status`, `start_time`/`end_time`                 | «наполнен / выполняется / ошибка»                            |

**Главный вывод:** прежняя констатация «в API нет способа получить состав датасета» **верна лишь наполовину** — прямой операции нет, но состав полностью восстанавливается по задаче наполнения. Пулт уже умеет читать `GET /api/tasks/{task_id}`: `client/tasks.TasksApi.get_task()` → `TaskWithRuntimes` → `CeleryTaskRuntime.parameters: dict` и `.result: dict | None` (`client/schemas.py`, строки 375–393). **Новых операций API, изменений контракта `docs/SOM1.json` и перегенерации реестра не требуется** — `get /api/tasks/` и `get /api/tasks/{task_id}` в реестре уже есть с T4.

Чего это **не** решает: чанки (нет), состав в одном запросе (нет → 1 + N запросов), состав датасетов, наполненных не через `POST /api/datasets/fill` (недоступен), и открытые вопросы по форме (см. §8).

## 2. Что меняется в контуре учёта состава

Сейчас (`dataset_composition.py`): `source` ∈ {`server` (недостижим — `apis.datasets.get_dataset_summary` не существует), `local` (факт push-а), `heuristic`, `unknown`}; `server_available()` смотрит только на мифические ключи `get /api/datasets/{id}/summary|composition` в реестре.

Станет: новый источник **`server_task`** («состав из задачи наполнения») и цепочка приоритетов

`server` (если однажды появится прямой эндпоинт) → **`server_task`** → `local` → `heuristic` → `unknown`.

| Источник                | Когда                                  | Достоверность                                                |
| ----------------------- | -------------------------------------- | ------------------------------------------------------------ |
| `server_task`           | есть задача `dataset-fill` по датасету | **эталон**; включает чужие датасеты (`skfu-*`, `leti-*`), которые сейчас уходят в гипотезу/`unknown` |
| `local`                 | наполнял пульт в этой/прошлой сессии   | факт «что отправили» — нужен для сверки с `parameters` и как страховка, если задачу уже не найти |
| `heuristic` / `unknown` | задачи наполнения нет                  | как раньше                                                   |

Появляется двухслойная достоверность: **запрошено** (`parameters`) vs **принято** (`result.done_*`, `loaded_files`, `failed_files`, `row_positions`) — это и есть «отображение датасетов в соответствии с их составом», включая «наполнен частично: 50 из 52 RAW, 2 файла с ошибкой».

## 7. Развилка (нужно решение)

- **Вариант A (рекомендую, числа не меняются):** вся логика в `read_composition` + переработка `TC-DS-03` (проверка метаданных и состава) и `TC-DS-05`. Каталог остаётся 48/69, KPI `48 / 69`, документы и тесты чисел не трогаются.
- **Вариант B (расширение):** добавить проверку `TC-DS-08` «Состав существующего датасета по задаче наполнения» (`tech`). Тогда ripple: `docs/02` §9 + строка, `GroupPlan("TC-DS", …, 8)`, каталог 48→49, программа 69→70, KPI `49 / 70`, `not_run`, `test_checks_engine.py`, `tests/smoke/*`, `docs/12`/README — всё это придётся согласовать.

## 8. Риски и что нужно уточнить

Риски: тяжёлые карточки задач в журнале (лимит тел и JSONL сессии) — читать с оглядкой на `PultConfig.body_limit`; 1 + N запросов при открытии `SCR-204` → кэш и ленивое чтение; `row_positions` в спецификации не описан (сумма значений ≈ `total_records`, но не равна — трактовать осторожно, показывать как «строк по данным задачи»); задачи удалённых `__TEST__`-датасетов остаются — при анализе дублей исключать датасеты, которых нет в реестре; для датасетов, наполненных не через `fill`, состав по-прежнему недоступен.
