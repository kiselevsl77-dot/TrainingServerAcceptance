## 2. Состав работ

### 2.1. Клиент (`client/datasets.py`) — минимум
- Дополнить докстринг-шапку замечаниями, которые подтверждены постановкой: **нет состава датасета и агрегатов (записи/чанки)** — P1; **`fill` без `task_id`** — P1; `DatasetType` — единственное значение `direct_fill`.
- Опционально: `fill_dataset(..., limit_hint=...)` не нужен — сигнатура уже соответствует контракту.

### 2.2. Экран «🗂️ Датасеты» — `acceptance/ui/pages/datasets.py` (новый, ~350–450 строк)
Паттерн — как в `notes.py`/`records.py` (KPI → вкладки → таблица → карточка → действия):

| Вкладка      | Содержимое                                                   |
| ------------ | ------------------------------------------------------------ |
| 📋 Реестр     | KPI (всего, `direct_fill`, созданные пультом `__TEST__`, задач `dataset-fill` в работе); фильтры `name`/`description`/`type`/период создания; кнопка «⟳ Обновить реестр» (`state.refresh_datasets`); таблица (`id`, `name`, `description`, `type`, `creation_date`) |
| 🆕 Создание   | `name` с контролем префикса `__TEST__`, `description`, `type` (только `direct_fill`) → `create_dataset` → фиксация сущности (`session.add_test_entity`), метка проверки `TC-DS-01` |
| 🔎 Карточка   | метаданные выбранного датасета; явное предупреждение «состав и агрегаты недоступны (P1)»; кнопка «✍ Создать замечание к API» (шаблон P1), «📎 В артефакты», «→ в чек-лист»; история вызовов по метке |
| ⬆️ Наполнение | выбор записей (RAW+markup) из живого реестра (через `acceptance.records.build_records` — пары, размеры, `__TEST__`-фильтр), карточка запуска (heavy, FR-T10) → `fill_dataset` → 202 → **поиск задачи** `dataset-fill` через `monitor.find_recent` (создана не раньше подачи) → `register_task` → наблюдение до терминального статуса; фиксация «в ответе нет `task_id`» (P1) |
| 🧹 Уборка     | список `__TEST__`-датасетов сессии (`session.test_entities` + реестр), подтверждение (чекбокс + слово `DELETE`; для чужих имён — повторный ввод `id`), удаление по одному и «удалить все созданные пультом»; фиксация через `mark_test_entity_deleted` |

Плюс: `app.py` — пункт `"datasets": ("🗂️ Датасеты", datasets.render)` в группе «Испытания»; выгрузка реестра датасетов в артефакты (csv/json) для отчёта.
`state.py` — `DATASETS_CACHE_TTL = 30.0`, `load_datasets() -> (list[DatasetResponse], error)`, `refresh_datasets()` (копия паттерна `load_loads`).

### 2.3. Сценарии — `acceptance/checks/datasets.py` (новый, 7 сценариев)

| id       | automation               | Класс     | Что делает сценарий                                          | Ожидаемый результат                                          |
| -------- | ------------------------ | --------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| TC-DS-01 | `datasets.create`        | live      | создаёт `__TEST__<uuid>` (`type=direct_fill`), сверяет ответ со схемой, регистрирует сущность в сессии | 201, `id` + `creation_date`, `type = direct_fill`            |
| TC-DS-02 | `datasets.list`          | tech      | `GET /api/datasets/` → `datasets` + `count`; пробует фильтры `name` (подстрока), `description`, `type`, `creation_date`; фиксирует расхождения как замечание, не как отказ | список и `count` согласованы, фильтры отвечают               |
| TC-DS-03 | `datasets.meta`          | tech      | `GET /api/datasets/{id}` (из пикера или первый из реестра) → сверяет состав полей с `DatasetResponse`; evidence: `fields`, отсутствие агрегатов | метаданные получены; **состав/агрегаты отсутствуют** → «успех» + замечание P1 |
| TC-DS-04 | `datasets.update`        | live      | создаёт `__TEST__` датасет → `PUT` (`name`, `description`) → `GET` подтверждает изменения; `updated_at` в схеме нет → замечание; удаляет за собой | изменения видны, `updated_at` отсутствует (замечание)        |
| TC-DS-05 | `datasets.fill`          | **heavy** | создаёт `__TEST__` датасет → выбирает пару RAW+markup (ASCII-имя markup, малый размер) → `fill` → 202 → ищет задачу `dataset-fill` (`monitor.find_recent`, окно ожидания) → `register_task` → поллинг до терминального статуса → удаляет датасет; evidence: `task_id`, цепочка статусов, длительность, число файлов | 202 получен; задача найдена и отслежена; самоочистка выполнена |
| TC-DS-06 | `datasets.fill_contract` | tech      | дешёвые предпроверки `fill` без ресурсов: несуществующий `dataset_id` → 404/422; тело без обязательного `raw_file_ids` → 422 | валидация понятна, 5xx нет                                   |
| TC-DS-07 | `datasets.delete`        | live      | создаёт `__TEST__` датасет → `DELETE` → `GET` → 404/`not found`; `mark_test_entity_deleted` | датасет удалён, отсутствие подтверждено, учёт закрыт         |

Общие правила модуля (как в других доменах): нет стенда/датасетов → `PreconditionError` («пропущена»); все изменяющие — только `__TEST__`-имена и самоочистка.

## 4. Решения (рекомендации)

1. **Экран — отдельный пункт меню** «🗂️ Датасеты» в группе «Испытания» (после «Записи»/«Задачи»); вкладку в «Записи» не делаем.
2. **`TC-DS-05`: 1 пара файлов** по умолчанию (параметр `fill_pairs`, `__TEST__`-датасет) — прогон дешёвый и повторяемый; 5+ пар — по решению оператора в карточке запуска.
3. **Окна ожидания `TC-DS-05`**: поиск задачи `dataset-fill` — до 30 с, ожидание терминального статуса — до 10 мин; в юнит-тестах — нулевые окна (проверяется и «найдено», и «не найдено»).
4. **Замечания P1 по датасетам** заводятся шаблонами (статус проверки «успех»), авто-создание — только для статуса «блокировано API», как сейчас.
5. **Нумерация документов**: `docs/11` (следующий номер после `docs/10`), далее T6 — `docs/12`.
6. **Уборка `__TEST__`-датасетов** делается сразу на экране (кнопка «удалить созданные пультом») — это заготовка под `TC-CLEAN-01` в T9.
