## 2. Способ загрузки файла (решение этапа)

**Разбор `multipart/form-data` не делаем.** Оба конца наши (тонкий API + наша страница),
поэтому файл идёт **сырым телом запроса**, а параметры — в query-строке:

```
POST /api/data/files?file_name=raw-01.csv&file_type=RAW&description=...
Content-Type: text/csv
<байты файла>
```

Почему так:

* браузер отдаёт `File` как тело запроса (`fetch(..., {body: file})`) и **сам** стримит файл
  с диска — 2,18 ГБ не проходят через память JS;
* пульт копирует поток во временный файл порциями (`rfile.read(CHUNK)`), считая `sha256`
  и размер; память ограничена размером порции;
* клиент стенда отправляет тот же временный файл файловым объектом (`httpx` стримит);
* `Content-Type` пробрасывается: стенд проверяет MIME (`application/octet-stream` для CSV
  отвечает `400 Only CSV files are allowed`), поэтому для `.csv` отправляем `text/csv`
  (`client/files.py:39 CONTENT_TYPES`).

Временный файл живёт от начала приёма до отправки на стенд и удаляется в `finally`;
в сессию пишется паспорт файла (имя, размер, `sha256`, тип, `file_id` стенда).

## 3. Состав работ Э2.1

1. **`pult/uploads.py`** (новый, чистый модуль):
   * `save_stream(stream, length, *, dest_dir, file_name, max_bytes, chunk)` — потоковая
     запись во временный файл с `sha256` и контролем размера (`UploadError` → 413);
   * `safe_name(value)` — имя файла без путей и управляющих символов;
   * `MAX_UPLOAD` (по умолчанию 3 ГиБ);
   * модуль не знает ни о стенде, ни об интерфейсе (правило `llm_tasks/31.4` §3).
2. **`client/files.py`**: `upload(..., path=Path)` — потоковая отправка (при `content`
   поведение прежнее); тем же путём пойдёт загрузка `.h5` в Э2.2.
3. **Сессия, схема v10**: `dataset_manifests` (паспорта загруженных файлов и состав
   датасета) и `flow_steps` (журнал шагов К2); функции `add_dataset_manifest`,
   `add_flow_step`; чтение старых файлов без миграции.
4. **Маршруты пульта** (30 → 33): `POST /api/data/files` (потоковая загрузка),
   `POST /api/datasets` (`create` / `fill` / `refresh` / `delete`), `GET /api/datasets/{id}`
   (состав). После записи кэш реестров сбрасывается (`state.invalidate`).
5. **View + интерфейс**: в шаге «Данные (датасет)» — загрузка файлов с прогрессом
   (`XMLHttpRequest.upload.onprogress`), таблица «что залито», создание и наполнение
   датасета, ожидание задачи `dataset-fill` (через `GET /api/tasks/`), снимок состава
   и чекбокс «датасет проверен вне стенда» с пояснением границы ответственности.
6. **Тесты**: `tests/unit/test_pult_uploads.py` (поток, лимит, `sha256`, имя),
   дополнение `tests/unit/test_client_files.py` (загрузка путём), `test_session.py` (v10),
   `test_pult_server.py` (маршруты), `test_pult_view.py` (зона данных), smoke-срез.
7. **Документы**: `README.md` (число маршрутов, схема v10, новый модуль), `docs/12` §28.2 —
   короткой правкой; подробное наполнение — по факту Э2.2/Э3.

## 6. Риски

* **Загрузка гигабайтных файлов** — самая дорогая операция этапа: длинный HTTP-запрос,
  нужен прогресс и понятная ошибка; при обрыве временный файл удаляется, факт неудачи
  пишется в журнал шага.
* **Очередь стенда** — задача `dataset-fill` может не разбираться воркером (тот же дефект,
  что у `training`): экран показывает состояние задачи как есть, приёмка — по поведению
  очереди, а не по времени.
* **Совместимость** — расширение `client.files.upload` не должно ломать сценарии проверок
  (`TC-FILE-*`), поэтому приём `bytes` сохраняется и покрыт тестами.
