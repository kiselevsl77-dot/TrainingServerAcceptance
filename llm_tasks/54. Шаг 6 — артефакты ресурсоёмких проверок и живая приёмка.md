## 1. Решение по артефакту видно отчёту (`FR-T10`, `TC-CLEAN-04`)

| Слой | Что появилось |
|---|---|
| Ядро | `acceptance/session.py`: слова решения `ARTIFACT_KEPT` («сохранён артефактом») и `ARTIFACT_DELETED` («удалён после проверки»), `add_artifact` принимает `name`/`entity_id`/`action`/`check_id`, а `path` стал необязательным — решение о модели, оставшейся **на стенде**, файла не имеет |

| Сценарии | `ml_tasks.cleanup_model` пишет решение в артефакты сессии в **обеих** ветках: `keep_artifact` → «сохранён артефактом», уборка → «удалён после проверки» (вместе с записью `__TEST__`-сущности) |
| Пульт | `pult/artifacts.py` — правила (кто кандидат, какие слова принимаются, как считается итог), `view.artifacts_view` — строки панели, `GET/POST /api/artifacts` — кандидаты и решение оператора |
| Интерфейс | вкладка «Задачи», зона «Артефакты ресурсоёмких проверок»: кнопки «💾 в артефакты» и «🗑 удалить» по каждой модели/файлу, счётчик «ждут решения» и предупреждение «TC-CLEAN-04 ставить рано» |

Кандидатами считаются **объекты стенда**, а не записи сессии: модели и файлы `.h5`/`.onnx`
с префиксом `__TEST__` (сначала следы своей сессии, затем «прошлый прогон»). `keep`
модели оставляет её на стенде, при `download` дополнительно выгружает ONNX в
`acceptance_data/artifacts/`; `delete` убирает объект (модель — `DELETE
/api/ml_models/models/{id}`, файл — в корне `/api/{file_id}`) и отмечает
`__TEST__`-сущность удалённой, чтобы `TC-CLEAN-01` видел полную картину.

Действие принимается и словами панели (`keep`/`delete`), и формулировками карточки
запуска («оставить для разбора», «удалить после проверки», «выгрузить в
доказательства») — страж `test_card_wording_matches_run_card_actions` не даёт словарям
разойтись.

## 3. Приёмка отрисовки браузером (`--headless=new --dump-dom`)

Живой пульт поднят против стенда `https://energomera.ai-center.online`, страница и её
данные сняты Chrome (`--virtual-time-budget`, иначе дамп успевает сняться до ответов API):

| Что проверялось | Результат |
|---|---|
| Страница `/` | DOM 61 328 Б, 6 вкладок, «Стенд:» заполнен адресом из `GET /api/state`, «Следующая: `TC-TR-03`», сообщений об ошибке обмена нет |
| Вкладка `/#tasks` | панель «Задачи» активна, зона «Артефакты ресурсоёмких проверок» отрисована: «объектов: 0 · наша сессия: 0 · ждут решения: 0 · TC-CLEAN-04 можно ставить», примечание «Кандидатов нет: тяжёлые проверки не оставили объектов на стенде», «Фоновых прогонов ещё не было» |

Проверка нашла **дефект окружения, а не кода**: на порту 8502 остались два процесса
пульта из прошлых сессий, а Windows позволяет поднять новый поверх них
(`SO_REUSEADDR`) — часть запросов уходила к старому процессу, и панель отвечала
«маршрут `GET /api/artifacts` не найден». Поэтому перед приёмкой пульт поднимается на
свободном порту (процессы 14812/26592 сняты). Этот дефект виден только браузером —
HTTP-тесты о нём не знают.

Повторный снимок после правки итога (`/#tasks`, живой пульт): `artifacts-meta` —
«объектов: 0 · наша сессия: 0 · ждут решения: 0 · TC-CLEAN-04 можно ставить»,
`artifacts-note` — «Объектов на стенде не осталось; решения зафиксированы: сохранено
артефактами 0, удалено 1 (решения есть у каждого объекта)»: панель помнит решение,
принятое в живом прогоне, хотя объекта на стенде уже нет.

## 5. Реальное обучение: что показал стенд (и почему приёмка не закрыта)

По решению заказчика (`llm_tasks/52`) приёмка запускает контрактное обучение
(`epochs=3`, `batch_size=32`) на **своей** `__TEST__`-модели, собранной по образцу
боевой (`stft_mlp-skfu-train-dev (trained)`: архитектура, `phase_type`, `output_size`,
группы `signals`), датасет — тот же, что у образца (`skfu-train`).

| Шаг | Факт |
|---|---|
| `POST /api/ml_models/models` (база) | 201, модель создана |
| `POST /api/ml_models/models/{id}/train` | **200 за 4,8 с**: задача `training` создана (`task_id=1a2809d4-…`, `type=training`, `name=train_model_<id>_<суффикс>`) |
| Наблюдение монитором пакета | задача опрашивается (`GET /api/tasks/{id}` → 200), runtime с `status=new` — **9 минут без изменений** |
| Итог | задача так и не стартовала: стенд принимает обучение, но не исполняет его (воркер очередь не разбирает) |

Вывод, зафиксированный в тесте как честный пропуск, а не отказ: `TC-TR-02` остаётся со
**примечанием** «задача не завершилась: она остаётся на стенде», и проверка не даёт
вердикта «отказ» — это и есть решение заказчика из `llm_tasks/52`. Приёмку «обучение
дошло до модели-результата» закрыть нельзя: результата нет по вине стенда, а не пульта.

Живые факты попутно уточнили два места в сценарии приёмки:

* **`signals` обязателен и по числам групп совпадает с `output_size`**: стенд отвечал
  `400` — «Number of signal groups (0) does not match output_size (2)»; в карточке
  сигналы приходят плоским списком (`signal_num`, `device_id`), а на создание модели
  идёт словарь «группа → устройства»;
* **подходящий датасет надёжнее брать из метрик модели-образца** (`metrics.dataset_id`),
  а не по имени: он заведомо совместим с её архитектурой и признаками.

## 6. Решение по артефакту в живом пульте (`FR-T10`, `TC-CLEAN-04`)

Отдельный живой тест заводит свой `__TEST__`-объект, работает с живым пультом
(`GET/POST /api/artifacts`) и убирает за собой; решение пишется в **отдельную** сессию
приёмки, сессия оператора не трогается (в конце возвращается выбранной):

```
объект приёмки: __TEST__artifact_demo_20261001-142108-25c8 (28a3488b-…)
кандидат в панели: decision="", decision_label="решение не принято", owner="прошлый прогон"
keep  → {"kind": "модель", "name": "__TEST__artifact_demo_…", "action": "сохранён артефактом",
         "entity_id": "28a3488b-…", "check_id": "TC-TR-04",
         "note": "__TEST__artifact_demo_… остаётся на стенде как артефакт испытаний"}
delete → {"action": "удалён после проверки", "note": "__TEST__artifact_demo_… удалён со стенда"}
итог панели: Объектов на стенде не осталось; решения зафиксированы:
             сохранено артефактами 0, удалено 1 (решения есть у каждого объекта)
```

Здесь же живая приёмка вскрыла **изъян интерфейса** (исправлен): сразу после удаления
список кандидатов пустел, и панель сообщала «Кандидатов нет» — оператор ставил бы
`TC-CLEAN-04` вслепую. Теперь счётчики решений берутся из сессии, а «ждут решения» — из
кандидатов стенда: убранный объект из итога не исчезает, а «пустой стенд» и «работа
сделана» различаются текстом. Стража — `test_decided_object_still_counted_after_removal`.

После прогонов стенд чист: моделей, файлов и датасетов с `__TEST__` в реестрах нет;
сессии приёмки (5 штук, по одной на попытку) удалены, оператору возвращена его сессия
«Тестовая сессия 3».

## 7. Что осталось

1. **Реальное обучение до модели-результата** — закрывается, когда воркер стенда начнёт
   разбирать очередь: приёмка готова (`PULT_LIVE_HEAVY=1`), ждёт только стенд.
   Как только задача дойдёт до терминального статуса, тот же тест сам выполнит
   `TC-TR-04` с решением «оставить артефактом» и напечатает длительность обучения.
2. **`TC-CLEAN-04`** — ручная проверка: оператор ставит её, когда панель артефактов
   показывает «решения есть у каждого объекта» (кандидатов без решения не осталось).
3. **Замечания по живому стенду** (в `docs/12` §15.5/§25.2 уже есть дефект P1 по
   `device_id`): добавить наблюдение «обучение принимается, но не исполняется» —
   задача `training` остаётся в статусе `new`.
