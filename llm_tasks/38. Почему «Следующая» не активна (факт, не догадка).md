## 1. Почему «Следующая» не активна (факт, не догадка)

**Что происходит на самом деле.** Кнопки живут в шапке (`index.html:17–18`), и их включает/выключает единственная строка в `renderHeader`:

```js
nextButton.disabled = !next.runnable;      // next приходит из GET /api/state
document.getElementById("btn-batch").disabled = !next.runnable;
```

А `next.runnable` в шапке считает `view.header_view` (`pult/view.py:307–308`):

```python
elif not programme.is_approved:
    next_view["reason"] = "Программа сессии не утверждена"   # → runnable = False
```

**Что при этом думает ядро.** Живая сессия `20260926-000303-25c5` (посчитано только чтением, без записи):

| Проверка                       | Значение                                                     |
| ------------------------------ | ------------------------------------------------------------ |
| статус сессии                  | «идёт», `run_revision` 0, `skip_done` True                   |
| программа                      | ревизия **1**, `approved=False`, статус **черновик**, 6 пунктов |
| очередь (вычисляемая)          | ревизия 1, `draft=True`, 6 пунктов, следующая — **`TC-SYS-01`** |
| `runner.can_run(...)`          | **`(True, '')`** — ядро разрешает запуск                     |
| `runner.programme_notice(...)` | «Прогон идёт по черновику программы (ревизия 1): он помечен в протоколе и отчёте» |
| правило шапки (`is_approved`)  | **False** → кнопка выключена                                 |

То есть **расхождение двух правил**: ядро прогон по черновику разрешает и помечает (`acceptance/queue.py:500` — «Прогон по черновику программы разрешён, но очередь это помечает»), а шапка требует утверждённой ревизии. Дополнительно: **на странице «Прогон» органов управления нет вообще** — там только таблица и итоги последнего запуска, причина — мелкой серой строкой в шапке, кнопок «исправить» нет. Отсюда ощущение «вижу проверки, но управлять нечем».

**Что можно сделать прямо сейчас** (без правок кода, 1 клик): «Планирование» → «Программа сессии» → заполнить «обоснование сокращения» (его требует утверждение, если есть непокрытые разделы) → **«Утвердить ревизию»**. После этого кнопка «▶ Следующая: `TC-SYS-01`» станет активной — правило шапки выполнится.

## 2. План части C — страница «Прогон» (UC-09, UC-12, UC-14, UC-15, UC-16)

**C0. Одно правило «можно запускать» вместо двух**
- Вынести правило готовности в один Python-помощник (например `view.run_readiness(session, programme, queue)`), который используют и шапка, и `GET /api/run` — плюс режимы `draft`/`blocked` с причиной и подсказкой (`fix.panel`, `fix.label`).
- На странице «Прогон» — баннер состояния: активная команда **или** причина + кнопка действия («Утвердить программу» → переход в «Планирование» к кнопке утверждения; «Собрать программу» → туда же). Само утверждение остаётся в «Планировании» (принцип `IR-P-18`: в «Испытаниях» состав не правится) — на «Прогоне» только переход.
- Фаза и предупреждение «прогон по черновику (ревизия N)» — из того же помощника, чтобы шапка и страница не расходились.

**C1. API**
1. `GET /api/run` расширяется (всё считает Python, JS только рисует):
   - `next.item` — название, класс, раздел, требование, ожидаемый результат, `confirm_required`, `operator_required`;
   - `card` — форма карточки запуска: поля с подписями (`run_card.FIELD_LABELS`), значения из `run_card.defaults()`, варианты `run_card.ARTIFACT_ACTIONS`, `filled`, `missing`;
   - `payload` — предпросмотр «что будет отправлено»: `test_payloads.payload_previews()` + `preview_lines()`/`summary()` (имена и тела `__TEST__`, «убирает ли за собой»);
   - `mark` — форма ручной отметки: допустимые статусы (`CheckStatus`: «выполнена вручную», «пропущена», «блокировано API», «прервана», «отказ»), обязательность заключения (`FR-P-32`);
   - `batch` — число пунктов для подписи «▶▶ Пачка tech (n)» (`batch_tech_ids`);
   - `modes` — режимы «только невыполненное» / «всё подряд» с текущим значением (`session.skip_done`);
   - `readiness` — причина и предлагаемое действие (из C0).
2. `POST /api/run` — новые действия: `mode` (`skip_done`, сохраняется в сессии — уже частично поддержано в теле), `pause` (`queue.set_pause` с диапазоном ядра), `auto-step`/`stop` (`runner.auto_step` + `stop_requested`) — если авто входит в C. Плюс предпроверка: пункт с карточкой/ручной → `409` с понятным текстом вместо молчаливого исполнения.
3. `POST /api/checks/{id}` — дополнить: `annotate` требует непустое заключение (иначе `422`), `run-card` сохраняет значения, чтобы форма переоткрывалась заполненной (`GET /api/run` отдаёт их в `card`).
