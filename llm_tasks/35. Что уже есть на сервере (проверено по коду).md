## План Step 2, часть 1 — страница «Планирование» (UC-05, UC-06)

**Коммит A — API-довесок (без страницы).**
1. `pult/server.py`: новые действия `sets: remove|reorder|revise|restore`, `programme: reorder`; те же ошибки, что у остальных (`404` — набор/пункт не найден, `422` — неизвестное действие); ответы возвращают уже готовые view-модели (`api_sets` / `api_programme`), чтобы страница не дособирала данные.
2. Тесты `tests/unit/test_pult_server.py`: по действию на каждое — массовое добавление с `mandatory`, удаление проверок, порядок, ревизия и возврат ревизии, порядок программы; плюс «набор не найден» → 404 и «неизвестное действие» → 422.
3. Гейты: pytest / ruff / ruff format / mypy / `gen_endpoints --check` (реестр эндпоинтов стенда не меняется, проверка должна остаться зелёной).

**Коммит B — сама страница.**
1. `pult/web/index.html`: вкладка **«Планирование»** между «Прогон» и «Сессии» (порядок процесса: планирование → прогон → результаты) и панель `#panel-planning` из трёх зон:
   * **Каталог** — фильтры (раздел, класс, поиск), таблица (`check_id`, название, класс, раздел, требование, ожидание, метки «в наборе»/«в программе», статус сессии), галочки массового выбора → «Добавить в набор» (с флагом «обязательная») и «Создать набор из выбранных»;
   * **Наборы** — таблица библиотеки (название, раздел, статус, ревизия, проверок, обязательных, в программе, пересечение), действия «утвердить», «новая ревизия», «вернуть ревизию», «удалить» (утверждённый — с подтверждением), участие в программе галочкой; состав выбранного набора — список с «убрать» и «вверх/вниз»;
   * **Программа сессии** — KPI (проверок, обязательных, разделов покрыто/не покрыто, пересечений, не описано в каталоге), матрица покрытия (раздел: в программе / реализовано / план / цель / не хватает), предупреждения, поле «обоснование сокращения» → «Утвердить ревизию», список ревизий с «вернуть», дельта с предыдущей (добавлено/убрано), таблица пунктов (порядок, проверка, класс, обязательный, происхождение).
2. `pult/web/app.js`: `loadPanel("planning")` → три вызова (`/api/catalog`, `/api/sets`, `/api/programme`) и три функции отрисовки; всё через `textContent` (правило экранирования §3 ТЗ), кнопки — существующим `button()`/`act()`/`actRefresh()`; выбранные галочки — только UI-состояние, никакой бизнес-логики.
3. Маршрутизация по хэшу (`#planning`, `#run`, …) — чтобы вкладку можно было открыть ссылкой и её отрисовку можно было проверить headless-браузером.
4. `pult/web/styles.css`: трёхзонная раскладка (на узком экране — в столбик), мелкие кнопки, подсветка меток.
5. Тесты: `tests/smoke/test_vertical_slice.py` расширяется до полного пути MVP — **набор из каталога (массовый выбор + обязательная) → утверждение набора → сборка программы по наборам → покрытие/предупреждения/дельта → утверждение ревизии → прогон → протокол**; плюс проверка, что `/` отдаётся для отображения (уже есть).

## Риски и как их снимаю

| Риск                                                      | Ответ                                                        |
| --------------------------------------------------------- | ------------------------------------------------------------ |
| Каталог большой (много проверок) — страница «тяжёлая»     | серверная фильтрация (`q`, `class`, `section`) уже есть; массовый выбор по фильтру («выбрать все отфильтрованные») |
| Утверждение программы с сокращением без обоснования       | поле `reduction` в `approve` + предупреждение сервера видно на странице; при пустом обосновании — подтверждение в браузере (как со снятием пункта) |
| Путаница «выбор наборов» между «в наборе» и «в программе» | две разные метки в каталоге и колонка «в программе» у наборов: видно, что попадёт в ревизию |
| Утверждённый набор нельзя менять                          | действия «новая ревизия»/«вернуть ревизию» на странице, а не «тихая» правка |
| Долгие операции планирования                              | их нет: все действия локальные (файлы `acceptance_data/`), стенд не опрашивается — фоновый поток не нужен |
