# 1. Что API стенда называет «моделью» (ответ на вопрос 1)

## 1.1. В API два разных уровня, и пульт показывает только второй

| Понятие в разговоре                      | Что это в API                                                | Где живёт                                                    |
| ---------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| «ML-алгоритм, формирующий модель»        | **архитектура** (`architecture`) — шаблон сети: описание, слои по умолчанию, фазы | `GET /api/ml_models/architectures` → `ModelArchitectureInfo{architecture, description, default_config, suitable_for_phases}` (`client/schemas.py:217`) |
| «Массив параметров и описание структуры» | **модель** — запись реестра: `id`, `file_id` (файл `.h5` с весами), `architecture`, `version`, `name`, `phase_type`, `output_size`, `config` (слои/`compile_config`), `metrics`, `pruning_mask`, `signals` (привязка к устройствам), `signal_aliases` (классы) | `ModelMetadata` (`client/schemas.py:243`), `GET /api/ml_models/models` / `/{model_id}` |

То есть «модель» у стенда — это **экземпляр**: `архитектура + конфиг слоёв + привязка сигналов + файл весов + метрики обучения`. Именно поэтому в реестре имена такие, как `rebalanced-stft_mlp-log1p-add-to-config (trained)`: это не алгоритм, а конкретный экземпляр (я проверил живьём — `architecture = stft_mlp`, а в `config.layers` добавлен слой `Log1p`, `id 92f3cc34…`, метрики — только `testing_history`). Пульт показывает **метаданные**; веса (`file_id` → `.h5`) он не читает, только размер файла из реестра `$Файлов`.

**Живой каталог алгоритмов (снято сейчас, 5 штук):**

| `architecture` | `suitable_for_phases` | Что в `default_config`                                       |
| -------------- | --------------------- | ------------------------------------------------------------ |
| `cnn_1d`       | single, three         | Conv1D×3 + MaxPool + GAP + Dense, `input_shape [2048,6]`, adam/binary_crossentropy |
| `mlp`          | single, three         | Flatten + Dense 256/128/64 + Dropout, `[2048,2]`             |
| `fft_mlp`      | single                | Dense 512/256/128 (he_normal), `[2048,1]`; метрики accuracy+precision+recall |
| `stft_mlp`     | single                | **Log1p** + Dense 64/32/16 + Dropout, `[130,1]`              |
| `transformer`  | single, three         | Conv1D-даунсемплинг + attention (`d_model 64`, heads 4, layers 3); `layers` пуст, параметры в самом конфиге |

Это и есть «список ML-алгоритмов», который вы хотите увидеть, — он отдаётся одной операцией и меняется стендом редко.

## 1.2. Ваш пайплайн по шагам — как он обеспечен в API

| Шаг вашей формулировки                      | Операция API                                                 | Тонкости (проверено)                                         |
| ------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| посмотреть список алгоритмов                | `GET /api/ml_models/architectures`                           | —                                                            |
| создать модель по алгоритму                 | `POST /api/ml_models/models` (`architecture`, `name`, `output_size`, `phase_type`, `signals`, `signal_aliases`, `config`, `pruning_mask`) — «Создает новую модель с заданной архитектурой» | число **групп сигналов обязано совпадать с `output_size`** («Number of signal groups (0) does not match output_size (2)»), `device_id` должны существовать; неизвестная архитектура → ошибка (`TC-MOD-03`); так делает приёмка `tests/integration/test_live_ml.py:334-352` |
| либо взять готовые веса                     | `POST /api/ml_models/models/upload` — «Загружает готовую модель (**например, после сжатия**)»: `.h5` + `metadata` (JSON-строкой) | путь для внешне полученных (урезанных/квантованных) весов    |
| выбрать датасет                             | `GET /api/datasets/`, `GET /api/datasets/{id}`; создать/наполнить — `POST /api/data/file`, `POST /api/datasets/`, `POST /api/datasets/fill/{id}` | `fill` отвечает **202 без `task_id`** — задачу `dataset-fill` находят обходом через `GET /api/tasks/` (уже отражено в `TC-DS-05`) |
| запустить тренировку                        | `POST /api/ml_models/models/{model_id}/train` — «Запускает обучение модели с поддержкой аугментации данных», 202 + `task_id` | тело: `dataset_id`, `epochs` 1…1000, `batch_size` 1…256, `learning_rate` (0…1], `trained_model_name`, `preprocessing_converter`, `augmentation_noise_percentage` 0.001…0.05, `augmentation_num_samples` 1…10, `quantization{enabled,num_bits,symmetric}`; `extra="forbid"` (`client/schemas.py:272`, `client/models.py:253-298`) |
| **дообучить после прунинга**                | Отдельной операции прунинга **в API нет**. `pruning_mask` — поле **создания/загрузки** модели («Маска прунинга (base64)», `docs/SOM1.json:3431`); отдельного `/prune` нет | живьём цепочка ровно такая: `stft-prev2026-pruned-step1` (не обучена, `pruning_mask` = да) → `stft-prev2026-pruned-step1-ft1` (обучена, `original_model_id` = id «step1»). Файл `stft-prev2026-pruned-step1.h5` (136 КБ) лежит в реестре `$Файлов` — то есть **маску/урезанные веса готовят вне стенда, а в API их «материализуют»** через `create` (с `pruning_mask`) или `upload` |
| **дообучить после квантизации**             | Квантизация — **не операция, а параметр обучения** (QAT): `quantization{enabled,num_bits,symmetric}` | живьём: `stft9984-qat-step2` → `stft9984-qat-step2-ft2`, у результата `metrics.quantization = {enabled: True, num_bits: 8, symmetric: True}`, `original_model_id` = id «step2» |
| «не трогать готовые натренированные модели» | `/train` адресуется **модели-основе** и создаёт **новую** запись (`trained_model_name`, а у результата `metrics.original_model_id` = id основы). Боевая модель остаётся нетронутой | во **всех** живых цепочках основой служила модель **без метрик** (не обученная, иногда уже с `pruning_mask`), а обученным результатом становилась новая модель: `skfu-train-dev` → `(trained)`; `-pruned-step1` → `-ft1`; `-qat-step2` → `-ft2` |

**Честный пробел (нужен вопрос разработчикам стенда).** Контракт не описывает, **наследует ли `/train` веса модели-основы** (то есть является ли это «дообучением» в строгом смысле или обучением с нуля на её конфиге). Единственное явное высказывание о наследовании весов в спецификации относится к AutoML/NAS: «Веса базовой модели НЕ наследуются… это поиск архитектуры (NAS) вокруг её конфига, а не дообучение» (`docs/SOM1.json:1454`). Ни в живых данных, ни в контракте нет примера вызова `/train` **на уже обученной** модели — все основы в цепочках были без метрик. Поэтому пункт «дообучить натренированную модель» я предлагаю уточнить у вендора (вопрос 2 в таблице).

# 2. Почему в разделе нет выбора датасета (ответ на вопрос 2)

**Задумано так, и это ровно этап Э2.** Факты:

* Шаг «Данные (датасет)» в интерфейсе помечен `этап Э2`, а в шагах он показывается с честной подписью «загрузка файлов и наполнение датасета — этап Э2» (`pult/view.py:1784-1832`, `pult/web/index.html:456-612`). Пикера нет намеренно, чтобы незаполненная форма не выглядела сломанной.
* При этом **серверная половина уже работает**: `GET /api/train` отдаёт список датасетов (`train_view(... datasets=…)` → поле `datasets` с `value`/`label`, `pult/view.py:1880-1886`), а `POST /api/train {action:"choose", kind:"dataset", id, label}` записывает `dataset_id`/`dataset_label` в профиль сессии — это покрыто тестами (`tests/unit/test_pult_server.py:2121-2129`). В JS эти `datasets` пока не рисуются, и обработчик `choose kind=dataset` из UI не вызывается (есть только `kind:"model"`, `app.js:2136-2146`).
* Кроме id датасета профилю нужна ещё отметка «датасет валидирован вне пульта» (`dataset_validated` / `dataset_validated_at`) — без неё шаг не станет «готов». Это тоже Э2.

Итого: датасет можно выбрать уже сейчас (через API), но осмысленный выбор датасета — вместе с его происхождением, составом и подтверждением — появляется в Э2. Добавлять «половинчатый» селект без паспорта датасета смысла нет.
