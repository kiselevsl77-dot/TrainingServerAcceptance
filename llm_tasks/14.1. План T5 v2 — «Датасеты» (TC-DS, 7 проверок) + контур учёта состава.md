# План T5 v2 — «Датасеты» (`TC-DS`, 7 проверок) + контур учёта состава

## 1. Принятое решение

Полный контур сразу: **провайдер состава с 4 режимами**, локальный факт при `fill`, sidecar + схема сессии v5, эвристика, анализ пересечений/дублей, раздел отчёта, capability-aware `TC-DS-03`, тесты на все режимы. Ключевой принцип: экран/отчёт не спрашивают «есть ли состав», а получают его у провайдера **вместе с ярлыком происхождения** — поэтому появление серверного эндпоинта не потребует ни переписывания UI, ни новых id проверок.

## 3. Контур состава — интерфейс

```python
# acceptance/dataset_composition.py
SOURCE_SERVER = "server"        # после доработки API — эталон
SOURCE_LOCAL_FACT = "local"     # мы сами отправляли fill: точный состав
SOURCE_HEURISTIC = "heuristic"  # наполнено вне пульта: гипотеза
SOURCE_UNKNOWN = "unknown"      # данных нет — честное «состав недоступен (P1)»

def server_composition(apis, dataset_id) -> DatasetComposition | None   # endpoints.find("get /api/datasets/{dataset_id}/summary")
def record_fill(session, *, dataset_id, raw_file_ids, markup_file_ids, task_id="", task_status="", operator="", note="") -> DatasetComposition
def read_composition(session, apis, dataset_id, *, mode="auto", allow_heuristic=True) -> DatasetComposition
def compare(server: DatasetComposition, local: DatasetComposition) -> dict[str, Any]   # расхождения → новое замечание
def overlap_report(compositions, files) -> dict[str, Any]  # пересечения по dataset_id; повторы file_name+size с разными id; префиксы s3_path
def save_store(records, path=None) / load_store(path=None)   # acceptance_data/dataset_composition.json
```

Сессия: `SCHEMA_VERSION = 4 → 5`, поле `dataset_composition: list[dict]`, строка истории версий про v5; файлы v1–v4 читаются как раньше (отсутствующее поле → пустой список).

## 4. Семь проверок `TC-DS`

| id       | automation               | Класс     | Ядро сценария                                                | Критерий                                                     |
| -------- | ------------------------ | --------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| TC-DS-01 | `datasets.create`        | live      | `POST /api/datasets/` `__TEST__<uuid>`, `type=direct_fill`; `add_test_entity` | 201, `id`+`creation_date`, тип верен                         |
| TC-DS-02 | `datasets.list`          | tech      | `GET /api/datasets/`: `datasets`+`count`, фильтры `name`/`description`/`type`/`creation_date` | ответ согласован, фильтры отвечают (расхождения → замечание, не отказ) |
| TC-DS-03 | `datasets.meta`          | tech      | **capability-aware**: есть `summary` → строгая сверка состава; нет → «успех» + замечание P1 + `source` в evidence | состав либо проверен, либо зафиксировано его отсутствие      |
| TC-DS-04 | `datasets.update`        | live      | `PUT` (name/description) → `GET` подтверждает; `updated_at` нет | изменения видны, отсутствие `updated_at` — замечание         |
| TC-DS-05 | `datasets.fill`          | **heavy** | `__TEST__` датасет → 1 пара RAW+markup (параметр `fill_pairs`) → `fill` → 202 → `monitor.find_recent("dataset-fill")` → `register_task` → до терминального статуса → запись состава `local`, удаление датасета | 202 + задача найдена и отслежена + состав зафиксирован + самоочистка |
| TC-DS-06 | `datasets.fill_contract` | tech      | несуществующий `dataset_id` → 404/422; тело без `raw_file_ids` → 422 | валидация понятна, 5xx нет                                   |
| TC-DS-07 | `datasets.delete`        | live      | `DELETE` → `GET` → 404/not found; `mark_test_entity_deleted` | удаление подтверждено, учёт закрыт                           |

Окна `TC-DS-05`: поиск задачи ≤30 с, ожидание статуса ≤10 мин (в юнит-тестах — нулевые; проверяются оба исхода: «найдена» и «не найдена»).
