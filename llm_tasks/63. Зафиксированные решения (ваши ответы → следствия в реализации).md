# 2. Технические находки последней разведки (влияют на план)

| Находка                                  | Факт                                                         | Следствие                                                    |
| ---------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **Multipart в пульте не поддерживается** | `pult/server.py:2221 _body()` читает `Content-Length` и делает `json.loads`; разбора `multipart/form-data` в `pult/` нет вообще | нужен **новый потоковый разбор multipart** в обработчике (читать `rfile` частями, писать во временный файл) |
| **`MAX_BODY = 1 << 20`** (1 МБ)          | `pult/server.py:87`                                          | загрузка идёт **мимо** этого лимита, со своим `MAX_UPLOAD` и честной ошибкой 413 |
| **RAW-файлы огромные**                   | реестр сейчас: RAW 181 файл — медиана **2,5 МБ**, максимум **2,18 ГБ**; LOADS — медиана 7 КБ, максимум 18,5 МБ; H5 — до 0,37 МБ | байты в JSON исключены (base64 + 2 ГБ = память) → **streaming**: браузер → пульт (поток во временный файл) → стенд (httpx с файловым объектом, без чтения в память). Прогресс — в браузере (`xhr.upload.onprogress`) |
| **Клиент читает файлы в память**         | `client/files.py:61 upload(content: bytes)`, `client/models.py:124 upload_model(content: bytes)` | расширить: принимать путь/поток (обратная совместимость с `bytes` сохраняется) + тесты |
| **Фоновый слой уже есть**                | `pult/jobs.py`: одно активное задание, `Job(check_id, action, label, params)`, `work() → rows/verdict/journal`, панель опрашивает `/api/jobs` | обучение/`check`/`fill` ведём **через этот слой**, не изобретая второй (задание помечаем `K2-TRAIN`, `K2-CHECK`, `K2-FILL`) |
| **Схема сессии**                         | `acceptance/session.py:30 SCHEMA_VERSION = 9`                | Э2/Э3 добавляют `dataset_manifests`, `flow_steps`, `base_model_id`, `trained_model_id`, `quality_metrics` → **v10**; обновить `README.md` (там `v9`, а в таблице файлов вообще устаревшее «схема v8») |
| **Отдача файлов оператору**              | `Raw(download=True)` + `_download_onnx`/`_download_file` (`pult/server.py:1472,1481`) | переиспользуем для `.h5` и `.onnx`                           |
| **Ограничение стенда для Э3**            | `POST /train` отвечает 200/202 и создаёт задачу, но воркер очередь не разбирает (runtime `new`) | приёмку Э3 строим вокруг поведения очереди, не «по времени»  |

# 3. План работ

## Э2.1 — данные (файлы и датасет)
1. `pult/uploads.py` (новый, чистый модуль): потоковый разбор `multipart/form-data` → временный файл, лимит `MAX_UPLOAD`, безопасное имя, MIME (`text/csv` для `.csv` — иначе стенд отвечает `400 Only CSV files are allowed`).
2. `pult/server.py`: `POST /api/data/files` (multipart, RAW/LOADS, описание) и `POST /api/data/files/delete` (уборка ошибочно залитого); расширить клиент `client/files.py` на поток.
3. `POST /api/datasets`: `create` (имя/описание), `fill` (пары RAW+LOADS → 202 **без** `task_id`, задачу ищем через `GET /api/tasks/`), `refresh` (состав/статистика), `delete`; `GET /api/datasets/{id}` — состав.
4. UI: зона «Данные (датасет)» — загрузка файлов с прогрессом, таблица «что залито», создание датасета, наполнение, ожидание `dataset-fill`, снимок состава, чекбокс-подтверждение «датасет проверен вне стенда» (теперь со ссылкой на первоисточник: 1.2 — «средствами комплекса достоверность разметки не проверяется, признак “датасет проверен” не ведётся»).
5. Сессия: `dataset_manifests` (файлы, размеры, `sha256`, число записей) и шаги в `flow_steps`; схема → **v10**.

## Э2.2 — модель (алгоритм или готовая `.h5`)
6. `GET /api/architectures` — каталог 5 алгоритмов с составом слоёв/фазами (для `fft_mlp`/`stft_mlp` фаза принудительно `single`; в UI это подписано).
7. `POST /api/models`: `create` (архитектура + имя + `output_size` + **сигналы и классы копией с выбранной модели-образца**) и `upload` (готовый `.h5` + metadata, `pruning_mask` опционально); проверки до отправки: групп сигналов = `output_size`, `device_id` существуют в `$Нагрузки`.
8. UI: зона «Модель-основа» — каталог алгоритмов, «Создать из алгоритма», «Загрузить готовую `.h5` (после сжатия/прунинга)», выбор модели-основы для обучения.

## Э3 — обучение и обязательная проверка
9. `POST /api/models/{id}` `action=train` — полный набор (`epochs`, `batch_size`, `learning_rate`, `preprocessing_converter`, аугментация, **`quantization` QAT 4/8 бит**, `trained_model_name`), запуск через `pult/jobs.py`, наблюдение задачи FSM-1.
10. `action=check` — **обязательный** следующий шаг; без него «принять показатели качества» заблокировано (1.7 §3.8).
11. Метрики «до/после»: `testing_history` основы и результата (на одном датасете и пороге — 1.2 §3.5.8, 1.7 §4.3.3); запись решения в сессию (`quality_metrics`), в отчёт — с подписью «дообучение: создана новая версия, исходная не изменена».

## Э4 — результат оператору
12. `GET /api/models/{id}/h5` и `GET /api/models/{id}/onnx` — скачивание в браузер (`Raw`), проверка целостности (размер/сигнатура), `GET /api/bundle` — комплект (`h5 + onnx + metrics.json + состав датасета + карточка прогона`).

## Э5 — полная нагрузка и приёмка
13. Правила боевых имён (двойное подтверждение + запись в сессию), правка `docs/12` §24.2 и §28.3–§28.4 (формулировки «метрики — только после проверки», «дообучение → новая версия») со ссылками на первоисточники (1.2 §3.5.8, 1.4 §7.3.6, 1.7 §3.8/§4.2.8/§4.3.3), живая приёмка К2 на боевом датасете.

# 4. Риски, о которых честно предупреждаю

* **Загрузка 2 ГБ** — самый дорогой пункт Э2: длительная операция в одном HTTP-запросе пульта. План: потоковая запись во временный файл, прогресс в браузере, лимит по размеру, понятная ошибка; при обрыве — временный файл удаляется и в сессию пишется факт неудачи.
* **Очередь стенда** — `training`-задача может остаться в `new`: приёмка Э3 проверяет «задача создана и отслеживается», а не «модель обучена за N минут».
* **Статус задачи `fill` без `task_id`** — наполнение отслеживаем обходным путём через `GET /api/tasks/` (как в `TC-DS-05`).
* **Путаница «сигнал»** — в UI пишем «выход модели ↔ устройства учёта», никогда не «каналы АЦП»; каналы (`U_A…I_C`, 2048 отсчётов) упоминаются только в контексте инференса.
