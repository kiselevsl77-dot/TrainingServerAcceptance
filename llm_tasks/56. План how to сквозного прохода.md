# Черновик how-to

## 0. Когда нужен этот путь

Нужен **не протокол приёмки**, а результат: загрузить данные, выбрать/создать модель, обучить, протестировать, получить ONNX.

От приёмки отличается объёмом: гонять 69 проверок и заполнять печатную форму не нужно — достаточно «мини-программы» из 6–10 пунктов (см. §9). Сессию пульта **всё равно стоит создать**: без неё некуда записать решение по артефактам (обученная модель в отчёт не попадёт).

## 2. Шаг 1. Датасет: закачать или выбрать

| Что у вас есть                                             | Что делать                                                   |
| ---------------------------------------------------------- | ------------------------------------------------------------ |
| Готовый датасет стенда (например `skfu-train` — 104 файла) | Ничего не загружать: выбрать его в карточке запуска (в пульте это селект «Датасет для проверки») |
| Свои RAW+markup и нужен **свой** датасет                   | Загрузить файлы и наполнить датасет — по коду, потому что **в интерфейсе пульта загрузки файлов и создания датасета нет** (в MVP 6 вкладок; это осознанное упрощение) |

Загрузка и наполнение (равноценно «Консоль запросов»/скрипт):

```python
from pathlib import Path
from client.settings import load_settings
from acceptance.api import Apis, build_client
from acceptance.http_log import Journal

settings = load_settings()
apis = Apis.build(build_client(settings, Journal(max_records=500)))

raw = apis.files.upload(  # POST /api/data/file
    file_name="__TEST__my_run_001.raw.csv",
    content=Path(r"D:\data\001.raw.csv").read_bytes(),
    file_type="RAW",  # RAW | LOADS | ONNX (маркер пары даёт имя файла)
    description="рабочий прогон: обучение",
)
markup = apis.files.upload(
    file_name="__TEST__my_run_001.markup.csv",
    content=Path(r"D:\data\001.markup.csv").read_bytes(),
    file_type="RAW",
)

dataset = apis.datasets.create_dataset(  # POST /api/datasets/
    name="__TEST__my_run",
    description="рабочий прогон: обучение",
)
apis.datasets.fill_dataset(  # POST /api/datasets/fill/{id} (async, 202)
    dataset.id,
    raw_file_ids=[raw.id],
    markup_file_ids=[markup.id],
)
```

Важно: RAW и markup стенд сопоставляет **по имени файла** (`<имя>.raw.csv` + `<имя>.markup.csv`), а не по типу. Наполнение **необратимо** (API не умеет вынимать файл из датасета) — наполняйте только `__TEST__`-датасеты.

## 3. Шаг 2. Модель: выбрать или создать

* **Выбрать** существующую — в пульте селект «Модель» (список из `GET /api/ml_models/models`); скриптом `apis.models.list_models(name=…, architecture=…)`.
* **Создать свою** (рекомендуется, чтобы обучение не касалось боевой модели) — рецепт проверен на живом стенде:

```python
template = next(m for m in apis.models.list_models() if m.metrics)  # образец: модель с метриками
card = apis.models.get_model(str(template.id))

groups: dict[str, list[str]] = {}  # карточка отдаёт список (signal_num, device_id),
for item in card.signals or []:  # а на создание нужен словарь «группа → устройства»
    groups.setdefault(str(item["signal_num"]), []).append(str(item["device_id"]))

base = apis.models.create_model(  # POST /api/ml_models/models
    architecture=str(card.architecture),
    name="__TEST__my_run_base",
    output_size=int(card.output_size or 2),
    phase_type=str(card.phase_type or "single"),
    signals=groups or None,
    signal_aliases=dict(card.signal_aliases or {}) or None,
)
```

* **Загрузить готовый `.h5`**: `apis.models.upload_model(file_name=…, content=…, name="__TEST__…", output_size=…)` (в пульте — проверка `TC-MOD-04`).
* Каталог архитектур: `apis.models.list_architectures()` (в пульте — `TC-MOD-01`).

## 4. Шаг 3. Обучение

**Путь «пульт»** (ничего программировать не нужно):

1. Вкладка **«Планирование»** → набор (например «ML-прогон») → добавить пункты: `TC-TR-01`, `TC-TR-02`, `TC-TR-04`, `TC-TR-05`, `TC-TR-06`, `TC-INF-02`, `TC-INF-04`, `TC-CLEAN-01`, `TC-CLEAN-04` → утвердить набор и программу.
2. Вкладка **«Прогон»** → режим «только невыполненное» → карточка запуска для `TC-TR-02`:

| Поле карточки                                    | Что вписать                                                  |
| ------------------------------------------------ | ------------------------------------------------------------ |
| Датасет для проверки                             | ваш датасет (`skfu-train` или `__TEST__my_run`)              |
| Модель                                           | ваша `__TEST__`-модель                                       |
| Эпох обучения / Размер батча / Скорость обучения | 3 / 32 / 1e-7 (по умолчанию спецификации: 50 / 32 / 1e-7)    |
| Оставить результат обучения артефактом           | **да** — иначе сценарий уберёт модель за собой (`NFR-T4`)    |
| Ответственный, «Что делать с артефактами»        | обязательны; «выгрузить в доказательства» = сохранить модель + решение «в артефакты» |
| Подтверждаю расход ресурсов                      | галочка (класс `heavy`)                                      |

3. «**▶ Подтвердить и запустить**» (или «**▶ Следующая (фоном)**» — ответ сразу, прогресс на вкладке «Задачи»).
4. Вкладка **«Задачи»**: карточка задачи, статус FSM-1 (`new → … → completed`), команды пауза/возобновить/прервать; ниже — панель «Артефакты ресурсоёмких проверок».

**Путь «скрипт»**:

```python
answer = apis.models.train(  # POST /api/ml_models/models/{id}/train
    str(base.id),
    dataset_id=str(dataset.id),
    epochs=3,
    batch_size=32,
    learning_rate=1e-7,
    trained_model_name="__TEST__my_run_trained",
)
task_id = str(answer.task_id)  # операция асинхронная: ждём задачу
```

Ожидание задачи (FSM-1) — потому что ответ приходит сразу, а обучение идёт минутами:

```python
import time

terminal = {"completed", "finished", "failed", "error", "cancelled", "revoked"}
for _ in range(60):  # 60 × 15 с = 15 минут
    task = apis.tasks.get_task(task_id)
    data = task.model_dump(mode="json") if hasattr(task, "model_dump") else dict(task)
    status = str(data.get("status") or "")  # у рантаймов статус лежит в data["runtimes"]
    if status in terminal:
        break
    time.sleep(15)
trained = [m for m in apis.models.list_models() if str(m.name) == "__TEST__my_run_trained"]
```

**Живой факт стенда (01.10.2026):** `POST /train` вернул `200` за 4,8 с, задача типа `training` создалась, но рантайм оставался в `new` 9 минут — стенд принимает обучение, но очередь не разбирает. Это замечание к стенду, а не ошибка пульта: пункт `TC-TR-02` в таком случае получает **примечание** «задача не завершилась», а не отказ.

## 5. Шаг 4. Тест модели

| Что проверить                            | Пульт       | Скрипт                                                     |
| ---------------------------------------- | ----------- | ---------------------------------------------------------- |
| Метрики, версия, `updated_at` результата | `TC-TR-04`  | `apis.models.get_model(id).metrics`                        |
| Проверка модели по датасету (async)      | `TC-TR-05`  | `apis.models.check_model(id, dataset_id=…, threshold=0.5)` |
| Инференс по датасету (async)             | `TC-INF-01` | `apis.models.inference(id, dataset_id=…, threshold=0.5)`   |
| Один сэмпл (sync, Base64-сигналы)        | `TC-INF-02` | `apis.models.inference_single(id, sample=…)`               |
| Границы `threshold` 0.0/1.0              | `TC-INF-03` | то же с `threshold=0.0` и `1.0`                            |
| Повторяемость результата                 | `TC-INF-04` | два вызова, сравнить `classes[]`                           |

Сэмпл для `inference/single` собирается из строки RAW-файла (`acceptance.ml_samples.parse_raw_sample`): шесть Base64-сигналов (`U_A_signal`…`I_C_signal`) + шкалы (`U_mult`, `U_dev`, `I_mult`, `I_dev`, `byte_order`, `signal_bytes`). Пункт `TC-INF-02` по умолчанию берёт **самый маленький RAW с ASCII-именем**; нужен конкретный файл — впишите `file_id`/`sample_file_id` в карточке. Успех = `classes[]` с `signal_num`, `device_ids`, `confidence`, `detected`.

## 6. Шаг 5. ONNX: конвертация и скачивание

Конвертацию делает **стенд** по запросу `GET /api/ml_models/models/{model_id}/download_onnx` (отдаёт `application/octet-stream`, `Content-Disposition`, `Content-Length`; `Range` не поддерживает).

| Способ                    | Как                                                          |
| ------------------------- | ------------------------------------------------------------ |
| Пульт, «по-испытательски» | пункт `TC-TR-06` в программе: скачивает файл, считает `sha256`, проверяет имя/размер/заголовки и **кладёт файл в доказательства** `acceptance_data/artifacts/` (имя из ответа, например `stftspike-qat-step2.onnx`) |
| Пульт, «по-рабочему»      | вкладка «Задачи» → «Артефакты ресурсоёмких проверок»: у **файла** `.onnx`/`.h5` кнопка «💾 в артефакты» сразу выгружает его в `acceptance_data/artifacts/`; у **модели** «💾 в артефакты» оставляет её на стенде, «🗑 удалить» убирает со стенда |
| Скрипт                    | `payload = apis.models.download_onnx(id)` → `payload.content` / `file_name` / `size` |

```python
import hashlib
from pathlib import Path

payload = apis.models.download_onnx(str(trained[0].id))
target = Path("acceptance_data/artifacts") / (payload.file_name or "model.onnx")
target.parent.mkdir(parents=True, exist_ok=True)
target.write_bytes(payload.content)
print(target, payload.size, hashlib.sha256(payload.content).hexdigest())
assert payload.size > 0 and b"onnx" in payload.content[:4096]
```

Альтернативно файл можно взять из реестра: `apis.files.list_files(file_name=".onnx")` → `apis.files.download(id)`.

## 7. Шаг 6. Уборка и фиксация

1. `TC-CLEAN-01` — самоочистка: незакрытых `__TEST__`-сущностей в сессии и реестрах не осталось.
2. Решение по каждому оставленному объекту — панель артефактов (`TC-CLEAN-04`): когда она пишет «решения есть у каждого объекта», проверку можно ставить.
3. Если нужен отчёт: вкладка «Результаты» → «Собрать отчёт»; комплект — `acceptance_data/reports/` (md + json + csv), выгрузки — `acceptance_data/artifacts/`.
4. Артефакты не удалять до подписания отчёта — они перечислены в разделе 8 отчёта.

## 8. Подводные камни (живые факты)

| Симптом                                                      | Причина и что делать                                         |
| ------------------------------------------------------------ | ------------------------------------------------------------ |
| `400 Number of signal groups (0) does not match output_size (2)` при обучении | у базовой модели не заполнены `signals`; задайте группы, число групп = `output_size` |
| Обучили «не ту» модель / «не на том» датасете                | без явного выбора пульт берёт **первую подходящую** сущность реестра (`pick_dataset`/`pick_model`): всегда заполняйте «Датасет» и «Модель» в карточке |
| `fill` вернул 202, а задачи нет                              | `fill` не отдаёт `task_id` — искать задачу `dataset-fill` в `GET /api/tasks/` |
| Задача обучения «висит» в `new`                              | стенд не исполняет очередь (см. §4) — фиксируйте замечание, не считайте отказом пульта |
| Удалили модель, а `.h5` остался                              | каскад не гарантирован (`TC-MOD-07`): проверьте реестр файлов и решите судьбу файла отдельно |
| Скачивание падает на не-ASCII имени                          | известный дефект P0; берите файлы с ASCII-именами, `Range` сервер не поддерживает — файл отдаётся целиком (RAW до 2,1 ГБ) |
| Датасет стал «неисправимым»                                  | наполнение необратимо — только `__TEST__`-датасеты           |
| «Маршрут `GET /api/artifacts` не найден» при живом пульте    | на порту остался старый процесс пульта (Windows разрешает `SO_REUSEADDR`): поднимайте на свободном порту |

## 10. Готово, если…

- модель-результат есть в реестре (`GET /api/ml_models/models?name=…`), у неё заполнены `metrics` и обновился `updated_at`;
- проверка/инференс дали `classes[]` с `confidence` (и повторились при втором вызове);
- файл `.onnx` получен: `size > 0`, имя оканчивается на `.onnx`, есть `sha256` — лежит в `acceptance_data/artifacts/`;
- в сессии есть записи: созданные/удалённые `__TEST__`-сущности, решение по каждому оставшемуся артефакту;
- `TC-CLEAN-01` подтверждает отсутствие следов, а панель артефактов — «решения есть у каждого объекта».

PS

Обращаю внимание, что нужно разделить контексты:

1) Сплошной проверки с минимальной нагрузкой на сервер (в рамках этого контекста ты рассуждаешь)
2) Сквозной проверки с реальной нагрузкой на сервер и реальными результатами.

Во втором случае важно не просто, чтобы был какой-то датасет, а нужен вполне конкретный, валидированный датасет. И расход ресурсов тут не важен, для достижения нужных метрик качества получаемой модели нужно будет закачать на сервер текущий "боевой" датасет.

И модель нужно будет выбрать не абы какую, а вполне конкретную. Сейчас, кстати, посмотреть свойства моделей (как я понял), можно только в ленте открыв то, что вернул вызов get models.

Если сейчас функционал пульта не позволяет сделать сквозной прогон [закачать датасет - выбрать модель - обучить модель - получить метрики - конвертировать в ONNX - скачать ONNX], то нужно его запланировать и добавить.
