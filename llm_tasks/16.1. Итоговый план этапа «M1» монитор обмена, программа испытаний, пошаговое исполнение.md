# Итоговый план этапа «M1»: монитор обмена, программа испытаний, пошаговое исполнение

## Модель (вариант C) — `acceptance/plan.py` + `acceptance/plan_runner.py`

**Домен плана (без UI, полностью тестируемый):**
* `PlanItem` — два уровня в одном списке: `level = check | call`, `item_id` (`TC-FILE-01` / `TC-FILE-01#2`), `parent_id`, `title`, `group`, `module`, `check_class`, `endpoint_key` (ключ реестра или `probe`), `method`, `path`, `safety`, `body_kind`, `params` (значения path/query/тела; источник — пикер или сценарий), `expected` (правило ожидания + текст проверки), `enabled` (галочка), `status`, `verdict`, `journal_from/to`, `duration_ms`, `started_at/ended_at`, `note`.
* `build_plan(specs)` — пункт на каждую проверку каталога + по одному дочернему пункту на её `CheckSpec.endpoints` (сопоставление со `EndpointSpec` реестра `acceptance/endpoints.py`) и на `probe_paths` (негативные пробы, помечены «маршрута нет в спецификации»). Порядок — как в `catalog.PLANNED_GROUPS`, что совпадает с §15 «Порядок выполнения» `docs/02`.
* Правила галочек: снятие проверки снимает её вызовы; включение вызова включает проверку; массовые действия «✔ включить всё в выборке / ✖ снять всё в выборке» работают по текущему фильтру (это и есть «снять галочку имеющимся фильтром» из пожелания).
* Вердикты: уровень «вызов» — правило по классу безопасности + ожиданию проверки (`read`/`write` → 2xx, `heavy` → 202 и `task_id`, пробы → допустимый набор 404/405/422); уровень «проверка» — статус движка (`CheckStatus`), как сейчас, единственный источник — `session.checks`; при исполнении «по вызовам» вердикт проверки пишется отдельно (`plan_verdict`) и в отчёте показывается оба, чтобы не подменять сценарный вердикт.
* `PlanState` — `items`, указатель «следующий», `exec_mode` (`check`/`call`), `pause_seconds`, `auto` (идёт/стоп + причина останова); сериализация в сессию → **схема v6** (`plan`, `plan_runs`: режим, состав включённого/снятого, вердикты, ссылки на номера журнала), миграция аддитивная, как v1→v5.

**Исполнитель (без UI):**
* `execute_item` — для пункта-проверки переиспользует существующий путь (`check_run.run_check` → `runner.automate`); для пункта-вызова — `execute_request` по шаблону реестра с меткой `TC-…` (журнал/JSONL — как сейчас); после прогона проверки дочерние пункты закрываются по фактическим обменам (метка + `journal_from/to`), поэтому двойного исполнения нет.
* Остановы авто-прогона: пункт `live`/`heavy` без заполненной карточки запуска (NFR-T4/FR-T10), сетевая ошибка, конец плана, кнопка «⏸ Стоп».
* Авто-исполнение с паузой — `st.fragment(run_every=pause_seconds)`: один пункт на тик, без фоновых потоков (Streamlit 1.64 в проекте это поддерживает, `session_state` доступен, состояние сохраняется в сессии).

## Риски и оговорки
* Правки `docs/01`, `docs/02` (FR-T4/FR-T6, §15) живут в копии и перезаписываются `sync_docs` — их нужно внести и в основной репозиторий `TrainingServerUI/context/01. Постановка/…`; иначе они исчезнут.
* Добавление заголовков в `HttpExchange` меняет формат `http_request`/`http_response` в JSONL сессии и в отчёте (обратная совместимость чтения сохраняется; `REPORT_VERSION` растёт только из-за нового раздела плана).
* Повтор multipart-вызова из монитора невозможен без повторного выбора файла — ограничение зафиксирую в UI и руководстве.
* Смоук-тесты авто-паузы: `run_every` проверяется подменой фрагмента (не реальным ожиданием), чтобы тесты не тормозили.
