## Итоговый состав этапа T3 (после уточнения)

### Боевые проверки TC-FILE-11/12/13 — автоматизируем с самоочисткой
- **Класс:** `live` → запуск только через карточку (`ui/common/run_card.render_run_card` + `engine.check_confirmation`), в доказательствах фиксируется `goal`/`data`/`responsible`/`confirmed` (FR-T10, NFR-T4).
- **Обязательные правила (NFR-T4, §9 ТЗ):**
  * имя файла только `__TEST__…` (проверяется в сценарии до запроса, иначе «отказ» без создания сущности);
  * `file_type=RAW` + `description` с меткой проверки;
  * самоочистка обязательна: `DELETE /api/{file_id}` в `finally`-блоке сценария; если удаление не удалось — статус «отказ» + авто-замечание, а факт остаётся в доказательствах;
  * каждая сущность пишется в `session.counters["test_entities"]` (`id`, тип, действие `создан`/`удалён`, время, `check_id`) — вход для TC-CLEAN-01/02 в T9 (схема сессии остаётся v4, миграции нет);
  * запись в `session.history` событиями `test_entity_created` / `test_entity_deleted`.
- **Что проверяют:**
  * TC-FILE-11 — загрузка CSV `__TEST__` → 201, метаданные (`id`, `file_name`, `file_type`, `size`, `import_date`), файл виден в реестре фильтром `id`;
  * TC-FILE-12 — повторная загрузка того же имени → второй файл (реестр допускает дубли имён; фиксируется как факт) + правка не предусмотрена API → результат фиксируется замечанием, если поведение расходится;
  * TC-FILE-13 — круговой рейс: `upload → download → сверка байт (размер + sha256) → delete`; отдельно фиксируется `Content-Type`/`Content-Disposition` из ответа скачивания.
- **Тесты:** unit — мок-стенд с «сломанным» удалением (409/500, проверка «отказ + замечание») и с корректным удалением (проверка «успех + запись в `test_entities` + ноль `__TEST__`-файлов в реестре»); integration — только при `PULT_LIVE_WRITE=1`, с проверкой, что после прогона фильтр `file_name=__TEST__` пуст.
