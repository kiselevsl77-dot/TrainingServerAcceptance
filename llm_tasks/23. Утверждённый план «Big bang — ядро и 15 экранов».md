### 3.1. Ревизия разреза: без пакета `core/`

Раздел 3 вводил пакет `acceptance/core/**`. При инвентаризации выяснилось, что переиспользуемые
слои (`checks/**`, `tasks_monitor.py`, `records.py`, `dataset_composition.py`, `exchange.py`,
`http_log.py` — всего ~40 модулей и тестов) импортируют `acceptance.session` и
`acceptance.plan` **напрямую**. Перенос в пакет `core/` — это механические правки импортов
в десятках файлов без выигрыша в архитектуре. Поэтому новые модули кладём **плоско**:

| Новый модуль | Заменяет | Оценка объёма |
|---|---|---|
| `acceptance/sets.py` | — (новое: библиотека наборов, `SCR-14`) | ~320 строк |
| `acceptance/programme.py` | часть `plan.py` (`PlanState`, `build_plan`, галочки) | ~380 строк |
| `acceptance/queue.py` | часть `plan.py` (пункты, указатель, статусы) + `plan_runner.py` | ~300 строк |
| `acceptance/runner.py` | `plan_runner.py` (исполнение, пачка tech, авто) | ~400 строк |
| `acceptance/results.py` | часть `session.checks` + история повторов | ~160 строк |
| `acceptance/report.py` | `report.py` (раздел «Программа и объём», `programme.csv`) | 1 026 → ~1 050 |

Удаляем на этапе 2: `acceptance/plan.py`, `acceptance/plan_runner.py`,
`acceptance/ui/common/plan_panel.py`, `acceptance/ui/pages/**`, `tests/unit/test_plan*.py`.

## 4. Данные: схема сессии v7 и общая библиотека наборов

### 4.1. Сессия (`sessions/<id>.json`, `SCHEMA_VERSION = 7`)

Добавляется (остальные поля — как в v6, без изменений):

```jsonc
{
  "programme": {
    "items": [                      // программа сессии (SCR-15); порядок = порядок прогона
      {"check_id": "TC-SYS-01", "order": 1, "mandatory": true,
       "sources": [{"set_id": "SET-SYS", "revision": 1}]}   // происхождение: слияние по ИЛИ
    ],
    "revision": 3,                  // номер ревизии (растёт при каждой правке состава)
    "status": "черновик",           // черновик | утверждена
    "approved": {"revision": 3, "by": "…", "at": "…", "comment": "…", "reason": ""},
    "updated_at": "…"
  },
  "queue": {                        // очередь прогона (SCR-05) — снимок утверждённой ревизии
    "revision": 3, "created_at": "…", "pointer": 0,
    "items": [
      {"check_id": "TC-SYS-01", "order": 1,
       "state": "ожидает",          // ожидает | выполняется | выполнена | снята
       "reason": "", "note": "", "journal_from": null, "journal_to": null}
    ]
  },
  "check_history": { "TC-SYS-01": [ {"status": "успех", "verdict": "…", "at": "…"} ] }
}
```

Поле `plan` (v6) удаляется вместе со старым UI на этапе 2; миграции нет, файлы v6 не читаем.

| Поле | Назначение | Требование |
|---|---|---|
| `programme.items[].sources` | происхождение: из каких наборов и ревизий пришла проверка | `FR-P-65…70` |
| `programme.revision` / `status` / `approved` | ревизии и утверждение программы | `AC-P-25…27` |
| `queue` | снимок утверждённой ревизии: прогон не меняет программу | `IR-P-18` |
| `queue.items[].state` / `reason` | «снято с причиной» — это результат, не правка состава | `FR-P-66` |
| `check_history` | история повторов проверки | `DR-P-5` (единый след результата)

### 4.2. Библиотека наборов (`acceptance_data/check_sets.json`, схема 1)

Наборы — **общие** данные пульта (шаблоны, переиспользуются сессиями), поэтому живут
отдельным файлом по образцу `records_overrides.json` (модуль `acceptance/sets.py`):

```jsonc
{
  "schema_version": 1,
  "sets": [
    {"set_id": "SET-SYS", "title": "System — полный объём раздела", "section": "TC-SYS",
     "scope": "полный",              // смоук | стандарт | полный (FR-P-65)
     "status": "черновик",           // черновик | утверждён (FR-P-67)
     "author": "", "revision": 2, "created_at": "…", "updated_at": "…", "note": "",
     "items": [{"check_id": "TC-SYS-01", "order": 1, "mandatory": false}],
     "revisions": [{"revision": 1, "at": "…", "author": "…", "comment": "…",
                    "title": "…", "section": "TC-SYS", "scope": "полный", "items": [...]}]}
  ]
}
```

Стартовое наполнение (`library_from_catalog()`): по набору на каждый **наполненный**
раздел каталога (`SET-SYS`, `SET-FILE`, `SET-REC`, `SET-LOAD`, `SET-TASK`, `SET-DS`)
плюс `SET-SMOKE` «Смоук-минимум» — по одной первой `tech`-проверке раздела, все пункты
с признаком `mandatory` (`FR-P-70`).

### 4.3. API модулей ядра: что уже реализовано (этап 1a)

```
acceptance/sets.py
  SetItem(check_id, order, mandatory)                 SET_DRAFT / SET_APPROVED
  SetRevision(revision, at, author, comment,          SCOPE_SMOKE/STANDARD/FULL,
              title, section, scope, items)           SMOKE_SET_ID, section_options
  CheckSet(set_id, title, section, scope, status,     section_title / section_totals
           author, revision, note, items, revisions)  suggested_set_id
    .add / .remove / .replace_all / .set_mandatory    sets_path / load_sets / save_sets
    .move / .reorder / .rename / .set_section         library_from_catalog
    .snapshot / .archive / .revise / .reopen          smoke_check_ids
    .approve / .restore_revision / .revision_rows
    .summary / .copy / .to_dict / .from_dict
  SetsLibrary.sets / .find / .ids / .by_section / .approved / .drafts
    .upsert / .create / .copy / .remove(force) / .summary / .section_rows

acceptance/programme.py
  ProgrammeItem(check_id, order, mandatory, sources, title, module, group,
                check_class, requirement, expected, automation)
    .source_ids / .source_note / .in_catalog / .has_snapshot
  ProgrammeRevision(revision, at, author, comment, approved, reduction, set_refs, items)
  Programme(items, set_refs, revision, status, reduction, approved, revisions)
    .from_sets(library, set_ids) / .rebuild(library, set_ids) → отчёт о сборке
    .find / .of_section / .selected_set_ids / .mandatory_ids / .status_label
    .add_check / .exclude / .move / .reorder / .set_mandatory  (смоук не исключается)
    .targets / .coverage / .uncovered_sections / .warnings(library)
    .summary / .rows(results) / .delta(revision)
    .snapshot / .archive / .revise / .approve(by, comment, reduction) / .restore_revision
    .revision_rows / .to_dict / .from_dict
  template_programme(name, library, failed_ids)   TEMPLATE_FULL / SMOKE / REGRESS
  regress_check_ids(failed_ids)   load_programme(session)   save_programme(session, …)
```

Правила, зафиксированные в коде и проверенные тестами:

* `rebuild` — объединение по ИЛИ, дедупликация, происхождение (`sources`), порядок по
  приоритету наборов, **обязательные пункты первыми**, ручной порядок не теряется;
* правка состава запрещена, пока ревизия утверждена (`_require_draft`) — нужна новая
  ревизия; архивные ревизии неизменяемы, `restore_revision` создаёт **новую** ревизию;
* `approve` требует непустую программу и обоснование (`reduction`) при непокрытых
  разделах; утверждение попадает в ревизию и в поле `approved`;
* `rows(results)` **не хранит** статус: единственный источник — `results.py` /
  `session.checks` (`DR-P-5`), программа только подтягивает его для таблицы;
* `delta(revision)` при отсутствующем номере возвращает `missing: True`, а не «дельту
  с ближайшей ревизией» — молчаливая подмена сравниваемой ревизии недопустима.

## 7. Риски

1. **Стоимость этапа 3** (11 экранов) — митигируем переиспользованием компонентов и
   порядком «сначала вертикальный срез» (`SCR-14` → `SCR-15` → `SCR-05` → `SCR-08`).

   (этап 4) держат соответствие «экран ↔ требование ↔ код».

   чтобы это не превратилось в «два планировщика», в `session.py` зафиксировано, что
   `plan` — legacy и удаляется вместе со старым интерфейсом (комментарий истории схемы).
