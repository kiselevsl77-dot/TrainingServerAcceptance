# План этапа 1b: `queue.py`, `results.py`, `runner.py`

Тактика та же — **expand → contract**: новое ядро вводится рядом со старым (`plan.py`/`plan_runner.py`/старый UI продолжают работать), единовременное удаление — на этапе 2.

## 1. `acceptance/results.py` — единый след результата (`DR-P-5`) и история повторов (`FR-P-36`)

Роль: **единственное** место, где читается/пишется статус проверки. Очередь и программа статус не хранят (риск 2 плана: «двойной учёт запрещён»).

```text
STATUS_NOT_RUN = "не выполнена"            STATUS_ICONS — из checks.registry (не дублируем)
ORIGIN_RUN = "прогон"                      ORIGIN_MANUAL = "отметка оператора"
SUSPENDED = "снято с причиной"             (origin снятия — виден в протоколе отдельно от «вне программы», FR-P-15/FR-P-35)

prepare_repeat(session, check_id) -> dict | None      # прежний результат → session.check_history[check_id]; вызывается ПЕРЕД прогоном
record(session, payload, *, replace=False) -> dict    # запись в session.checks (по одной на проверку) + событие в session.history
suspend(session, check_id, reason, *, author="") -> dict   # пустая причина → ValueError (AC-P-15); пишет результат «пропущена» + origin=SUSPENDED
resume(session, check_id) -> bool                     # возврат в очередь: снимает запись снятия, пишет событие (ничего не «исчезает молча»)
is_suspended(session, check_id) -> bool
result_of(session, check_id) -> dict | None           # запись как dict (терпимо к битым записям)
status_of(session, check_id) -> str                   # "" если результата нет
state(session) -> dict[str, dict]                     # check_id → {status, icon, verdict, at, journal_from, journal_to, repeats, suspended, reason}
row(session, check_id) -> dict                        # та же строка для таблиц SCR-05/SCR-06/SCR-08
history(session, check_id) -> list[dict]              # история прежних результатов
repeats(session, check_id) -> int
summary(session) -> dict                              # total/done/passed/failed/blocked/skipped/not_run/repeats
```

Ключевая развязка с движком: `automate()` уже пишет результат сам, поэтому исполнитель вызывает **только** `results.prepare_repeat()` до прогона — новый результат движка ложится поверх, а прежний остаётся в истории. Двойной записи нет, `engine.record_result` для старого UI не трогаем (запись в журнал решений плана).

## 2. `acceptance/queue.py` — очередь как снимок утверждённой ревизии (`IR-P-18`)

```text
QUEUE_PENDING = "ожидает"   QUEUE_RUNNING = "выполняется"   QUEUE_DONE = "выполнена"   QUEUE_OFF = "снята"
MARKER_NEXT = "следующая"   MARKER_RUNNING = "выполняется"  MARKER_LAST = "последняя"

QueueItem: check_id, order, state, reason, note, call_index, journal_from, journal_to
Queue: revision, signature, approved, draft, created_at, items, pointer,
       last_check_id, mode, pause_seconds, stop_reason

build_queue(programme, *, author="", comment="") -> Queue   # снимок: состав и порядок = текущая ревизия программы
Queue.find/index_of/size/check_ids
Queue.next_item() -> QueueItem | None      # «следующая»: первый ожидает после pointer, снятые и выполненные пропускаются
Queue.current()  -> QueueItem | None       # «выполняется»
Queue.last()     -> QueueItem | None       # «последняя» (по last_check_id) — по ней читается лента
Queue.marker(check_id) -> str              # "", «следующая», «выполняется», «последняя»  (маркеры макета SCR-05)
Queue.begin(check_id) / .finish(check_id, *, state, journal_from, journal_to)
Queue.take_off(check_id, reason) / .return_to_queue(check_id)   # причина обязательна; делегирует results.suspend/resume
Queue.reset()                              # новый прогон: отметки сняты, состав неприкосновенен
Queue.is_current(programme) -> bool        # сигнатура состава не разъехалась с программой
Queue.rows(results=None) / .summary()      # таблица и KPI экрана «Прогон»; статус берётся из results.py
Queue.to_dict / .from_dict
load_queue(session) / save_queue(session, queue, *, event="", message="")
```

Нормы, закреплённые структурой и тестами:
* **правки состава нет вовсе** — в модуле отсутствуют `add/remove/move/exclude/reorder/set_mandatory` (тест-«замок» по аналогии с `test_target_docs.py`); состав меняется только на `SCR-15` новой ревизией (`IR-P-18`);
* расхождение очереди и программы ловится `is_current()` по `signature` (хеш упорядоченных `check_id` ревизии), а не «на глаз»;
* прогон по черновику **разрешён, но помечен** (`draft=True` → баннер «Прогон идёт по черновику программы (ревизия N)»; открытый вопрос 12 в `docs/15` §11.2).

В сессию добавляются три поля прогона: `mode`, `pause_seconds`, `last_check_id` (+ `call_index` в пункте). Это тот же v7 (поле `queue` сегодня не используется нигде), миграции не требуется.

## 3. `acceptance/runner.py` — одна команда «▶ Следующая: `TC-…`»

```text
MODE_CHECK = "сценарием"    MODE_CALL = "по вызовам"    DEFAULT_PAUSE_SECONDS = 3.0 (clamp 0.5…120)
RunOutcome: check_id, state, status, verdict, detail, journal_from, journal_to,
            duration_ms, repeats, check_result, stopped, stop_reason

next_label(queue, programme) -> str            # «▶ Следующая: TC-FILE-13» (подпись команды, IR-P-20)
needs_confirmation(queue_item | programme_item) -> (bool, reason)   # live/heavy → карточка запуска (FR-P-19); manual → «только оператор»
can_run(queue, programme) -> (bool, reason)    # готовность: нет очереди / программы / пустой состав
execute_next(queue, programme, session, runtime, *, monitor=None, client=None, params=None,
             run_evidence=None) -> RunOutcome  # begin → прогон → results → finish → pointer++, last_check_id
execute_check(...) / execute_call(...)         # прогон пункта целиком / один вызов режима «по вызовам»
run_batch_tech(queue, programme, ...) -> list[RunOutcome]   # «▶▶ Пачка tech (N)»
auto_step(queue, programme, ...) -> RunOutcome | None        # один шаг авто («⏯ Авто с паузой»); таймер — в UI
auto_stop_reason(queue, programme, *, card_pending=False, stop_requested=False) -> str   # правила останова
collect_queue(queue, programme, session) -> dict   # KPI, маркеры, ready/не готово — одним вызовом для экрана
call_steps(spec) / expected_statuses(...) / judge_response(...) / parse_operation(...) / path_params / query_params / plan_endpoint
```

* `MODE_CHECK`: пункт прогоняется сценарием (`checks_runner.automate`), статус/вердикт/диапазон журнала — из результата, `state=выполнена`; повтор пишет историю.
* `MODE_CALL`: один шаг = **один вызов** проверки (операции реестра + негативные пробы `probe_paths`, ожидание 404/405 — как в `plan.py`), `call_index++`; когда шаги кончились — пункт закрывается.
* `live`/`heavy` без подтверждения — запрос **не отправляется** (стоп + причина и id пункта для карточки запуска); пачка/авто останавливаются.
* Функции оценки вызова (`expected_statuses/judge_response/parse_operation/path_params/query_params/plan_endpoint`) переносятся в `runner.py` как чистая копия ~80 строк из `plan.py`: новый исполнитель **не должен** зависеть от модуля, который удаляется на этапе 2 (это зафиксирую в журнале решений).
