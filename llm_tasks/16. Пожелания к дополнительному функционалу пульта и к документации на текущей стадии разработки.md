# Пожелания к дополнительному функционалу пульта и к документации на текущей стадии разработки

## 1. Дополнительные требования к функционалу

| Функционал                      | Пояснение                                                    | Зачем и как                                                  |
| ------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| Монитор обмена                  | Вертикально расположенная лента, отображающая отправленные вызовы API и поступившие ответы.<br />Компонент должен содержать возможность выбирать степень подробности запросов и ответов (по раздельности). | Текущий способ "отправить все залпом" может не подойти для испытаний с точки зрения прозрачности. Приемочной комиссии нужно видеть по раздельности каждую отправляемую команду (вызов) и получаемый ответ, а также иметь возможность повторной отправки с подкорректированными параметрами. При этом, должна быть возможность скопировать содержание отправляемого запроса, проанализировать его и отправить средствами curl |
| Контроль исполнения вызовов API | Добавить возможности исполнения API вызовов по одной (по команде оператора), а также исполнения задач с заданной оператором паузой | Сейчас, как сказано выше, отправляется все "залпом", в соответствии с выбранным фильтром. <br />Для реализации механизма отправки вызовов (команд) по одной в добавок к монитору обмена требуется добавить кнопки "Выполнить" (следующую команду, которая запланирована по программе испытаний).<br />Также, следует иметь визуальный компонент, в котором будет сразу показываться успех выполнения запроса (соответствие ожиданиям). |
| Программа испытаний             | В дополнение к монитору обмена следует показывать список запланированных вызовов | Чтобы оператор видел, какие команды будут вызываться следующими.<br />Желательно также иметь возможность снять "галочку" с некоторых из запланированных (с помощью имеющегося фильтра) вызовов  команд. |

## 2. Замечания

1) В документе "12. Руководство пользователя пульта испытаний (функционал и правила).md" остались ссылки на SOM1.json в то время, как мы перешли на контракт api_17_09_26.json. Проверь обоснованность ссылок.
2) Раздел 15.5, пункт 4 содержит ссылку на phase_connection и ph_n. То же в п. 25.2 в таблице. Проверь актуальность.
3) app.log сейчас пишется одной длинной лентой, и становится не удобным искать нужный фрагмент. Нужно либо ввести разделение по запускам сервера (какая-то разметка вроде линии //--------------------------//), либо выделить для них отдельную папку applog и писать отдельные файлы логов с датой и временем запуска сервера (мне так нравится больше).
4) Требуется четко разнести терминологию, касающуюся испытываемого сервера и нашего backend/UI. Такие термины как "задача", "карточка" требуют либо уникальности, либо какого-то выделения префиксом/постфиксом, как $Задача, %Карточка (например, сущности сервера выделять префиксом $, а внутренние сущности пульта не выделять).

## 3. Вопросы

1. Как формируются файлы для отправки в рамках проверок (те, которые содержат __TEST__)? Оператор должен четко понимать, что конкретно отправляется на сервер обучения. Это должно быть описано в инструкции; в интерфейсе может также показываться, если не будет перегружать UI и не будет слишком сложным для реализации и сопровождения.
